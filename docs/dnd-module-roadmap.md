# Дорожная карта: D&D-модуль (интеграция с Long Story Short)

Идея: встроенный модуль приложения для игр D&D 5e поверх интеграции с [Long Story Short](https://longstoryshort.app/doc/developers/) (далее LSS). Не плагин для третьих разработчиков — внутренний модуль, включаемый на игре.

Документ зафиксирован по итогам grill-сессии 2026-10-09. Реализация начинается отдельными OpenSpec-изменениями по фазам ниже.

## Решения, зафиксированные сразу

- **Форма модуля**: встроенный модуль (`app/dd/`), подключаемый в композиции корня при признаке D&D-игры. Механизма сторонних плагинов не строим.
- **Привязка к игре, не к сессии**: модуль включается при создании игры (выбор системы в лаунчере) **или** на открытой игре (меню «Включить D&D-модуль» с подтверждением). Включение = аддитивная миграция: только новые таблицы + флаг режима в `game_settings`; ни одна существующая строка не трогается.
- **Выключение с сохранением**: таблицы D&D остаются, флаг гаснет, повторное включение возвращает всё. Удаление D&D-данных — отдельная явная операция (вне roadmap до требования).
- **Обычное приложение не отказывает** игру с модулем: открывает как обычную + предупреждение «в игре есть D&D-модуль, эта версия его игнорирует; данные сохранены». `.nri`-архив такой игры открывается и переносится так же. Старые ограничения «другая БД / нельзя импортировать / только на старте приложения» **сняты**.
- **offline-first**: интернет нужен для первого скачивания SRD/хоумбрю, ИИ-генерации и фазы 4. Игра на скачанных датасетах работает офлайн.
- **Реестр сущностей остаётся один**: модуль регистрирует свои типы в существующем `entity_registry`; ядро ничего не знает о D&D (охранки слоёв остаются).
- **Датасеты глобальны**: хранилище `~/.nri_manager/datasets/`, игра подключает наборы списком id; в игру пишутся только внешние ссылки по id (формат LSS). SRD 5.1/5.2 скачиваются с longstoryshort.app при первом включении модуля.
- **Записи датасетов — read-only сущности реестра**: шесть типов записей (вид/подвид/класс/подкласс/предыстория/черта) — справочные сущности с парным ключом «датасет + id»; заклинания — отдельные сущности «слаг + источник» (SRD-2014/2024 — только имя и честная строка «полный текст в LSS»; текст — из гримуарных файлов). Всё видно в поиске, упоминаниях и предпросмотре; правка только через файл источника; в настройках D&D-игры — один переключатель «показывать справочные записи в поиске» (монстров не касается).
- **Метка системы**: в списке игр лаунчера и в шапке главного окна у D&D-игры — подпись «D&D».
- **Никаких аккаунтов и логинов в продукте**: личность игрока живёт в сессии LSS внутри iframe; у нас — только код стола (как в «Столе»).
- **Перед фазой 4 — обязательное согласование с LSS**: домен в белом списке (CSP `frame-ancestors`), слаг приложения, архитектура встраивания (LSS просят обсуждать до кода; `@shakusky` в Telegram). Страница-мост при этом не нужна (см. факты): согласуем HTTPS-домен и прямой SDK-встраиваемый экран.
- **Заклинания LSS — отдельный канал от датасетов**: гримуар импортирует/экспортирует заклинания только в формате Foundry VTT; наш хоумбрю заклинаний — файлы этого формата, генерация (фаза 3) целится в него.
- **Интеграция с LSS односторонняя — только импорт**: файл персонажа от игрока → наши поля → дальнейшее управление у нас. Мы ничего не отправляем в LSS: группы (`lss:group-*`) и комнаты Vortex не используем.

## Фазы (порядок)

| # | Фаза | Что это | Приоритет |
|---|---|---|---|
| 1 | **Модуль + датасеты** | Включение/выключение на любой игре (аддитивная миграция, флаг, предупреждение в обычном приложении), глобальное хранилище датасетов, скачивание SRD 5.1/5.2 и двух файлов SRD-слагов заклинаний, импорт хоумбрю-датасетов, Python-валидатор датасетов по полному списку проверок LSS (error/warning) | ядро |
| 2 | **D&D-лицо игры** | Одно изменение: справочный лист датасетов с вкладками по типам и заклинаниями; поля карточек разложены по табам (общий механизм), табы «D&D»/«Заклинания» у персонажа (класс/вид/уровень со ссылками на датасет и снимками имён, ссылка на лист LSS — прямой адрес `/iframe/characters/digital/<id>/` при наличии id; привязки заклинаний — ссылки, не копии); импорт персонажа из файла-экспорта LSS (сырой файл хранится всегда); монстры — свои сущности модуля (карточка + лист «Бестиарий»), а не разделы датасетов; встречи — надстройка события (таб «Встреча» + декоративная пометка лестницы); гримуары Foundry-формата в глобальное хранилище (слаги расширяют словарь валидатора); справочные сущности и монстры в поиске/упоминаниях/предпросмотре/закреплениях; пометки лестницы от внешних источников | высокая волна |
| 3 | **Генерация в форматах LSS** | ИИ выдаёт датасеты (по одному сущностному файлу за вызов против `dataset-*.json`), документы персонажей (`character.json` v2) и файлы заклинаний в Foundry-формате; круг «генерация → валидатор → перегенерация»; экспорт файлов для импорта в LSS; SRD как few-shot | после 2 |
| 4a | **C-lite: лист ГМа в приложении** | Наша HTTPS-страница на согласованном домене с SDK прямо в ней (страница-мост НЕ нужна — это паттерн столов, чьи расширения умеют только открывать URL; наш QWebEngine исполняет JS сам) + регистрация домена/слага в LSS + QWebEngine/QWebChannel; события собственного листа ГМа приходят в приложение напрямую | конец |
| 4b | **C-full: броски игроков** | Публичный сервер-посредник: игрок открывает нашу страницу в браузере, событие идёт на сервер, приложение ГМа забирает его по коду игры. Без аккаунтов — код стола + токен участника. Комнаты Vortex не используем — своё решение | самый конец |
| — | **Хвост low** | Предметы/лути; пресет календаря D&D-мира в мастере календаря; синхронизация HP к нам в карточку (`dnd:health`) и «урон/лечение» из нашего интерфейса (`lss:command`) — только после стабилизации этих API у LSS | по требованию |

```
1 → 2 (поля персонажа → импорт файлов LSS → монстры/встречи)
      → 3 (датасеты → персонажи)
            → 4a → 4b   (перед 4 — переговоры с LSS)
```

### Статус реализации (на 2026-10-10)

- **Фаза 1** — изменение `add-dnd-module-foundation`: реализовано, живые QA-процедуры в `docs/qa/test-cases/13-dnd-module-foundation.md`; архивирование OpenSpec не выполнено.
- **Фаза 2** — одно изменение `add-dnd-game-face`: реализация завершена (табы карточек, справочник, D&D-лицо персонажа, импорт LSS, монстры/бестиарий, встречи, гримуары, внешние источники в реестре); кейсы — `docs/qa/test-cases/14-dnd-game-face.md`. Заклинания и гримуары перенесены в фазу 2 (в фазе 1 — только файлы SRD-слагов как словарь валидатора).

## Факты об интеграции (на 2026-10-09)

- **Датасеты** — статические JSON по публичным URL без ключей; JSON Schema draft-07 (`wizard-dataset.json`, по-сущностные схемы, `grant.json`); закрытый словарь грантов — 28 типов; SRD-наборы — production-данные LSS, эталон для few-shot и golden-тестов конвертера.
- **В датасетах шесть секций, монстров и текстов заклинаний нет** — файл датасета несёт виды, подвиды, классы, подклассы, предыстории и черты; монстры у нас — свои сущности модуля (бестиарий), тексты заклинаний живут в гримуарах Foundry-формата, а SRD-заклинания — только файлы слагов.
- **Жёсткие правила датасетов**: `id` сущности — внешний ключ навсегда; лицензия обязательна и только CC0 / CC-BY / CC-BY-SA с версией; правка датасета ретроактивна для уже собранных персонажей; реестра публикации нет — обмен файлами.
- **Формат персонажа** — документ `jsonType: "character"`, `version: "2"`, `data` — JSON-строка по `character.json`; единственный канал бонусов — `data.bonuses`; текстовые блоки — документ форматированного редактора (не HTML; `blockquote` запрещён, неизвестный тип узла ломает блок); формулы — латиница, переменные заглавными (`[STR]`, `[PROF]`). Импорт в LSS делает игрок средствами LSS; публичного REST API персонажей для хоста нет.
- **Встраивание листа** — iframe + postMessage, SDK `@longstoryshort/vtt-sdk` (MIT). Стабильно `lss:roll`; состояние `lss:manifest`/`dnd:health` и команды `lss:command` зарезервированы. Работает только со страниц на домене из белого списка LSS (localhost нельзя). Хост не может открыть чужой лист; листы игроков шлют события только своим хост-сессиям.
- **Группы** (`lss:group-*`, SDK ≥ 0.8.0) — общие права за столом внутри LSS; требуют слаг приложения. **Нас не затрагивают**: группы имеют смысл только когда хост рассылает код группы в листы игроков, а мы в LSS ничего не отправляем. Импорт листа игрока к нам покрыт фазой 2 (файл-экспорт), чтение мастером подключённых листов — интерфейс LSS, не наш продукт.
- **Vortex (комнаты LSS)** — у LSS свой стол: 6-значный код комнаты, игроки подключают листы, броски идут туда. Не используем: фаза 4b — своё решение.
- **Канал заклинаний** — гримуар LSS импортирует/экспортирует заклинания в формате Foundry VTT; это отдельный путь от импорта датасета. Датасет называет не-SRD-заклинание слагом, который резолвится только у игрока, загрузившего свой файл заклинаний. Файлы слагов SRD (`srd-spell-slugs-2014/2024.json`, 318+339 записей) — гейт предупреждения валидатора «слаг вне SRD».
- **HTTPS обязателен для любого встраивания** — и инструменты, и iframe листа отказываются встраиваться в не-HTTPS (даже `http://localhost` — пустой фрейм по `frame-ancestors`). Контент QWebEngine из `file://` или собственной локальной схемы — тоже не встраивает: нашим хост-страницам нужен настоящий HTTPS на согласованном домене.
- **Лист — адресный** — кроме `/iframe/characters/list/` есть `/iframe/characters/digital/<id>/` и `/iframe/characters/builder/<id>/`; страница-мост нужна только столам с URL-расширениями (Owlbear), приложениям с собственным JS — прямой SDK.
- **Состояние и команды листа** — `dnd:health` лист шлёт сам при каждом изменении HP (включая правки игрока в листе); `lss:command` (`op: adjust, capabilityId: hp`) меняет HP извне. Оба зарезервированы: ни под них ничего не резервируем и не пишем до стабилизации API у LSS.
- **Инструменты** (калькуляторы и т.п.) встраиваются без белого списка и авторизации — кандидат на дешёвое украшение UI позже.
- **Смены контрактов** LSS документирует в Changelog интеграций с «рецептом лечения» — валидатор и импортёры пиновать версии схем и читать changelog при обновлениях.

## Границы, зафиксированные grill-сессией

- Модуль не лезет в ядро: ядро, БД-миграции базовой схемы и обычный флоу не знают слов «D&D»; всё добавочное — таблицы/типы/экраны модуля.
- Включение и выключение обратимы и не трогают существующие данные; «повышения» обычной игры не существует — это обычный включаемый модуль.
- Обычное приложение не теряет и не портит D&D-данные (просто игнорирует незнакомые таблицы).
- Фазы 4a/4b не обещают ничего до письменного согласования домена, слага и архитектуры с LSS; QWebEngine входит в продукт только вместе с 4a как отдельное решение о зависимости.
- Генерация (фаза 3) не выдаёт файл наружу, пока он не прошёл собственный валидатор с полным списком проверок LSS.
- **Два профиля сборки обязательны**: приложение работает и без модуля вообще (только ядро), и с включённым D&D-модулем. Каждый прогон приёмки проверяет **оба** — тесты ядра на чистой сборке (код `app/dd/` недоступен составу) и тесты ядра + модуля; зелёный только один профиль — не зелёный.
- **Тест-кейсы к каждому изменению**: каждый OpenSpec этого эпика включает задачу запуска скилла `openspec-test-case-generator` по спекам изменения; результат — тест-кейсы в `docs/qa/test-cases/` с трассировкой требований.

## Как работать с фазой

1. `/grill-me` фазы (или куска, если фаза велика — как с чар-листами).
2. `/opsx-propose` — только этот кусок; в tasks сразу включается задача запуска `openspec-test-case-generator` по спекам изменения.
3. Apply отдельным изолированным изменением; гейка не меняется: `ruff check` + `run_tests_isolated.py` **в обоих профилях** (ядро без модуля и ядро с модулем), покрытие 100 %.
