# Спайк: кастомный календарь — зона затронутых изменений

**Проведён 2026-09-16 grill-сессией. Дерево решений зафиксировано там же; план — [дорожная карта календаря](custom-calendar-roadmap.md). Код не менялся.**

Задача спайка: до планирования выяснить, что затронет переход с григорианского календаря (`datetime.date`, `QDate`, `QCalendarWidget`) на настраиваемый игровой (своё число месяцев, длины месяцев, имена и длина недели, вставные дни), и где находится точка входа настройки календаря в жизненном цикле игры.

---

## 1. Как календарь устроен сейчас

Единого календарного модуля нет: над датами Python/Qt висит тонкая надстройка эпох.

- **Домен.** `app/domain/date_era.py` — `era_key(date, is_bc)` через `date.toordinal()` (BC — зеркало григорианского календаря, константа `BC_YEAR_STEP = 732 = 2×366`), `cmp_era_dates`, диапазон `1…9999`. Дата сущности — `datetime.date` + булев флаг эры (`BaseEntity.start_date/end_date/start_bc/end_bc`, `app/domain/entities/base.py`).
- **Хранение.** 6 датированных таблиц (`_ERA_TABLES`: events, organizations, characters, items, locations, ratings): `Date`-колонки (в SQLite — ISO-строка `YYYY-MM-DD`) + era-флаги + производные `start_key/end_key` INTEGER. Ключи синхронизируются ORM-хуками `_sync_era_keys` (`db/models.py:25-40`) и идемпотентным SQL-бэктиком на старте (`db/migrations.py:_backfill_era_keys` — на `julianday`/`strftime`, то есть ещё одна копия григорианской формулы).
- **Запросы.** Всё (`ORDER BY`, фильтр окна таймлайна, снимок мира) идёт только через `start_key/end_key` — лексикография ISO-строк расходится с хронологией на границе эпох.
- **UI дат.** Нативный `QCalendarWidget` в двух местах: `theme_date_popup.py::_CustomCalendar` (одиночная дата; используется диалогом события, карточкой сущности, снимком мира) и `timeline_date_popup.py::_DateWindowPopup` (чип «Выбор даты» — два календаря, диапазон). Сетка дней, длины месяцев, дни недели — целиком внутри Qt; приложение подменяет только навигационную панель (комбо месяцев, спин года `1…9999`, чекбокс «до н.э.»).
- **Имена месяцев.** Единственная настройка: ключ `custom_months` в `game_settings` (JSON `{1..12: имя}`), процесс-глобал `_current_months` в `presentation/utils/date_utils.py`, читается «в момент рисования». Редактируется диалогом `MonthSettingsDialog` (жёстко 12 полей).
- **Настройки игры** читаются напрямую (без репозитория) в `Application.start()`: загрузка месяцев — `main.py:166`, сохранение через сигнал-цепочку `_on_month_settings` (`main.py:825-837`: set → save → перезагрузка таймлайна).

## 2. Точка входа: жизненный цикл игры

- `main()` → `GameLauncherDialog.exec()` → при выборе игры `Application.start(db_path)`: `ensure_game_directory` → `create_engine` → **`init_db` (первый момент, когда схема и `game_settings` существуют)** → `_load_month_settings` → репозитории → сервисы → VM → `MainWindow` → `timeline_vm.load_events()` → `show()`.
- `GameDataManager.create_game()` (`db/game_manager.py:88-105`) создаёт **пустой** файл БД; различие «новая игра vs старая» в `start()` видно только по отсутствию ключа в `game_settings` — эталон сидирования «один раз для новой игры»: `_seed_default_event_types` (`migrations.py:154-167`).
- Лаунчер синхронный и БД не открывает вообще; «создание игры» — однострочный `QInputDialog` (`game_launcher_dialog.py:130-141`). Принести мастер создания в лаунчер — значит притащить в него асинхронную работу с БД.
- Переключение игры = `shutdown()` + `start(path)` (`_on_game_selected`, `main.py:306-345`) — любой календарный стейт обязан перезагружаться в `start()`, как сейчас `set_custom_months(...)`.
- Экспорт/импорт игры (`game_manager.py:153-259`) пакует `game.db` целиком: настройки календаря, лежащие в `game_settings`, переезжают с игрой бесплатно. В глобальном `~/.nri_manager/*.json` — разъехались бы. Ровно один вывод: **только `game_settings`**.

## 3. Инвентарь точек касания

Всего ~35–40 файлов app-кода из ~140 (~25%) при переходе на «координаты игрового календаря + пересчитываемый ключ» (решение сессии).

### Ядро — переписывается (6 файлов)

| Файл | Что делает | Завязка на григорианский |
|---|---|---|
| `domain/date_era.py` | `era_key`, `cmp_era_dates`, `assert_range` | `toordinal()`, константа 732, зеркало BC — полная |
| `presentation/utils/date_utils.py` | формат `dd Month yyyy[ г. до н.э.]`, процесс-глобал месяцев | фикс. 12 месяцев `_DEFAULT_MONTHS` |
| `infrastructure/db/models.py` | era-колонки 6 таблиц, хук `_sync_era_keys` | хук зовёт `era_key` |
| `infrastructure/db/migrations.py` | `_MIGRATIONS`, `_backfill_era_keys` | второй экземпляр формулы на `julianday`/`strftime` |
| `infrastructure/repositories/event_repository.py` | ORDER BY/FILTER по ключам | только через ключ — переживает замену |
| `presentation/views/timeline_rows.py` | строки/окно/сортировка таймлайна (qt-нулевое ядро) | через `era_key` + `format_game_date` |

### UI календаря — заменяется целиком

| Файл | Зависимость |
|---|---|
| `views/theme_date_popup.py` | `QCalendarWidget`/`QDate`, комбо `range(1,13)`, диапазон `MIN_DATE/MAX_DATE = QDate(1,1,1)…(9999,12,31)` |
| `views/timeline_date_popup.py` | две `_CustomCalendar`, `cmp_era_dates`, предзаполнение через `QDate` |
| `views/event_dialog.py`, `views/entity_card_dialog.py` | legacy-прокси `date()/setDate(QDate)` — публичный API для тестов |
| `theme/compiler.py:326-370` | QSS-правила класса `QCalendarWidget` — косметика, умирает вместе с виджетом |

`QCalendarWidget` принципиально не способен показать «13 месяцев по 28 дней» и свою неделю — замена на собственную сетку неизбежна.

### QML — григорианского кода нет

В QML даты приходят готовыми строками (`startDisplay/endDisplay/dateDisplay`, `windowText`) и флагами эры; `isoDate` — непроверяемая строка, QML её не парсит. Единственный ISO-контракт в обратную сторону — `WorldSnapshotViewModel.setDateIso` → `date.fromisoformat` (`world_snapshot_view_model.py:232-238`), QML-кодом не вызывается. Вся Qt-григорианщина сосредоточена в двух widgets-попапах.

### Транзит и приложения

- `event_service.py`, `entity_service.py`, `wiring.py:637-652` (снимок мира: дата → ключ) — даты идут насквозь kwargs'ами, риск низкий.
- VM (`timeline_viewmodel`, `detail_panel_view_model`, `search_viewmodel`, `event_dialog_island_view_model`, `entity_card_island_view_model`, `world_snapshot_view_model`) — сравнения через ключ (живут), подписи через `format_game_date` (переписываются), QDate-дефолты `date.today()`.
- `xlsx_schema.py:327-409` — парсинг дат импорта: ISO, Excel-дата, regex «N месяца Y г. до н.э.», справочник `_BC_MONTHS` из 12×2 хардкодных русских имён (комментарий прямо пишет: кастомные имена вне области парсинга). Переучивается под игровые имена.
- `xlsx_import_service.py` — ghost-границы по `era_key`, `_era_text` в ISO.
- **«Скачать шаблон» — побайтовое копирование статического файла из ресурсов** (`xlsx_import_dialog.py:64-70`); шаблон по календарю требует генерации на лету.
- `month_settings_dialog.py` + `month_settings_view_model.py` + `qml/MonthSettingsRoot.qml` — жёстко `range(1,13)`; удаляются, мигрирует значение ключа.
- `main.py` — загрузка/сохранение месяцев и цепочка обновления (`825-837`) становятся образцом для календарь-настроек; `main_window.py` — пункт меню.

### Не трогать

Системное время (`utcnow`/mtime/`meta.json`) в `character_sheet_*`, `image_store`, `game_manager`, лаунчере — к игровому календарю отношения не имеет.

## 5. Риски и коварные места

1. **Процесс-глобалы.** `_current_months` — мутабельный модульный dict; календарь-объект по тому же пути повторяет ту же проблему (устаревание при переключении игры, тесты). Сознательное решение: либо тот же паттерн с аккуратным сбросом в `start()`, либо DI.
2. **Две копии формулы ключа** (Python `era_key` + SQL-бэкфилл на `julianday`) обязаны остаться согласованными при миграции C1.
3. **Константа BC 732** выведена из григорианского года; для игрового календаря зеркало «до н.э.» нужно считать через длину игрового года (включая вставные дни).
4. **Невалидные координаты после смены длин месяцев** (31-е число в 30-дневном месяце, 13-й месяц после сокращения) — нужна политика авто-сдвига со списком перенесённых записей (решение сессии), закладывать в миграцию записей, а не только в мастер.
5. **Лексикография ISO-координат потеряет смысл** как порядок — порядок только через ключ; любой новый запрос обязан ходить по `*_key`, как сейчас.
6. **Порог >20 файлов** («крупные PR разбивать») — куски C1/C3 уже близки; делить по образцу R3 (два последовательных изменения внутри куска) при необходимости.

## 6. Итог

Тезис сессии подтверждён: таймлайн действительно корневой потребитель, но весь его запросный слой уже изолирован за целочисленным ключом — замена календаря сводится к новому арифметическому ядру (координата ⟷ порядковый день) и замене двух widgets-календарей на собственную сетку; QML и репозитории почти ничего не замечают. Дорожная карта и порядок кусков — в [custom-calendar-roadmap.md](custom-calendar-roadmap.md).
