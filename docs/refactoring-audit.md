# Аудит архитектуры: карта мест для рефакторинга

Дата аудита: 2026-09-22
Область: `app/` (+ `tests/` только как индикатор безопасности правок; `build/`, `dist/`, `alembic/` исключены)
Метод: сплошное чтение продакшн-кода, поиск отклонений от базовых принципов.
Здесь зафиксированы только места и целевые решения; сам рефакторинг выполняется отдельным применением OpenSpec-предложения.

## Критерии (зафиксированные нормативы)

Проверялось соответствие таким принципам:

- **SOLID** (единая ответственность, открытость/закрытость, подстановка, разделение интерфейсов, зависимость от абстракций).
- **DRY** — одно знание в одном месте.
- **KISS** — простота решения.
- **YAGNI** — нет кода «на будущее».
- **Закон Деметры** — объект не лезет во внутренности смежного (`a.b.c.d()`, приватные атрибуты чужого).
- **Композиция над наследованием.**
- Мелочи сугубо про производительность не включаем, если они не являются следствием архитектурного нарушения (зафиксировано в рамке grill-сессии).

Правило сортировки списка: сначала наибольшая польза при условии, что правку страхуют существующие тесты. Непокрытые гиганты включаем с задачей «сначала покрыть тестами».

Метки критичности: **К1** — мешает развивать/ломает молча; **К2** — заметный долг, чинится целиком; **К3** — приложимые мелочи (в OpenSpec-задачи не идут, только в отчёт).

С 2026‑09‑22 этот список критериев — не разовая линза аудита, а постоянная норма: он фиксируется нормативным разделом «Coding principles» в `AGENTS.md` (задача 7.4) и применяется ко всем будущим правкам, включая сессии ИИ. Покрытие: шлюз 100% по строкам (уже в `pyproject.toml`/CI) — поддерживать, не измельчать (задача 7.5).

## Глубокое исследование Q14: кто владеет сессией и транзакцией

### Как устроено сейчас

- **Одна сессия на игру.** `Application.start()` создаёт движок и фабрику сессий (`app/main.py:175-176`), берёт ровно один экземпляр (`:179`) и раздаёт всем репозиториям (`:209-215`, `:284-292`, `_build_entity_services:933-950`) и `ImageStore` (`:180`). Фабрика формально есть, но порождает ровно одну сессию.
- `expire_on_commit=False` (`app/infrastructure/db/database.py:27-28`) — карта объектов живёт всю игру, службы вынуждены делать ручные `refresh`/`expire_all` (`entity_service.py:175`, `calendar_settings_service.py:359,494` и др.).
- **Вместо транзакций — сериализация.** Глобальный `asyncio.Lock` `ApplicationWiring._session_lock` (`wiring.py:60`) + `_spawn` (`:69`) сериализуют весь работу с сессией; контракты «мок-диалог держит лок» описаны только комментариями (`main.py:651-656`, `character_sheet/list_dialog.py:27`).
- **`BaseRepository`** (`infrastructure/repositories/base_repository.py:14-72`): `(session, model)` в конструкторе, приватно `_session/_model`; запись — только `flush()`, коммита нет. Все девять репозиториев принимают сессию в конструктор и живут с ней всю игру.
- **Кто кому несёт сессию.** `main` → репозитории и напрямую в `CalendarWizardViewModel` (`main.py:413,483`); сервисы подглядывают в `repo._session` (5 мест, C1); календарный сервис — единственный с честным параметром сессии на вызов; `wiring`/`main` лезут в `app._session` напрямую (B3).

### Разброс коммитов/rollback по слоям (итоги карты)

- Коммитят: `wiring.py:333` (создание сущности «снаружи»), `main.py:1254` (сохранение LLM-настроек), `entity_service.py:183`, `event_service.py:122,144,203,267`, `calendar_settings_service.py` (восемь мест — сознательные микро-транзакции стадий мастера, норма дизайна D6 из карты календаря), `character_sheet_service.py:157,207,255,277,302`, `character_sheet_instance_service.py:96,121,134,150,166,179`, xlsx `:805` + коммит-хранилище картинок `store.py:195,242`.
- Роллбачат несогласованно: `event_service.save_event_type` коммитит без обёртки отката (`:122`), `delete_event_type` глотает ошибку (`:146-148`), у половины методов листовок отката нет вовсе (перечислены выше: `:255`, `:302`, `:134`, `:150`, `:179`).
- **Владение разорвано:** создание сущности коммитит `wiring` (`:333`), обновление — сервис (`:183`), создание события — сервис (`:203`), а popup-ветка создания связанной сущности не коммитит **никто** (`wiring.py:593-628`) — она «едет» на следующем случайном коммите.

### Небезопасные сценарии (реальные цепочки в коде)

1. **Popup-сущности едут на чужом коммите.** Диалог события → «Создать нового» → создание + `sync_related` + `flush` без коммита (`wiring.py:602-614`). Если до финала родительского диалога другая задача коммитит (сохранение типа события `event_service.py:122`, сборщик мусора картинок `store.py:195`, черновик календаря `calendar_settings_service.py:303`, LLM-настройки `main.py:1254`) — **отменённая сущность остаётся в базе**. Обратная очистка (`:674-678`, удаление при отказе) тоже без коммита: удаление висит незаписанным и уезжает на случайном коммите или сгорает при чужом откате (`:355/:429/:568`).
2. **Тотальный откат при коллизии картинки.** Конфликт контрольной суммы при загрузке изображения (`store.py:79-85`) делает `rollback()` **всей** общей незакоммиченной сессии: посреди xlsx-импорта это откатывает десятки уже подготовленных строк импорта, а сервис продолжает писать в те же объекты → финальный коммит `xlsx:805` пишет половину. Аналогично конфликт имени листа персонажа (`character_sheet_service.py:159`) стирает подготовленные сущности открытого диалога события.
3. **Двойной коммит внутри одного try.** `entity_service.py:183` → сборщик мусора картинок → второй коммит `store.py:195`; падение второго даёт откат и «не удалось сохранить» при **уже записанных** данных (плюс второй коммит подбирает чужие незаписанные строки общей сессии).
4. **Сборщик мусора xlsx вне try** (`xlsx_import_service.py:813-814`): падение пост-коммита → `wiring:194-199` показывает «импорт не удался», хотя всё записано.
5. **Падение коммита типа события без отката** (`event_service.py:102-123`) оставляет общую сессию грязной — мусор подмешается в следующую операцию.
6. **Коммит мимо лока:** `main.py:1216` запускает сохранение LLM-настроек сырым `asyncio.ensure_future`, минуя `_session_lock`, — тот самый параллельный доступ к сессии, из-за которого лок и вводился (докстрока `wiring.py:51-59`).
7. **`delete_event_type` глотает ошибку молча** (`event_service.py:146-148`) — пользователь не уведомлён.
8. Мастер календаря атомарен в опасном месте (`promote_draft`, `calendar_settings_service.py:319-360`), микро-коммиты стадий — нормативный дизайн; проблема лишь в том, что сессия и ORM зашли в модель представления (A2).

### Безопасность правок (тестовая завязка)

- **49 тестовых файлов** + `tests/conftest.py` конструируют репозитории/сервисы/модели представлений с голой сессией; **7 e2e-файлов** (`tests/ui/*`, строки: `test_e2e_search.py:24,32`, `test_e2e_events.py:46,118,234`, `test_e2e_wiring_gaps.py:277,430,489`, `test_e2e_llm.py:159-165`, `test_char_sheets_wiring.py:634`, `test_e2e_mentions.py:48`, `test_character_sheet_main_coverage.py:39`) используют `Application._session` как тестовый API.
- Замена сессии на единицу работы **в конструкторах репозиториев** ломает до ~49 файлов; добавление публичного свойства `session` и делегирование сервису — **0 поломок**.

### Решение (фиксируется как объём волны 5)

1. **Минимум (a) — сразу:** публичные свойства `session`/`model` в `BaseRepository`; замена `repo._session/_model` в пяти местах C1; ORM-модели, `_TABLE_MODELS` и прямой `session.get` уходят из `calendar_wizard_viewmodel` в новый метод `CalendarSettingsService` (например `record_names(session, report)`).
2. **Заплатки целостности (чинят сценарии 1–7 независимо от механизма):** сохранение LLM-настроек под лок (`run_locked`); откат-обёртка `save_event_type`; коммит после очистки popup-сущностей; в `store.py:81` — точечное сохранение вложенным сохранённым блоком (`begin_nested`) вместо тотального отката; сборщик мусора xlsx — в собственный try с логом; ошибка удаления типа события — пользователю.
3. **Единица работы (Q15) на траектории сущность/событие:** `GameSessionUoW(сессия, лок)` с контекстом `.transaction()` (коммит на выходе, откат на ошибке, защита от вложенного входа, реестр послезаписных действий). Переводятся: `entity_service.update_entity_with_relations` (коммит + сборщик → хук), `event_service.create/update_event_with_relations`, точки `wiring` popup-пути (popup получает явную транзакцию, накрывающую обе половины). **Конструкторы репозиториев не меняются** → `conftest` и 49 файлов живы.
4. **Вторая волна в тот же механизм:** мастер календаря (модель представления получает единицу работы вместо сессии — финальный выход сессии из представления, закрывает A2 полностью), `main._save_llm_settings`, `ImageStore` (через хуки), листы персонажей, xlsx (дефолтные коммит/откат-колбэки `:777-778` становится реализацией единицы работы).
5. **Не трогаем:** семантику `expire_on_commit=False` (ручные `refresh` завязаны на UI-объекты, вне рамок), календарные микро-транзакции стадий мастера (нормативный дизайн), `StubCalendar`.
