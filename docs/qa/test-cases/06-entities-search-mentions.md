# Тест-кейсы: добавление и генерация сущностей, связанные сущности, упоминания, глобальный поиск

Источники: `openspec/specs/entity-addition/spec.md`, `openspec/specs/entity-generation/spec.md`, `openspec/specs/related-entity-creation/spec.md`, `openspec/specs/mentions/spec.md`, `openspec/specs/global-search/spec.md`.

Живые проверки: `python -m app.main`, одноразовая игра `qa-<дата>`, завершение `pkill -if "app.main"`. Кейсы генерации обращаются к реальному LLM-эндпоинту — выполняются человеком по явному решению (кнопки ИИ в автостоп-режимах не нажимать).

## entity-addition (EADD)

### TC-EADD-001 — Состав меню «+» на шкале

- Требование: Меню «+» даёт точки входа создания событий и четырёх карточных типов
- Сценарий: Состав меню
- Тип: положительный
- Приоритет: P1
- Статус: уточни
- Предусловия: открыта игра, главное окно со шкалой событий.
- Шаги: 1) Нажать кнопку «+» на шкале. 2) Прочитать состав меню.
- Ожидаемый результат: меню содержит ровно «Новое событие», «Новый персонаж», «Новая локация», «Новая организация», «Новый предмет» и «Типы событий…».
- Источник: openspec/specs/entity-addition/spec.md#Requirement: Меню «+» даёт точки входа создания событий и четырёх карточных типов

### TC-EADD-002 — Пункт сущности открывает карточку своего типа

- Требование: Меню «+» даёт точки входа создания событий и четырёх карточных типов
- Сценарий: Пункт сущности открывает карточку своего типа
- Тип: положительный
- Приоритет: P0
- Статус: уточни
- Предусловия: открыта игра, главное окно.
- Шаги: 1) Открыть меню «+». 2) Выбрать «Новый персонаж». 3) Закрыть карточку без сохранения. 4) Повторить для «Новая локация», «Новая организация», «Новый предмет».
- Ожидаемый результат: каждый раз над главным окном открывается лист «Карточка: <тип>» (Персонаж/Локация/Организация/Предмет) в режиме создания новой сущности.
- Источник: openspec/specs/entity-addition/spec.md#Requirement: Меню «+» даёт точки входа создания событий и четырёх карточных типов

### TC-EADD-003 — Успешное создание локации из «+»-меню

- Требование: Карточка нового сущности сохраняется одной транзакцией без связей
- Сценарий: Успешное создание
- Тип: положительный
- Приоритет: P0
- Статус: уточни
- Предусловия: открыта игра «qa-<дата>», в которой нет сущности с именем «Тестовая локация».
- Шаги: 1) «+» → «Новая локация». 2) Заполнить имя «Тестовая локация». 3) Нажать «Сохранить». 4) Найти её глобальным поиском. 5) Открыть «Обзор мира…» и проверить раздел локаций. 6) Проверить карточку: секции связей пусты.
- Ожидаемый результат: карточка закрылась; локация записана (найдена поиском, видна в снимке мира и в панели деталей после выбора); ни с кем не связана.
- Источник: openspec/specs/entity-addition/spec.md#Requirement: Карточка нового сущности сохраняется одной транзакцией без связей

### TC-EADD-004 — Секции создания не привязывают

- Требование: Карточка нового сущности сохраняется одной транзакцией без связей
- Сценарий: Секции создания не привязывают
- Тип: негативный
- Приоритет: P1
- Статус: уточни
- Предусловия: в игре есть сохранённые сущности; открыта карточка новой сущности из меню «+» (без сохранения).
- Шаги: 1) Нажать «Привязать существующего» в любой секции. 2) Нажать «Создать нового».
- Ожидаемый результат: окно не показывается ни в первом, ни во втором случае; списки секций остаются пустыми.
- Источник: openspec/specs/entity-addition/spec.md#Requirement: Карточка нового сущности сохраняется одной транзакцией без связей

### TC-EADD-005 — Сбой записи нового сущности сообщается штатно

- Требование: Карточка нового сущности сохраняется одной транзакцией без связей
- Сценарий: Сбой записи сообщается штатно
- Тип: негативный
- Приоритет: P1
- Статус: уточни
- Предусловия: открыта карточка новой сущности из «+»-меню с заполненными именем и описанием; искусственно смоделирован сбой записи в базу (способ — вне UI, см. Пробелы).
- Шаги: 1) Нажать «Сохранить». 2) Прочитать появившееся сообщение. 3) Проверить список поиска и снимок мира.
- Ожидаемый результат: ровно одно модальное сообщение с причиной; база не изменена (сущности нигде нет); карточка открыта с введёнными данными.
- Источник: openspec/specs/entity-addition/spec.md#Requirement: Карточка нового сущности сохраняется одной транзакцией без связей

### TC-EADD-006 — Неудачное открытие карточки создания: только журнал

- Требование: Неудачное открытие карточки создания не порождает модальных сообщений
- Сценарий: Карточка не открылась
- Тип: негативный
- Приоритет: P2
- Статус: уточни
- Предусловия: смоделирован сбой конструкции/загрузки кандидатов карточки создания до любого обращения к записи (способ — вне UI, см. Пробелы); включено сохранение логов в файл.
- Шаги: 1) Выбрать пункт сущности в меню «+». 2) Убедиться, что окно не появилось и модальных сообщений нет. 3) Открыть журнал приложения.
- Ожидаемый результат: окно не появилось; модального сообщения нет; причина сбоя видна в журнале.
- Источник: openspec/specs/entity-addition/spec.md#Requirement: Неудачное открытие карточки создания не порождает модальных сообщений

## entity-generation (EGEN)

### TC-EGEN-001 — Запуск бандла на новой сущности

- Требование: Кнопка генерации сущности
- Сценарий: Запуск бандла на новой сущности
- Тип: положительный
- Приоритет: P0
- Статус: уточни
- Предусловия: AI-ассистент в статусе «готово», описание мира заполнено; открыт диалог новой сущности из «+»-меню.
- Шаги: 1) Нажать «Сгенерировать сущность» в строке заголовка. 2) Наблюдать за всеми полями с AI-кнопками.
- Ожидаемый результат: генерация всех AI-полей запустилась одновременно; каждое поле перешло в состояние генерации.
- Источник: openspec/specs/entity-generation/spec.md#Requirement: Кнопка генерации сущности

## Пробелы

1. Способ вручную смоделировать сбой записи/commitа в базу (TC-EADD-005, TC-RELC-007, TC-MENT-007) спецификациями не задан.
2. Детерминированные приёмы воспроизведения ошибок LLM (401, таймаут) для TC-EGEN-017/018 и состояний «запрос только в ожидании между попытками» / «сохранение ещё выполняется» (TC-EGEN-015/016) не заданы.
3. Текст подсказки на неактивной кнопке генерации («та же, что у AI-кнопок полей») в entity-generation не определён.
4. Текст подтверждения закрытия диалога при in-flight запросе (TC-EGEN-014) не определён.
5. Точный текст/формат агрегированного диалога ошибок бандла (TC-EGEN-017/018) не определён — заданы только правила (RU-причина, дедупликация одинаковых причин).
6. Текст ящика «мёртвое упоминание» (TC-MENT-011/012) не определён — зафиксированы только идентичность и не-critical статус.
7. Глазами наблюдаемый способ подтвердить «запрос к базе не уходит» / «ровно один запрос» (TC-SRCH-004/005) не определён.
8. Способ узнать числовой id сущности для ручной сборки маркера руками (TC-MENT-001/011/012) не определён.
9. Правила валидации имени сущности (допустимость имени «[]» для TC-MENT-003 и пустого имени при создании) спецификациями не заданы.
10. Порядок групп в списке результатов (совпадает ли с каноническим порядком реестра итерации) не определён явно.
11. Сценарий «Нет второй реализации» (TC-SRCH-022) не проверяется глазами: ненулевой-кодовый метод проверки не определён.
12. Поведение сохранения новой сущности с пустым именем (edge случайного промаха «Сохранить» в TC-EADD-003) entity-addition не задано.
13. Способ наблюдать состояние базы при открытом родителе — зафиксированы ли связи попап-сущности до его сохранения (TC-RELC-006) — не определён: модалка родителя блокирует другие окна.
