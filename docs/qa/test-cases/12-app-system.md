# 12 — Системные аспекты приложения: журнал, версия, ошибки сохранения, целостность архитектуры, UI-тесты

Источники: `openspec/specs/app-logging/spec.md`, `openspec/specs/app-version/spec.md`, `openspec/specs/save-error-reporting/spec.md`, `openspec/specs/architecture-integrity/spec.md`, `openspec/specs/ui-testing/spec.md`.

Общие предусловия (по своду правил `README.md`): живые UI-проверки — `python -m app.main`, одноразовая игра `qa-<дата>`, кнопки генерации ИИ не нажимать, завершение `pkill -if "app.main"`. Кейсы-гейты запускают тестовые прогоны в однократной копии/ветке checkout, если требуется временное нарушение.

## app-logging (LOGG)

### TC-LOGG-001 — Журнал пишется в каталог настройки, а не в каталог запуска

- Требование: Файл журнала — в каталоге настройки, с ротацией
- Сценарий: Каталог не зависит от способа запуска
- Тип: хранение
- Приоритет: P1
- Статус: уточни
- Предусловия: запуск из исходников (`python -m app.main`); журнал выключен.
- Шаги: 1) включить «О приложении → Сохранять логи в файл» 2) выполнить любое действие, порождающее лог 3) проверить наличие файла `nri_manager.log` в домашнем каталоге приложения (тот же корень, где лежат настройки `ui.json`/`llm_config.json`) 4) проверить каталог репозитория/запуска
- Ожидаемый результат: файл журнала создан в каталоге настройки пользователя; в каталоге репозитория файла журнала нет
- Живая проверка: аудит 2026-09-24 «about-menu-audit» (отчёт архивирован) §Логи в файл — тумблер включается через `osascript` System Events (пункт «Сохранять логи в файл», mark `AXMenuItemMarkChar` = ✓); `ls ~/.nri_manager/` — `nri_manager.log` там; `ls` корня репозитория — файла нет
- Живая проверка: аудит 2026-09-25 «table-llm-logging-live-audit» (отчёт архивирован) AB5 — после живого AX-нажатия пункта меню журнал пишется в `~/.nri_manager/nri_manager.log` (переписка при включении/выключении); `find <repo> -maxdepth 1 -name '*.log'` и `git status --porcelain` — ни одного `.log` в dev-дереве
- Источник: openspec/specs/app-logging/spec.md#Файл журнала — в каталоге настройки, с ротацией

### TC-LOGG-004 — Выключение журнала останавливает запись и снимает дескриптор

- Требование: Файл журнала — в каталоге настройки, с ротацией
- Сценарий: Выключение снимает дескриптор
- Тип: состояние
- Приоритет: P2
- Статус: уточни
- Предусловия: журнал включён, в файл уже пишутся записи.
- Шаги: 1) выключить журнал пунктом меню «Сохранять логи в файл» 2) выполнить действия, порождающие лог 3) проверить размер/содержимое файла 4) убедиться, что дескриптор файла освобождён (способ проверки — см. «Пробелы»)
- Ожидаемый результат: новые события в файл не пишутся; дескриптор файла у процесса не удерживается
- Живая проверка: аудит 2026-09-24 «about-menu-audit» (отчёт архивирован) §Логи в файл — при включённом журнале `lsof -p <pid>` держит FD файла журнала; после выключения FD исчез, размер файла не растёт на последующую активность
- Живая проверка: аудит 2026-09-25 «table-llm-logging-live-audit» (отчёт архивирован) AB6 — при включённом журнале `lsof` показывает у процесса FD `3w` REG `nri_manager.log`; после выключения `lsof` пуст (rc=1) — дескриптор отпущен
- Источник: openspec/specs/app-logging/spec.md#Файл журнала — в каталоге настройки, с ротацией

## Пробелы

1. app-logging: способ подтвердить «дескриптор файла освобождён» при выключении журнала в ручной сессии спецификацией не зафиксирован (TC-LOGG-004).
2. app-logging: способ ручного сравнения порога журнала приложения и порога обработчика файла не задан (TC-LOGG-006).
3. app-logging: способ наработки объёма за порог ротации (~2 МБ) в ручной сессии не зафиксирован (TC-LOGG-002, TC-LOGG-003).
4. save-error-reporting: способ смоделировать сбой записи в базу в живой сессии не задан ни для одного негативного пути (все негативные кейсы SAVE, TC-ARIN-006).
5. save-error-reporting: точный текст/уровень модального сообщения об ошибке не задан («из которого понятна причина» — качественная норма без фиксированного текста).
6. architecture-integrity: средство обнаружения «сигнальный обработчик пошёл к сессии мимо `_spawn`/`run_locked`» (статический охранитель или ручной приём) спецификацией не зафиксировано (TC-ARIN-020).
7. ui-testing: спеки набора не фиксируют команду прогона E2E/widget-наборов и имена тестов; гейт-кейсы используют общий прогон репозитория `python -m pytest` (все кейсы-гейты UITT, TC-VERS-002).
8. ui-testing: способ проверки статуса job тестов CI из локальной сессии не зафиксирован (TC-UITT-026, TC-UITT-027).
9. ui-testing: значения «дефолтных таймаутов» стандартного HTTP-клиента спекой не заданы (TC-UITT-030).
