# Design: add-generate-entity

## Context

Факты текущего кода (проверены):

- PySide6 + qasync: весь async-код крутится на единственном event loop Qt, потоков нет; «отдельный поток на поле» = отдельная `asyncio.Task` с non-blocking HTTP.
- `LlmService` (`app/application/services/llm_service.py`): сейчас `asyncio.Queue` + один `_worker_loop` — requests обслуживаются строго по одному. `queue_size`, `start_worker`, `stop_worker`. Очередь — искусственное ограничение, не требование транспорта.
- `RemoteLlmProvider._request` (`app/infrastructure/llm/remote_provider.py`): цикл ретраев (до 2, backoff 0.5/1.0 c, только 429/5xx/таймаут/сеть) внутри провайдера, через общий `httpx.AsyncClient` (пул до 100 соединений) → параллельные запросы транспортом не ограничены.
- `LlmViewModel.request_generation` — per `field_id` (`"etype.field"`), сигналы `generation_started(field_id)` / `generation_finished(field_id, text)` / `generation_error(field_id, err)`. Ошибка поля сегодня **молчалива** (лог + сброс кнопки) — код не догоняет spec.
- `Application._wire_ai_buttons` (`app/main.py`) — ручная проводка per-кнопки, field_id склеивается там же.
- Диалоги `EventDialog` / `EntityCardDialog`: `get_ai_buttons()`, `AiAssistButton` per поле (progress-оверлей, read-only, disabled), `reject()` уже guard'ом не пускает закрытие во время генерации; `closeEvent` нет; диалоги открываются modeless через `open()`; «Сохранить» → `saved.emit` + `accept()`.
- Qt: ESC на QDialog идёт через `reject()`; X на modeless-диалоге шлёт close-событие, `reject()` не вызывая (сегодня дыра: сигналы долетают до уничтоженного виджета). «Клик мимо окна закрывает» — в коде механизмов не видно (modeless QDialog сам по себе так себя не ведёт), механизм уточняется тестом.
- `FIELD_CONFIG`: event=3, item=3, location=4, organization=4, character=5 полей с AI-кнопками.
- Ошибки `LlmError`/`LlmHttpError`/`LlmNetworkError`/`LlmTimeoutError` несут RU-сообщения (displays `str(exc)`). `asyncio.CancelledError` — `BaseException`, не ловится текущими `except Exception`.
- Тесты: pytest, offscreen Qt, `httpx.MockTransport` для LLM, без сети. Затронуты: `tests/application/test_llm_service.py`, `tests/presentation/test_llm_viewmodel.py`, `tests/ui/test_e2e_llm.py`.

## Goals / Non-Goals

**Goals:**

- Параллельное выполнение всех запросов генерации (одиночные и бандл) без общей очереди.
- Кнопка «Сгенерировать сущность» с полной моделью состояний диалога: блокировка полей, «Сохранить» disabled, toggle-отмена, phase-зависимая защита закрытия, агрегированные ошибки.
- Отмена как first-class сущность: фазы запроса (in-flight / ожидание ретра), scope — диалог-владелец.

**Non-Goals:**

- Изменение промтов, текстов `RemoteLlmProvider` (таймауты, политика ретраев).
- Чейнинг полей (сначала `name`, остальные с сгенерированным именем в контексте) — поля независимы (решено в обсуждении, кандидат в будущие фичи).
- Отмена одиночной генерации отдельным контролем (отменяется только как часть диалог-уровневой отмены: бандл-кнопка / закрытие).
- Настройка/лимиты параллельности, стриминг ответов, миграции БД.

## Decisions

### D1. Параллельность: task на запрос, очередь убрана

`LlmService` перестает быть очередью: `generate_for_field` создаёт `asyncio.Task` (`_run(request)`) и возвращает его результат; `asyncio.Queue`, `_worker_loop`, `queue_size`, `start_worker`, `stop_worker` удаляются. `GenerationRequest` теряет поле `future` (task сам несёт результат).

- Почему не `asyncio.Semaphore(N)`: 3–5 параллельных запросов — тривиальная нагрузка; лимит добавляет настройку без выигрыша. Локальные серверы с низким параллелизмом (Ollama, `num_parallel=1`) выстраивают очередь сами, на сервере — поведение приложения не меняется.
- Альтернатива «оставить очередь, только бандл параллельный» отклонена: два механизма для одного транспорта усложняют отмену/фазы.
- `RemoteLlmProvider` не меняется в политике: ретраи работают per-запрос независимо и корректно в параллельном режиме.

### D2. Фазы запроса и опциональный phase-hook в провайдере

Фазы нужны close-guard'у (подтверждать закрытие только при in-flight). Retry-цикл живёт **внутри** провайдера, поэтому service сам фазы видеть не может. Решение: в `RemoteLlmProvider._request` добавить необязательный `on_phase: Callable[[str], None] | None = None` (default `None` → zero overhead, остальные вызовы `check_connection` не тронуты): вызывается с `"in_flight"` перед каждым `POST` и `"waiting"` перед `asyncio.sleep` backoff. `LlmService._run` передаёт хук, пишущий в запись сервиса.

- Альтернатива «приближённо: фаза = весь call провайдера = in_flight» отклонена: делает невозможным сценарий «X молча, если запросы только в ожидании» (окно 0.5–1 c между ретраями было бы ошибочно помечено in-flight).
- Альтернатива «вынести ретраи в service» отклонена: переворот архитектуры, большой diff.

### D3. Отмена: scope = диалог, CancellationError проходит насквозь

`LlmService` держит реестр активных запросов: `_active: dict[owner, dict[field_id, _ActiveGen]]`, `owner` — непрозрачный объект (диалог; ключ по identity, не по field_id — два диалога одного типа могут быть открыты одновременно, т.к. карточка связанной сущности открывается поверх родительского). API: `cancel_all(owner)`, `any_in_flight(owner) -> bool`, `count_in_flight(owner) -> int`, запросы снимаются из реестра по завершении (в `finally`).

- Сигналы доставки `generation_finished` / `generation_error` несут owner (identity-ключ): каждый диалог фильтрует `owner is dialog`, иначе вложенная карточка того же типа сущности (те же field_id) получала бы результаты родительского диалога — owner-scope реестра продолжается до уровня сигналов.
- Отмена = `task.cancel()` по каждому. `CancelledError` (BaseException) не перехватывается существующими `except Exception` (ни provider, ни viewmodel) — task умирает отменённым, `generation_finished`/`generation_error` **не** эмитятся (отмена ≠ ошибка, диалог об ошибке не показывается). `finally`-блоки снимают запись из реестра и сбрасывают фазу.
- Кнопка-отмена бандла и guard закрытия оба идут через `cancel_all(owner)`; после отмены wire-слой синхронно сбрасывает кнопки диалога (`set_generating(False)` per кнопка) — состояние UI определяется владельцем, без сигнала `generation_cancelled` (сигнатурный контракт не расширяется, проводка и так держит ссылки на кнопки).

### D4. Оркестрация бандла — в wire-слое (`main.py`), не в ViewModel

Проводка уже живёт в `Application._wire_ai_buttons` (per-кнопки lambdas, field_id). Бандл — та же паттерн: локальный per-диалог state (`_batch: dict[field_id, text|error]`, счётчик ожидающих) в замыкании. Старт: проверить условия (status/мир/нет активной генерации) → per кнопка `set_generating(True)` → `asyncio.ensure_future` per `llm_vm.request_generation`. `generation_finished`/`generation_error` фильтруются по field_id диалога (текущая проводка уже так делает); при достижении нулевого счётчика: ошибки ≠ ∅ → один `QMessageBox.warning` (список неудавшихся + причины; одинаковая причина — один раз).

- Почему не в `LlmViewModel`: ViewModel намеренно не знает о QObject-диалогах; оркестрация «набор кнопок + диалоги ошибок per диалог» — ответственность presentation-проводки. Сигнальный контракт VM расширяется минимально (по необходимости только новые методы, без новых сигналов).
- Кнопка сущности — новый лёгкий `EntityGenerateButton(QPushButton)` в `ai_assist_button.py`: 24×24, стили из тех же констант, state idle (✨, tooltip «Сгенерировать сущность (все поля)») / cancelling (⏹/✕, tooltip «Отменить генерацию») / не готово (LLM не настроен или нет мира — стиль неактивной AI-кнопки, клик показывает ту же подсказку, что у кнопок полей, как в `AiAssistButton._on_clicked`) / идёт генерация (истинно disabled). Сигналы `batch_requested` / `batch_cancel_requested`. `AiAssistButton` переиспользовать нельзя: он требует target-поле для progress-оверлея.
- Размещение: HBox (stretch + кнопка) в самом верху формы в обоих диалогах (правый верх формы по spec).

### D5. Guard путей закрытия диалога

Диалог получает из проводки обратный коллбэк `set_close_guard(fn)` (DI-паттерн как существующая проводка `saved`/`create_related_requested`; диалог не получает ссылок на app/service). Путь закрытия:

- `closeEvent` (X и любые прочие close-события): если активна генерация (`any(b.is_generating for b in self._ai_buttons)` + сущности-кнопка) → `fn.close_requested()`; иначе default.
- `keyPressEvent`: `Escape` при активной генерации → `event.ignore()` (диалог не закрывается — spec). Вне генерации — default (→ `reject()`).
- Кнопка «Отмена»: `clicked` → `fn.close_requested()`, а не `self.reject` (сегодня — `reject`); вне генерации `fn` эквивалентен `reject()`.
- Смысл `fn.close_requested()` (реализуется в проводке, видит service и кнопки): `any_in_flight(dialog)` → `QMessageBox.warning` «Идёт запрос к LLM (N полей). Если закрыть, запрос будет прерван и результаты не появятся.»; «Нет» → closeEvent игнорируется / «Отмена» остаётся; «Да» → `cancel_all(dialog)` + обычный `reject()`. Без in-flight (только ретрай-ожидания) → `cancel_all` + `reject()` молча.
- `reject()` остаётся тем же guard'ом «не закрываем при генерации» как safety net (прямые вызовы извне), но штатные пути его уже не используют — он не может быть обойдён без осознанного `accept/reject` из кода.
- «Клик мимо окна»: статически механизм не найден; close-событие — единственная задокументированная точка закрытия, guard её накрывает. Задачей фиксируется тест: синтетическое закрытие (close-событие) во время генерации не должно пройти молча. Если тест обнаружит альтернативный путь (например, платформный), перехватывается там же.

### D6. Ошибка одиночной генерации

`_on_error` в `_wire_ai_buttons` дополняется `QMessageBox.warning(parent=dialog)`: «Не удалось сгенерировать поле «<label>»: <reason>», `reason = str(exc)` (RU-сообщения уже в `LlmError`-иерархии). Сброс кнопки — как сейчас. Это доводит код до уже существующего spec-требования «система сообщать об ошибках… показывает пользователю» (сегодня молча).

### D7. Тестовая стратегия (TDD)

- Service: два медленных mock-провайдера стартуют параллельно (стена < 2t); `cancel_all` отменяет in-flight и waiting; фазы через `on_phase` (последовательность `in_flight`→`waiting`→`in_flight` при ретрае); scope owner-ов (owner A не трогает owner B).
- Provider: `on_phase` не влияет на поведение без хука; хук вызывается в правильных точках (MockTransport 503→200).
- UI (offscreen Qt): state-матрица — старт бандла (все поля read-only+progress, save disabled, кнопки disabled, entity-кнопка = отмена); ранний результат (одно поле разблокировано, другие идут); завершение (все активны); отмена (состояния сброшены, результатов нет, окна об ошибке нет); ESC/click-outside-block во время генерации (синтетические события); X in-flight → подтверждение (QSpy/подмена QMessageBox), «Нет» → диалог жив; X waiting → закрытие молча + cancel; «Отмена» — тот же путь; save disabled в одиночной генерации; агрегация: 2 падения одной причиной → один текст, 2 разные → построчно; полная успешность → окон нет.
- Обновить существующие: `test_llm_service` (очередь → параллельно), `test_llm_viewmodel`, `test_e2e_llm`.
- Всё через `httpx.MockTransport`, без сети (правило проекта).

## Risks / Trade-offs

- [Неизвестный механизм «клик мимо закрывает»] → closeEvent-guard накрывает задокументированный путь; задача с тестом синтетического закрытия; если тест покажет особый платформный путь — перехватывается там.
- [Локальная LLM с `num_parallel=1` + 3–5 параллельных запросов] → сервер держит соединения в очереди, read-таймаут (120 c) на запрос может истечь при долгой очереди → ошибка 429/таймаутового класса с ретраями и видимым сообщением (новая фича ошибок, D6). Компромисс осознан: ограничивать параллельность семафором не будем (non-goal), при реальном болевом случае — отдельная настройка.
- [`QMessageBox` из `closeEvent`] → модальное окно внутри обработчика закрытия — штатная Qt-практика подтверждения; порядок: сначала `event.ignore()`, затем box, затем либо `accept` закрывания либо `cancel`.
- [Два диалога одного типа одновременно (вложенная карточка)] → owner по identity; field_id не используется как ключ реестра, только как label в сообщениях.
- [Отмена во время retry-backoff] → `CancelledError` из `asyncio.sleep` проходит насквозь, без ошибок и без повторной попытки — как и задумано (отмена ≠ ошибка).

## Migration Plan

Без миграций данных и конфигов; backwards-совместимо с сохранёнными world/field prompts и конфигом подключения. Роллербэк = откат коммита. В `docs/CHANGELOG.md` — запись о фиче (кнопка «Сгенерировать сущность», параллельная генерация, отмена, ошибки видимы).

## Open Questions

- Точный механизм «клик мимо окна закрывает диалог» (механизм не найден статически) — закрывается тестовой задачей D7; не влияет ни на spec, ни на план, ни на разбивку задач.
