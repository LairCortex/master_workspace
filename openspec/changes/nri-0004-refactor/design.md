## Context

См. proposal.md (Why) — мотивация не повторяется. Факты, определяющие подход:

- **Покрытие (базовая линия, 389 тестов, total 72%):** `app/main.py` — **0%** (551 stmt), `xlsx_import_dialog.py` — 0% (68), `game_launcher_dialog.py` — 57%, `mention_text_edit.py` — 56%, `main_window.py` — 70%, `search_service.py` — 61%, `xlsx_import_service.py` — 63%; домен и viewmodels — 90–100%.
- **`app/main.py` (891 строк)** кроме DI содержит: `init_db()` + `_migrate_nullable_end_dates()` (мigrции без alembic), `_wire_signals()` (~400 строк nested async-closure'ов с бизнес-логикой), `_get_entity_service()` (создаёт `EntityService` заново на каждый вызов), `_wire_ai_buttons()`.
- **В runtime-пути лежат ORM-модели, а не доменные dataclass'ы**: `EntityService`/`SearchService`/viewmodels работают с ORM-объектами (`Any`); dataclass'ы из `domain/entities/` не импортируются никем, кроме самих себя и `tests/domain/`. Доменный слой формален.
- **`EntityCardDialog` уже частично config-driven** (`_EXTRA_FIELDS`, `_RELATED_CONFIG`), но `_init_ui`/`populate`/`get_data` содержат жёсткие ветвления по типу.
- **CI** (`.github/workflows/build.yml`): jobs `test` (pytest, offscreen) → `build` (`needs: test`, 3 ОС) → `release`. `pytest-cov` уже в `[dev]`, coverage в CI не собирается.
- **Конвенции проекта (AGENTS.md):** без alembic — изменения схемы только inline в `init_db()` при старте; гейт качества — тесты; коммиты `<TASK-KEY>: imperative English`; ветка `main`.

## Goals / Non-Goals

**Goals:**
- Бизнес-логика сохранения/связей — в сервисном слое с полным покрытием; `main.py` = DI + тонкий wiring (~400 строк).
- Характеризационная сеть **до** переноса логики: текущее поведение зафиксировано тестами.
- Убрать 1:1-дубли (`search()` ×4 репозитория, dataclass ×4) и ветвления в `EntityCardDialog`.
- Профилактика: coverage-gate и ruff в CI, функциональный чек-лист в репозитории, ошибки не глотаются молча.
- Нулевое изменение наблюдаемого поведения (UI, БД-схема, `.nri`, LLM-конфиг, форматы промтов).

**Non-Goals:**
- НЕ вводим alembic — конвенция `init_db()` сохраняется (только перенос в модуль, §B).
- НЕ вводим E2E/UI-драйвер — компенсируем чек-листом (§CL).
- НЕ подводим доменные dataclass'ы к runtime-пути (типизация возвратов сервисов) — отдельная будущая перемена.
- НЕ вводим DI-фреймворк, форматтеры (ruff — только lint), НЕ меняем механизм signal-wiring (Qt-сигналы + `ensure_future` остаётся).
- НЕ «улучшаем» асинхронные тонкости при переносе (`session.refresh`, `MissingGreenlet`-защиты) — перенос 1:1, любые улучшения — отдельная перемена.

## Decisions

### D1 (E). Характеризация в две волны — порядок гарантирует «не потерять функциональность»

**Решение:**
- **Волна 1 (E1, до любых переносов):** тесты на *существующий* код в зонах дыр: `search_service` (61%), `xlsx_import_service` (63%), `xlsx_import_dialog` (0%), `mention_text_edit` (56%), `game_launcher_dialog` (57%), `main_window` (70%). API не меняется — это чистые характеризационные тесты (поведение фиксируется чтением кода + чек-листом).
- **Волна 2 (в составе A):** каждый перенос из `main.py` — отдельный коммит из 3 частей: (1) создать сервисный метод, содержащий **перенесённую 1:1** логику текущей closure; (2) добавить тесты этого метода (поведение описано по текущей closure + чек-листу); (3) wiring в `main.py` заменяет closure на вызов метода. Полный прогон (389+) и чек-лист — в каждом коммите.

**Почему:** логику с 0% покрытием нельзя переносить «как есть» — регресс M2M-синхронизации проявится только при ручном тесте. Волна 1 закрывает то, что закрыто без нового API; волна 2 не даёт покрытию «отставать» от переноса.
**Альтернативы:** (а) перенос без волны 1 — отвергнуто (нет сети на самый рискованный код); (б) сначала большой рефакторинг, потом тесты «на всё» — отвергнуто (тот же риск, но без посильной откатности между шагами).

### D2 (A). Целевое API сервисов

Текущие closure'ы в `_wire_signals()` маппируются на сервисы так (семантика 1:1, без «улучшений»):

| Closure в `main.py` | Целевое место |
|---|---|
| `_process_entity_items(items, repo_cls, collection)` (создать новое / привязать существующее / отвязать лишнее) + 4 вызова в `on_saved`/`on_event_updated` | `EventService.apply_event_relations(event, org_items, char_items, item_items, loc_items)` |
| `on_saved` (create event + description + relations + commit) | `EventService.create_event_with_relations(name, start_date, end_date, characteristics, backstory, relations) -> event` |
| `on_event_updated` (update + description + relations + commit) | `EventService.update_event_with_relations(event_id, name, start_date, end_date, characteristics, backstory, relations)` |
| sync M2M по одному атрибуту из `on_entity_saved` (только привязать/отвязать существующих) | `EntityService.sync_related(entity, attr_name, desired_ids)` |
| `on_entity_saved` (update fields + description + sync + commit) | `EntityService.update_entity_with_relations(entity_id, field_data, characteristics, backstory, related_changes)` |
| `on_add_entity` (standalone create) | `EntityService.create_entity(...)` — уже существует; main.py остаётся тонким |
| `on_create_related` (связанная сущность вложенным диалогом) | `EntityService.create_entity(...)` + `session.flush()` — остаётся там, где живёт диалог (внимание к parent-диалогу) |
| `_load_available_into_dialog` (4× `get_all` для табов) | метод `Application._load_available_into_dialog` поверх единого каталога сервисов (UI-обеспокоенность, сервис не нужен) |
| `_get_entity_service` (новый `EntityService` на вызов) | `self._entity_services: dict[str, EntityService]` — **один раз** в `Application.start()` |

**Зависимости DI:** `EventService` получает 4 `EntityService` (character/organization/item/location) через конструктор — прецедент уже есть в `XlsxImportService`. `EntityService.sync_related` использует сессию через `repo._session` (репозиторий уже держит сессию) — `refresh`/append/remove на ORM-коллекции сохраняются 1:1.
**Почему не новый `RelationshipsService`:** всего 2 метода с разной семантикой (create-or-link vs link-only); отдельный класс увеличил бы DI-граф без возврата.
**Итог:** `main.py` теряет ~450 строк; wiring становится декларативным (сигнал → `ensure_future(сервисный_вызов)` + обновление панелей).

### D3 (B). Перенос миграций в модуль

`app/infrastructure/db/migrations.py`: `async def init_db(engine)` + `_migrate_nullable_end_dates()` + `_MIGRATIONS`. `main.py` — только `from ... import init_db`.
**Важный бонус:** `init_db` имеет 0% покрытия — добавляем тесты: (1) свежая БД → schema up-to-date; (2) **синтетическая легаси-схема** `end_date NOT NULL` → после `init_db` колонка nullable (фиксирует hotfix 0.9.1, самый опасный код в миграциях — rebuild таблиц с `PRAGMA foreign_keys=OFF`); (3) идемпотентность (второй запуск ничего не ломает).
**Альтернатива:** alembic — отвергнуто (конвенция проекта, риск для существующих `.db`).

### D4 (C). `search()` базовым в `BaseRepository`

`BaseRepository.search(query)` — outerjoin на `DescriptionModel`, `func.lower().contains` по name/characteristics/backstory (текущая копия 1:1 во всех 4 репозиториях). Пер-тип классы остаются (DI по имени, привязка модели), теряя только `search()`. Тесты: текущие 4 параметризованных набора → один параметризованный тест на 4 модели (покрытие остаётся 100%).
**Альтернатива:** generic-репозиторий с фабтикой — отвергнуто (DI по явным именам читабельнее; класс по 3–4 строки достаточно дешев).

### D5 (D). Общая основа domain-dataclass'ов

`BaseEntity` (dataclass): `name, description, start_date, end_date=None, id=None, music_url=None, ratings` + общий `__post_init__` (`_validate_base` переезжает из `event.py` в `base.py`; совместимые алиасы/обновление импортов в том же коммите). Дочерние классы — только специфика: `Character(+personality, +image, +tasks)`, `Organization(+image, +tasks)`, `Location(+image, +tasks)`, `Item(+)`. M2M-списки остаются в дочерних (у всех разные наборы).
**Факт, ограничивающий ценность:** dataclass'ы вне runtime-пути (см. Context) — выгода §D косметическая (согласованность задокументированного доменного слоя), поэтому пункт ставится **после** F и выполняется последним из «кодовых». Подключение dataclass'ов к runtime (типизированные возвраты сервисов) — Open Question на будущее.

### D6 (F). `EntityCardDialog` — завершение config-драйвинга

Расширяем существующий `_EXTRA_FIELDS` до полной таблицы `_FIELD_SPECS[type] -> list[FieldSpec(name, label, kind)]`, где `kind` ∈ {`mention` (QTextEdit+AI), `text`, `tasks`…}. `_init_ui` строит форму итерацией по спецификации вместо ветвлений; `populate`/`get_data` — те же итерации. `_RELATED_CONFIG` уже data-driven — не трогаем.
**Жёсткое ограничение совместимости:** публичные имена атрибутов виджета, на которые ссылаются тесты и wiring, сохраняются без изменения (`characteristics_input`, `backstory_input`, `personality_input`, `tasks_input`, музыка-блок, панель изображения). Риск: средний — митигация: существующие тесты диалога (в составе 389) + пункт чек-листа №5 + посильный коммит (строка формы по строке форм можно не разбивать — диалог пересиливается целиком за один коммит с тестами).
**Порядок:** F выполняется **после** A — wiring диалога к тому моменту уже не тянет бизнес-логику, и правки диалога изолированы.

### D7 (G). Гигиена

- Удалить untracked `local.model.lm+2-key.pem`, `local.model.lm+2.pem` — остатки локальной LLM, удалённой в 0.13.0. Не участвуют в сборке (spec-файл их не бандлит). Если нужны пользователю — перенос за пределы репозитория **до** коммита (Open Question).
- 6× `except Exception: pass` → `logging` (модульные логгеры, `warning` для «не удалось загрузить настройки», `error` + `exc_info` для поиска по mention/LLM). Поведение при ошибке не меняется (все эти места сейчас именно «тихо продолжать»), меняется наблюдаемость.

### D8 (H). Тулинг-страховка

- **ruff** (dev-dep + CI-job `lint`): `target-version = py311`, `line-length = 120`, select `E` + `F` (только ошибки, без opinionated-правил; форматтер не вводим). Стратегия легаси: в первом коммите §H замерить количество нарушений; если `E501`/прочие > 30 — принимаем baseline-исключения по списку (с пометкой «сужаем постепенно»), если ≤ 30 — чиним всё. CI: новый job параллельно `test`, `build.needs: [test, lint]`.
- **Coverage-gate:** шаг `test` в CI → `python -m pytest tests/ -v --cov=app --cov-report=term --cov-fail-under=<X>`. `X` фиксируется **после волы 1 (E1)** по фактическому измерению (сейчас 72%, ожидается ~78–80%) — гейт предотвращает падение, не принуждает к росту. Альтернатива (жёсткий фикс 75% до замеров) — отвергнута (риск падения CI в середине implement).

### D9 (CL). Функциональный чек-лист

`docs/functional-checklist.md` создается по итогам этого аудита (контент — раздел «Функциональный чек-лист» ниже; файл материализуется первым task implementation). Используется: после **каждого** коммита implementation прогоняются затронутые группы; после финала change — полный прогон всех групп. Чек-лист намеренно живёт в `docs/` (а не только в OpenSpec) — он регрессионная сеть на будущее.

## Risks / Trade-offs

- [Перенос логики из `main.py` меняет незаметно поведение] → характеризация в две волны (D1); 389+ тестов и чек-лист в каждом коммите; мелкие коммиты → `git revert` одного коммита откатывает один пункт.
- [`EntityCardDialog` после перестройки визуально/функционально отличается] → имена атрибутов виджетов не меняются (D6); существующие тесты диалога + чек-лист №5.
- [Coverage-gate падает CI в середине implement] → порог ставится после волы 1 по замеру (D8), а не заранее.
- [ruff генерирует шум по легаси] → замер нарушений до включения; baseline-исключения при >30 (D8).
- [Тест миграций на «старой» схеме не отражает реальное легаси] → синтетическая схема из горячего фикса 0.9.1 (`end_date NOT NULL`) — ближайшая к реальной; полный набор исторических схем не воспроизводим.
- [Асинхронные тонкости (`session.refresh`, порядок commit/rollback) ломаются при переносе] → перенос 1:1, без «улучшений» (Non-Goals); изменения поведения — отдельная перемена с новыми тестами.
- [Trade-off D5:] dataclass'ы остаются вне runtime-пути — выгода §D косметическая; осознанно принимаем (подключение к runtime — будущая перемена).

## Migration Plan

Никаких данных/схем не мигрируется; миграция кодовая, посильная:

1. **CL** — чек-лист (docs, нет кода).
2. **E1** — тесты дыр покрытия (без изменения поведения).
3. **A** — 3–4 коммита: `EventService` (2 метода + тесты), `EntityService` (2 метода + тесты), каталог сервисов + упрощение wiring, очистка `main.py`.
4. **B** — модуль миграций + 3 теста `init_db`.
5. **C** — базовый `search()` (1 коммит, тесты параметризуются).
6. **G** — `.pem` + логирование (1 коммит).
7. **F** — config-драйвинг диалога (1 коммит + тесты).
8. **D** — `BaseEntity` (1 коммит, тесты домена обновляются в том же коммите).
9. **H** — ruff-job + coverage-gate (1 коммит; порог по замеру после E1).

**Откат:** каждый пункт — независимый коммит `NRI-0004: ...`; откат = `git revert <sha>`. Зависимости порядка: E1 → A; A → F (wiring должен уже быть тонким). Остальные — независимы. Внешний гейт — CI (`test`+`lint`).

- Расширить ли ruff за E+F (isort `I`, `UP`, `SIM`) — решается в коммите H по объёму нарушений.
- Будущая перемена (не в этом change): подключить доменные dataclass'ы к runtime-пути (типизированные возвраты сервисов вместо `Any`).
