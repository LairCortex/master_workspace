## ADDED Requirements

### Requirement: Картинки экземпляра ссылаются на images

Значение поля-картинки заполненного листа SHALL ссылаться на запись `images` так же, как поле шаблона (идентификатор записи, без пути). Пустое значение (ключ с очищенной картинкой) SHALL не ссылаться. Выбор файла в Fill SHALL проходить через тот же конвейер, что выбор в карточке сущности и в Design.

#### Scenario: Дедуп листа и персонажа

- **WHEN** то же изображение уже привязано к персонажу и его выбирают в Fill
- **THEN** второй файл на диске не создаётся, обе ссылки указывают на одну запись `images`

## MODIFIED Requirements

### Requirement: Таблица метаданных images

База игры SHALL содержать таблицу `images` с полями: sha256 (уникальный), расширение, фактические ширина/высота, размер файла в байтах, время создания. Сущности организации, персонажа и локации, поля-картинки шаблонов чар-листов и значения-картинки заполненных листов SHALL ссылаться на изображение ссылкой на запись `images` (с обнулением ссылки при удалении сущности, поля, шаблона, значения листа или экземпляра), а не хранить пиксели. Наследственная колонка base64 после миграции SHALL хранить только NULL и не использоваться.

#### Scenario: Запись метаданных при сохранении

- **WHEN** сохранено новое изображение
- **THEN** в `images` появляется одна строка с sha256, определённым расширением, фактическими размерами и размером файла; сущность, поле шаблона или значение листа ссылается на эту строку

#### Scenario: Общее изображение у двух сущностей

- **WHEN** две сущности привязаны к одному файлу изображения (одинаковый sha256)
- **THEN** в `images` одна строка, обе сущности ссылаются на неё; удаление одной из сущностей не удаляет файл

#### Scenario: Лист и персонаж делят файл

- **WHEN** значение-картинка экземпляра и персонаж ссылаются на одну запись `images` и персонажа удаляют
- **THEN** файл на диске сохраняется, Fill по-прежнему показывает изображение

#### Scenario: Очистка наследственной колонки

- **WHEN** legacy-игра смигрирована
- **THEN** базовые колонки base64 содержат NULL, изображения доступны через `images`

### Requirement: Единый конвейер сохранения изображений

Сохранение изображений из любого источника (выбор файла в карточке сущности, поле «image» xlsx-импорта, выбор файла в поле-картинке шаблона чар-листа, выбор файла в Fill) SHALL проходить через единый конвейер: проверка читаемости → вычисление sha256 → при существующей записи с этим sha256 файловая запись не повторяется → иначе атомарная запись оригинала и preview (частичные файлы по итоговому имени не допускаются) → запись в `images`.

#### Scenario: Нечитаемый файл из диалога

- **WHEN** пользователь выбирает файл, который не может быть декодирован как изображение
- **THEN** пользователю показывается сообщение об ошибке, изображение к сущности или полю не привязывается, приложение работает

#### Scenario: Нечитаемый файл в xlsx-импорте

- **WHEN** в xlsx-файле поле изображения указывает на нечитаемый файл
- **THEN** импорт завершается, сущность создаётся без изображения, в отчёте импорта есть предупреждение по этой строке

#### Scenario: Нечитаемый файл в чар-листе

- **WHEN** в свойствах поля-картинки шаблона или в Fill выбран нечитаемый файл
- **THEN** поле остаётся без изображения, показывается ошибка

#### Scenario: Повторное сохранение того же изображения

- **WHEN** сохраняется изображение, уже существующее в хранилище (sha256 совпадает, файлы на месте)
- **THEN** запись в хранилище не дублируется, сущность, поле шаблона или значение листа получает ссылку на существующую запись

#### Scenario: Атомарность записи

- **WHEN** запись новых файлов прерывается (сбой, ошибка диска)
- **THEN** по финальным именам файлов отсутствуют (частичные файлы не допускаются), приложение остаётся в согласованном состоянии после startup-сканирования

### Requirement: Порядок операций при замене, снятии и удалении

При замене изображения, снятии изображения («Убрать» / очистить поле шаблона / очистить картинку в Fill) и удалении сущности, шаблона чар-листа или заполненного листа SHALL сначала коммититься изменения ссылок в базе, и только затем выполняться удаление файлов (best-effort). Физическое удаление файла-изображения допускается только если на него больше не ссылается ни одна сущность, ни одно поле шаблона и ни одно значение экземпляра. Ошибка физического удаления SHALL не отменять и не отменяться: пользовательская операция фиксируется, ошибка фиксируется в логе.

#### Scenario: Замена изображения

- **WHEN** у сущности заменено изображение и сохранено
- **THEN** сущность ссылается на новое изображение; файл старого изображения удалён с диска, если не используется другой сущностью, полем шаблона или значением листа

#### Scenario: Замена изображения общим изображением

- **WHEN** изображение сущности заменено на другое, при этом старое изображение используется ещё одной сущностью
- **THEN** файл старого изображения на диске сохраняется

#### Scenario: Снятие изображения

- **WHEN** пользователь снимает изображение с сущности
- **THEN** после сохранения ссылки на изображение у сущности нет; файл удалён, если не используется другими сущностями, полями шаблонов или значениями листов

#### Scenario: Очистка картинки на листе

- **WHEN** пользователь очищает картинку поля шаблона и сохраняет шаблон, и на файл больше нет ссылок
- **THEN** файл удалён с диска

#### Scenario: Очистка картинки в Fill

- **WHEN** пользователь очищает картинку в Fill, сохраняет лист, и на файл больше нет ссылок (включая шаблон и сущности)
- **THEN** файл удалён с диска

#### Scenario: Удаление шаблона с картинкой

- **WHEN** удалён шаблон, у которого поле-картинка было единственной ссылкой на файл
- **THEN** файл удалён с диска

#### Scenario: Удаление экземпляра с картинкой

- **WHEN** удалён заполненный лист, у которого значение-картинка было единственной ссылкой на файл
- **THEN** файл удалён с диска

#### Scenario: Сбой удаления файла

- **WHEN** после фиксации изменения ссылок операции удаления файла не удалась
- **THEN** изменения сущности, шаблона или листа сохранены, пользователю операция засчитана, ошибка удаления записана в лог

### Requirement: Startup-сканирование и инвариант целостности

При открытии игры SHALL выполняться сканирование, после которого гарантируется: у каждой записи `images` существует файл оригинала; preview существует или может быть детерминированно пересоздан; каждый файл в хранилище принадлежит ровно одной записи `images`. Правила сканирования: файл без записи — удалить; запись без оригинала — удалить запись и обнулить ссылающиеся ссылки сущностей, полей шаблонов и значений экземпляров; запись с оригиналом, но без preview — пересоздать preview; незаиспользуемая (без ссылок сущностей, полей шаблонов чар-листов и значений заполненных листов) запись — удалить запись и файлы.

#### Scenario: Удаление сиротского файла

- **WHEN** в `images/` найдётся файл, для которого нет записи в `images` (остаток прерванной операции)
- **THEN** после открытия игры файл удалён

#### Scenario: Записи без оригинала

- **WHEN** в `images` есть запись, а файл оригинала отсутствует
- **THEN** после открытия игры запись удалена, ссылающиеся сущности, поля шаблонов и значения листов очищены, изображения этих мест отображаются как отсутствующие

#### Scenario: Картинка листа держит запись

- **WHEN** на запись `images` ссылается только поле шаблона чар-листа, сущностей-ссылок нет
- **THEN** после открытия игры запись и файлы сохраняются

#### Scenario: Картинка экземпляра держит запись

- **WHEN** на запись `images` ссылается только значение заполненного листа, сущностей и полей шаблона на неё нет
- **THEN** после открытия игры запись и файлы сохраняются

#### Scenario: Повторный запуск

- **WHEN** игра открывается повторно после успешного сканирования
- **THEN** состояние хранилища не изменяется (сканирование идемпотентно)
