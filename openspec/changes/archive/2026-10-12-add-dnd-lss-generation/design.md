# Design: add-dnd-lss-generation

## Context

См. proposal.md — Why. Состояние, формирующее подход:

- Фазы 1–2 дали модулю `app/dd/` все приёмные двери: `DatasetValidatorService` (схемы `dataset-*.json` + полные кросс-проверки LSS), `CharacterValidatorService` (конверт + `character.json`), импортёры датасетов/персонажей/гримуаров, глобальные хранилища датасетов и гримуаров, сервис связей с игрой.
- LLM-канал один: `BaseLlmProvider.generate(system_prompt, user_prompt, max_tokens=None, on_phase, with_thinking)` с русскими ошибками, повторами и авто-бюджетом вывода; AI-гейт («готово + описание мира») живёт в `LlmViewModel`.
- Позы UI зафиксированы продуктом: листы —sheets через `open_sheet`; закрытие с подтверждением — modeless-подтверждение PR-010; волна генерации сущности — образец отмены/блокировок; released-остров не отвечает (`_root_alive`-норма).
- Состав корня — единственное место сборки; модуль получает зависимости протоколом, ядро о D&D не знает (охранки слоёв).

## Goals / Non-Goals

**Goals:**

- Один механизм круга, три канала поверх него; наружу — только документы, прошедшие существующие валидаторы.
- Детерминированное ядро (промптостроение, склейка конвертов, сборщик «карточка → документ») — Qt-free и покрыто offscreen-тестами; Qt — только листы-задачи.
- Нулевых изменений ядра, схем БД и профилей сборки.

**Non-Goals:**

- Расчёт механики D&D (бонусы/навыки/слоты) — остаётся листу/построителю LSS.
- Генерация монстров/встреч; правка принятых файлов постфактум; слияние в чужие гримуары/датасеты; фоновое исполнение; отправка во внешний LSS.

## Decisions

### Д1. Круг живёт в модуле, канал описан протоколом

`app/dd/application/generation_loop.py`: Qt-free раннер `run_rounds(channel, context, max_auto=2, feedback=…)`. Канал — протокол `GenerationChannel`: `build_prompt(ctx) -> (system, user)`, `parse(answer) -> str` (извлечение JSON-документа), `validate(text, ctx) -> ValidationReport`, артефакт круга — текст документа. Обратная связь круга: `user = «предыдущий ответ + список ошибок (код/путь/сообщение)»`, только `severity=ERROR`. Ручной «Ещё круг» — повторный вызов раннера поверх сохранённого последнего ответа.
*Почему так:* круг одинаков для трёх каналов (проверено grill'ем); альтернатива «цикл внутри каждого листа» дублирует лимиты и формат обратной связи, а «механизм в ядре» ломает норму «ядро не знает D&D».

### Д2. Три реализации канала

- `DatasetSectionChannel`: модель пишет массив записей одной секции; приложение оборачивает в конверт `dataset-<тип>.json` (версия формата, id датасета, лицензия из диалога принятия — до подстановки конверт собирается «холостым», лицензия — единственное поле принятия). Валидация — `DatasetValidatorService.validate(content, connected, spell_slugs, source=HOMEBREW)`.
- `SpellbookChannel`: модель пишет массив содержательных частей заклинаний; приложение собирает конверты Foundry Item (обязательные служебные поля, `system`-блок). Гейт — структурная часть `GrimoireImportService` (ошибки) + семантические проверки и словарь SRD-слагов (предупреждения).
- `CharacterChannel`: вход — концепция/пре-выборы или текущий документ (дозаполнение); модель пишет только содержательную часть `data`; приложение достраивает скелет по `character.json`. Склейка «скелет+содержимое» детерминирована: числовые механические ключи из ответа модели отбрасываются до валидации (гарантия требования «числа — LSS»).
*Альтернатива* (модель пишет файл целиком) отвергнута: конверты и скелет — детерминированная работа, её отдача модели множит схемные провалы круга.

### Д3. Промтостроение из ресурсов, golden-пин

`app/dd/resources/generation/`: фиксированные few-shot-наборы на секцию/канал (SRD-извлечения) + скелеты системных промтов (RU). `PromptComposer` собирает: скелет + описание мира + идея мастера + слой slug-словаря (источник + slug + снимок имени) для персонажа/заклинаний. Языковая директива — содержимое по-русски, протокол латиницей. Golden-тесты сверяют собранные промты на фиксированных входах; подключение датасетов меняет только слой словаря.
*Альтернатива* (редактируемые промты в `game_settings`) отложена grill-решением: ключ появится вместе с требованием крутить формулировки.

### Д4. Сборщик «карточка → документ» — одна дверь экспорта и дозаполнения

`app/dd/application/character_document_builder.py`: из данных карточки (сущность + `DdCharacterExt` + привязки заклинаний) собирает `CharacterDocument` v2; тексты карточки → узлы форматированного редактора формата LSS (построитель блоков общий с каналом персонажа); привязки → слаги подключённых источников (отключённый источник — привязка без ссылки, снимок сохраняется); пустые поля не пишутся; ключ `data` — JSON-строка. Экспорт («Экспорт для LSS…» в D&D-табе карточки, доступна без AI) и дозаполнение (Д6) вызывают только его.
*Почему не патч сырого файла:* карточка — правда продукта после любой правки; сырой файл застаревает, экспорт из него врал бы мастеру.

### Д5. Персонаж: создание и дозаполнение идут через существующий импорт

- С нуля: `CharacterChannel` → собранный документ → `CharacterValidatorService` → `CharacterImportService` (сырой файл хранится, карточка раскладывается).
- Дозаполнение: сборщик (Д4) строит текущий документ → модель дозаполняет пустые содержательные поля → склейка (заполненное мастером защищено на уровне склейки: непустые значения не перезаписываются) → валидатор → импорт заменяет сырой файл и обновляет карточку.
*Альтернатива* (прямая правка карточки минуя импорт) отвергнута: сырой файл рассинхронизируется с карточкой — норма «сырой файл хранится всегда» перестаёт иметь смысл.

### Д6. Принятие — через существующие импортные двери хранилищ

Принятый датасет-файл записывается в глобальное хранилище как homebrew через существующий импорт датасетов (источник `HOMEBREW`) и подключается `DatasetConnectionsService`; гримуар — через `GrimoireImportService`/`GrimoireStorage` новым файлом. Никаких вторых дверей записи в хранилища.

### Д7. UI: листы-задачи поверх Qt-free ядра

Три листа (widget-sheets по позе модуля): задача датасетов (чекбоксы секций, число 1–10, идея, на секцию — статус круга, предпросмотр записей, отчёт, лицензия `ThemeComboBox`, «Принять/Перегенерировать/Отменить»); лист заклинаний (то же без лицензий); лист персонажа (концепция + пре-выборы уровень/вид/класс; дозаполнение — кнопкой в D&D-табе, открывает тот же лист в режиме дозаполнения). Точки входа: лист «Датасеты D&D…» → «Сгенерировать ИИ»; лист гримуаров → «Сгенерировать ИИ»; меню «D&D» → «Сгенерировать персонажа…», D&D-таб карточки → «Дозаполнить ИИ». Исполнение — задачи qasync на общем цикле; закрытие листа с in-flight — modeless-подтверждение, отмена не ошибка (поза волны сущности); released-лист не отвечает.

### Д8. Провайдер и режим вызова

Каждая секция/документ — одиночный `generate(..., with_thinking=True, max_tokens=None)`; параллель секций в задаче не батчится в один запрос, но и не сериализуется против воли (как синглы PR-024). Фазы повторов показываются штатным индикатором AI-кнопок.

## Risks / Trade-offs

- [Модель оборачивает JSON в fence/комментарии] → `parse` терпимо извлекает JSON-объект; не извлеклось — ошибка «не JSON» входит в обратную связь круга.
- [Огромный `character.json` не влезает в бюджет] → модель пишет только содержательную часть; бюджет и так авто-пробуется (`max_tokens=None`).
- [Дозаполнение затрёт написанное] → защита на уровне склейки (Д5) + offscreen-тест «предыстория мастера не изменилась»; спецификация пинит сценарий.
- [Дрейф контрактов LSS] → схемы уже запинены фазами 1–2; каналы используют те же бандлы, changelog LSS читается при обновлениях (норма roadmap'а).
- [Нелицензионный контент] → выбор только из трёх разрешённых лицензий, ответственность мастера; предупреждение валидатора остаётся видно.
- [Долгие задачи под закрытым окном] → отмена с подтверждением; фоновых задач нет по grill-решению.

## Migration Plan

Аддитивно: новых таблиц и ключей `game_settings` нет, файловые форматы — только чтение/запись уже специмированных хранилищ. Раскатка — обычный релиз; откат — выключить модуль (данные генерации живут как обычные хоумбрю-файлы и персонажи).

## Open Questions

- Дефолтное число заклинаний в генерации (5 как у секций или иное) — влияет только на предзаполнение поля, не на контракт.
