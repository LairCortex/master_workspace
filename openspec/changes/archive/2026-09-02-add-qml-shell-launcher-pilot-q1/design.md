# Design: QML-каркас и пилот лаунчера (Q1)

## Context

Дизайн зафиксирован grill-сессией 2026-09-02 (см. `docs/design-system-roadmap.md`, абзац Q1). Текущее состояние: presentation — только QtWidgets; токены компилируются `ThemeRuntime` в QSS (мастер) и CSS (web-игрок) в памяти, live-retheme через `add_listener`; лаунчер — `GameLauncherDialog` (188 строк) без view model, напрямую зовёт функции каталога `app/infrastructure/db/game_manager.py` (`list_games`, `create_game`, `delete_game`, `import_game`, `read_archive_meta`); контракт для приложения — `game_selected(path)` + `selected_path`, используется дважды: стартовый поток в `run()` до главного окна и `_on_switch_game()` поверх окна. VM приложения — уже `QObject` c property/сигналами, совместимы с QML. PySide6 в venv 6.10.2; планка покрытия строк — 100%; CI — три ОС с `QT_QPA_PLATFORM=offscreen`.

## Goals / Non-Goals

**Goals:**
- Работающий второй UI-стек: движок, мост токенов, контракт биндингов, тесты, сборка — на одном реальном экране.
- Лаунчер целиком на QML без изменения пользовательского потока и внешнего контракта.
- Каркас пригоден для роста (Q2/Q3 добавляют острова без переделки каркаса).

**Non-Goals (рамка куска, зафиксирована в спеках):**
- Перенос любых иных экранов, нативных меню/попапов, mention-edit, канваса.
- Библиотека общих QML-компонентов, qmldir-модули, зум/анимации/тултипы в QML —Q2+.
- Модификация `ThemeRuntime`/компилятора QSS/CSS сверх отдачи производных палитре.

## Decisions

1. **Острова `QQuickWidget` внутри нативных окон, а не QML-вершина.** QtWidgets остаётся хозяином: меню, диалоги, qasync-цикл, канвас не трогаются; QML растет кусками. Отказ: `QQmlApplicationEngine` + QML `ApplicationWindow` (вторая вершина приложения сразу, конфликт с нативными меню), `createWindowContainer` (проблемы фокуса и попапов).

2. **Один общий `QQmlEngine`, поднимаемый в `Application.start()`** (до первого диалога; стартовый лаунчер показывается в `run()` позже). Синглтон-владелец — само приложение; острова получают движок DI-подобно, как сейчас получают `theme`. Отказ: движок на островок (двойной расход, разные контексты палитры). На Qt 6 импорт-путь задаётся программно (`addImportPath()` на движке до загрузки qml) — qrc не используется, т.к. PySide6 6.10 лишён удобной сборки qrc «из коробки», а файловая поставка уже применена для web-ресурсов table_host.

3. **`QmlPalette` — тонкий QObject-мост**: словарь `tokens` (Property + notify `changed`), ключи = имена `tokens.json` точь-в-точь, производные (`accent_rgba`, hover/pressed, mention) добавляются Python-компилятором в тот же словарь. Кладётся в `contextProperties()` движка один раз. Live-retheme: подписка `ThemeRuntime.add_listener` → пересборка словаря → `changed.emit()` → биндинги пересчитываются; QSS/CSS-ветки не затрагиваются. Отказ: генерация QML-текста палитры (третий компилятор), по property на токен (шум), вычисление производных в JS (двигатель цветов разъехался бы с QSS).
   Валидность токенов: при невалидном наборе `tokens` пуст → qml-биндинги получают `undefined` → контролы остаются на базовом виде Controls (аналог «палитра ОС» для QSS); тумблер no-op как сейчас.

4. **Стиль Basic программно** (`QQuickStyle.setStyle("Basic")` до загрузки любого qml). Отказ: `qtquickcontrols2.conf` (лишний файл в бандле), Material/Universal (рамка W2 «не копировать чужой стиль»), Fusion (чужая геометрия). Делегаты/стили лаунчера — inline в qml с чтением палитры; общие компоненты — Q2.

5. **LauncherViewModel поверх функций каталога** (`app/presentation/viewmodels/launcher_viewmodel.py`): Property `games` (список ролей `{name, modifiedLabel, path}`), `selectedIndex`/`selectedPath`, сигналы `gamesChanged`, `openRequested(path)`, `createRequested(name)`, `deleteRequested(index)`, `importRequested(fileName)`. Синхронные мутации каталога (`refresh`, `create(name) -> path`, `remove(path)`, `import_(path)`, `archive_meta(path)`) — методы VM поверх функций `game_manager` (исключения каталога прокидываются наружу как сейчас); сигналы `*Requested` эмитит qml и нужны, чтобы всплывашками управлял не QML. Контроллер — QDialog-обёртка: слушает `*Requested`, поднимает нативные `QInputDialog`/`QMessageBox`/`QFileDialog`, вызывает метод VM, при успехе закрывает диалог/издаёт `game_selected` (как сейчас), при ошибке показывает предупреждение. Каталог-сервис в контекст QML не отдаётся — только VM. Отказ: прослойка-контекст без VM (контракт биндингов требует VM-стиль; заодно лаунчер догоняет остальные экраны), вызов каталога прямо из QML (сервис в контексте = несъёмная связка), async-VM (каталог — синхронные файловые операции, корутин нет).

6. **Внешний контракт не меняется**: `GameLauncherDialog` остаётся `QDialog`-обёрткой с `game_selected(path)` и `selected_path` — стартовый `run()` и `_on_switch_game()` правятся только в части «нет QSS-подключения содержимого». Обёртка поднимает `QQuickWidget`, грузит `LauncherRoot.qml` по URL, кладёт VM в `rootContext` объекта (context-свойства объекта острова: `vm`, `palette` — движок даёт только движковые; палитра дублируется в context объекта из движка). Отказ: новый стартовый API (цепляет main-флоу и тесты сверх необходимого).

7. **Тесты**: `QT_QUICK_BACKEND=software` в `tests/conftest.py` (до импорта Qt, рядом с текущим комментарием про порядок окружения); существующие сценарии `tests/ui/` и темы сохраняются, адреса кнопок — `widget.findChild(QQuickItem, "openButton")` (QML-объекты — QObject-дети острова; `objectName` каждого интерактивного контрола — контракт qml-кода); пиксель — `grab()` + hex токена (обе темы), golden нет; новый тест бандла `.spec` — по образцу `test_spec_theme_bundle.py`; отдельный тест «QML-островок поверх реальной VM лаунчера биндится без правок VM» — proof контракта. Fallback на ОС без software-рендера: проверки `status == Ready` компонента и значений property биндингов без `grab()`.
   Минимум PySide6 поднимается до `>=6.8` в `pyproject.toml`.

8. **Покрытие 100%**: весь новый Python-код (палитра, VM, обёртка, wiring, константы) под тестами; qml-файлы — данные вне python-покрытия; coverage считает только `.py`, поэтому `source = ["app"]` к qml неприменим и менять его не нужно.

## Risks / Trade-offs

- **[Ставка на вход приложения]** Лаунчер — первое, что видит пользователь; регресс QML-рендера = нерабочий старт → митигация: приёмка на трёх ОС + прогнанный бандл до merge;widgets-версия остаётся в истории, откат — revert коммита куска.
- **[Headless-рендер Quick на Linux CI]** software-бэкенд может отказаться `grab()` в контейнере → митигация: заранее принятый запасной план (биндинг/палитра-проверки без рендера); пиксельная приёмка обязхательна минимум на двух ОС.
- **[Рост бандла]** QtQuick-плагины заметно утяжеляют сборку → принимается: Q2/Q3 платят тот же один раз; файло-тест не даст разъехаться списку.
- **[Двойной учёт темизации]** QSS-ветка и QML-палитра живут рядом; риск разъезда поведения оф-скина → митигация: один `ThemeRuntime` источник, общий тест валидности, инвариант зачистки расширен на qml.
- **[`objectName`-адресация хрупкая]** переименование контрола ломает тесты молча → митигация: контракт objectName в спеке, тестовый smoke «все интерактивные контролы острова найдены».

## Migration Plan

Кусок вливается целиком: каркас + лаунчер атомарно (каркас без потребителя мёртвый, лаунчер без каркаса невозможен). Бэкап-пути нет по дизайну (вторая копия запрещена); откат = revert merge-коммита. Пользовательских данных/миграций не затрагивается.

## Open Questions

- Точная форма записи `games` в палитрную роль (list[dict] vs QObject-модель для `ListView.model`) — решается на имплементации: Quick6 принимает `list` через `required property var`, QObject-модель заводится только если проявится деградация на больших каталогах. Не влияет на спеки/задачи.
