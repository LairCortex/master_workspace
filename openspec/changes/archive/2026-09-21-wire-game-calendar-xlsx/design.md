# Design: wire-game-calendar-xlsx

## Context

Дерево решений зафиксировано grill-сессией 2026-09-21. Мотивация — в proposal.md; требования — в дельте specs/xlsx-import. Текущее состояние: дата импорта — `parse_cell_date` (`xlsx_schema.py`) возвращает `tuple[date, bool]` по фиксированному словарю (`_BC_TEXT_RE`, `_BC_MONTHS`, знаковое ISO, голое ISO, нативная ячейка); строка черновика тут же превращается в координату активного календаря со сдвигом невалидных (`shift_invalid`) и строкой переноса в отчёт (`_to_coord`, C3a). Подпись даты приложения печатает игровой формат (`format_game_date`: `dd ИмяМесяца гггг[ г. до н.э.]`, вставной день — `Имя гггг`). Шаблон — байтовая копия `resources/import_template.xlsx`; его эталон клетка-в-клетку закреплен генератором `build_template_workbook()`/`SAMPLE_ROWS` в `tests/application/test_xlsx_import_template.py`.

Ключевые ограничения: домен (`game_calendar`) не локализует и тексты парсинга на себя не берёт — словарь имён и грамматики живут у импорта; схема БД не меняется; имена месяцев календаря уникальны внутри измерения (`validate`), но месяцы и вставные дни между собой не сверяются — их различает форма записи; эра настраиваемой не является (флаг при дате); комментарии и докстринги — на английском; гейт 100%-покрытия.

## Goals / Non-Goals

**Goals:**
- Один парсер с ветвлением по активному календарю; стандартная ветка не приобретает ни одной новой формы.
- Координатная валюта результата парсера (включая вставной день) — импорт перестаёт знать григорианский центр дат.
- Шаблон генерируется под активный календарь и гарантированно импортируется в свою игру без переносов; пресет «Стандартный» получает прежнее содержимое.
- Предметные причины пропуска строк и динамическая подсказка «Даты».

**Non-Goals:**
- Формат `дд.мм.гггг`, числительные прописью/римские цифры, настраиваемые имена эр, парсинг дат вне колонок `Дата начала/конца`.
- Экспорт дат в xlsx (его нет), e2e-приёмка кастомного календаря (C6).
- Изменения домена `game_calendar` — `month_names`/`spec` достаточно.
- Отдельный «координата-или-None» фасад и протокол-стратегия `DateGrammar`: две ветки (пресет и `spec`), третья ветка парсинга в Non-Goals выше — развилка по признаку D1 остаётся единственной точкой ветвления.

## Decisions

### D1. Ветка по наличию `spec` у активного календаря

Признак кастомной ветки — `getattr(current_calendar(), "spec", None) is not None`: тот же структурный критерий, что уже используют `_intercalary_caption`/`render_calendar_year` для различения кастомного календаря («Стандартный» с переопределёнными именами — рудимент без UI, остаётся стандартной веткой). **Почему не ключ `game_calendar` в `game_settings`**: слой импорта не должен заглядывать в хранилище настроек — accessor уже единственный источник правды. **Почему не «имена отличаются от григорианских»**: кастомный календарь вправе скопировать григорианские имена и остаться кастомным.

### D2. `parse_cell_date(value, calendar=None) -> DateParse | None`

Сигнатура получает необязательный календарь (по умолчанию `current_calendar()`) — тесты и будущий предпросмотр мастера подсунут свой без подмены глобального. Результат — маленький frozen-результат `DateParse` с инвариантом «координата XOR проблема»: поля `coord: GameCoord | None`, `is_bc: bool`, `problem: DateProblem | None`, ровно одно из `coord`/`problem` заполнено; конструируется только фабриками `DateParse.ok(coord, is_bc)` / `DateParse.fail(problem)` и несёт свойство `ok`. **Старый кортеж `tuple[date, bool]` уходит из публичного API вместе с этим изменением** — отдельного «координата-или-None» фасада не вводится: потребитель читает `DateParse.coord`/`DateParse.problem` напрямую. Зона удара переезда одна: единственный вызов в сервисе (`_row_to_draft`) и позитивные проверки `test_xlsx_schema` мигрируют на `DateParse` в группе 1 (fast), переходного кортежного фасада между группами нет. **Почему результат с проблемой, а не `None` + отдельный классификатор**: предметные причины требуются ровно там, где разбор уже различил формы; второй проход по тексту копировал бы грамматики.

### D3. Грамматики кастомной ветки — два regex + словари имён

Нормализация текста: `strip()`, схлопывание внутренних `\s+→' '`, регистронезависимое сопоставление (casefold-ключи). Форма месяца — `день(1-2 цифры) имя(не число) год(1-4 цифры) необязательный хвост`; форма вставного дня — та же без номера дня. Хвост наследует нынешний подшаблон эры (`г.? до н.?э.?` — до н.э.; одиночное `г.` или пусто — наша эра; хвост — единственный источник эры). Словари: `months` (именования календаря, casefold) и `intercalary` (имена правил `spec.intercalary`, значение — индекс правила); поверх словаря месяцев работает мост родительного падежа: слово из старого `_BC_MONTHS` разворачивается в именительную форму и проходит только при её наличии среди месяцев календаря (в стандартной ветке справочник работает как сегодня). Порядок разрешения: словарь месяцев → мост родительного → словарь вставных (для формы без дня) → проблема. Пересечение имён месяцев и вставных дней (валидатор его не запрещает) различается самой формой записи: с номером дня — только месяц, без — только вставной. **Почему regex, а не разбор по токенам**: формы плоские, текущие тесты зафиксировали точные границы (в т.ч. отсутствие `дд.мм.гггг`).

### D4. Перечень предметных проблем пред-анализа

`DateProblem` — код + параметры для русской подписи вызывающим: `unknown_name` (имя не найдено ни в месяцах, ни во вставных), `intercalary_with_day` (номер дня при вставном имени), `month_without_day` (имя месяца без номера), `out_of_range` (год/день вне конструктора координаты — до сдвига политикой не доходит, год вне 1…9999 умирает здесь). Подпись строки пропуска (`RowIssue`) достраивается в `xlsx_import_service` (тексты отображения не попадают в чистую функцию парсинга — словари кодов у потребителя, как `_CODE_PHRASES` мастера). Сдвиг невалидного дня (31 в 30-дневном месяце) остаётся не проблемой, а переносом — политика C1/C3a без изменений, включая формулировки отчёта.

### D5. Старая ветка — существующий код без единой новой формы

Стандартная ветка вызывает нынешние `_parse_bc_iso`/`fromisoformat`/`_parse_bc_text` слово в слово (разобранное число обёртывается тем же `as_game_coord` в координату обычного дня и оформляется `DateParse.ok(coord, is_bc)`, неразбираемое остаётся `None`); `fail()` с проблемным кодом в стандартной ветке не появляется ни при каком входе. Тесты `test_xlsx_schema`, зафиксировавшие None-случаи (`«5 флореля …»`, `31.12.2025`), остаются как regression-запрет на расширение; позитивные проверки переносятся на `DateParse.ok(...)` без изменения значений. «3 Зимостой 44» в стандартной игре — `None` (сценарий дельты).

### D6. Генератор шаблона переезжает в `app/application/services/xlsx_template.py`

`build_template_workbook(calendar: GameCalendar) -> Workbook`: тело генератора и `SAMPLE_ROWS` мигрируют из теста без переписывания; функция доорабатывается по активному календарю. Золотые снимки: эталон «Стандартного» — таблица клеток, строится в тесте из нынешнего генератора (равенство файла и генератора закреплено тестом сегодня, поэтому удаляемый файл ничего не теряет); второй золотой — фиксированный кастомный календарь (13 месяцев со своими именами длины, 8-дневная неделя, 1 вставной день). **Почему не модуль в presentation**: генератор — часть контракта импорта (реестр колонок уже в `xlsx_schema`), а диалог остаётся транспортом (правило repo: логика не в View).

### D7. Корректировка примерных дат — детерминированное усечение до валидных координат

Каждая примерная строка `SAMPLE_ROWS` сохраняет лист, имя строки, год и эру; месяц корректируется до `min(month, len(months))`, день — до `min(day, month_length(month'))`. Вид ячейки сохраняется (нативная остаётся нативной, ISO-текст — ISO). В кастомном календаре строка «Заговор» записывает BC-дату игровой текстовой формой (`format_game_date` того же координатного значения), а при `spec.intercalary` непустом лист «События» получает дополнительную примерную строку с датой вставного дня (`Имя год`). Для пресета корректировка — тождество, содержимое совпадает с удалённым файлом клетка-в-клетку. Устойчивость к вырожденному календарю: единственный месяц длиной 1 даёт день 1.

### D8. `save_template_as` генерирует после подтверждения сохранения

Диалог выбора места (дефолтное имя `import_template.xlsx` — без изменений) → сборка workbook в `BytesIO` → запись на диск; `QMessageBox` при OSError/отказе сборки — существующие ветки ошибок переиспользуются. Сборка до диалога исключена: генерация дешёвая, но пользовательская отмена не должна порождать работу. Статический ресурс, `datas`-запись `nri_manager.spec` и бандл-тест удаляются; на место `test_spec_template_bundle.py` приходит запрет-тест (в `datas` спецификации нет `import_template`, файла нет в `resources/`).

### D9. Динамический блок «Даты» подсказки и описания колонок

Хелпер `date_formats_hint(calendar) -> str` (рядом с генератором, тексты — presentation-словарь): пресет — нынешние две строки дословно; кастом — прежние строки + строка игровой формы, где пример строится валидной координатой активного календаря (`day = min(3, длина первого месяца)`, `format_game_date(..., is_bc=True)`), при наличии вставных дней — и его имя. `build_format_text` подставляет блок вместо литерала; описание реестра `COL_START_DATE.description` — текстовая константа пресета, а диалог при рендере таблицы подставляет колонкам дат календарь-зависимое описание (реестр остаётся статичным: сверка заголовков по `label` не затрагивается).

### D10. Индекс вставного дня из порядка правил спеки

Имя → `IntercalaryDay(year, index)` по позиции правила в `spec.intercalary` (0-based) — тот же индекс, которым оперируют кодек координат и `_intercalary_caption`. Правила не удаляются молча (редактор пересобирает спеку, невалидные координаты сдвигает обход), поэтому парсер не встречает «имя без индекса» в живом календаре.

## Risks / Trade-offs

- [Смена валюты возврата парсера задевает потребителя] → фасада нет, но зона удара узкая и закрыта в одной группе: единственный вызов `_row_to_draft` и 11 позитивных кейсов `test_xlsx_schema` мигрируют на `DateParse` вместе со сменой API (16 None-кейсов не трогаются — семантика `None` стандартной ветки прежняя). Матричные тесты новых грамматик пишутся до добавления кастомной ветки (TDD), прогон всего pytest после каждого шага задач.
- [Стандартная ветка может непреднамеренно расшириться при рефакторинге] → старые None-кейсы остаются в реестре тестов нетронутыми; отдельный тест «стандартная ветка на любой кастомной грамматике = None».
- [Золотой снимок «Стандартного» переживает удаление файла только если генератор≡файл на момент удаления] → equality-тест прогоняется зелёным до удаления ресурса; золотая таблица фиксируется из его же выхода.
- [Клетка-в-клетку для пресета против будущего мирного изменения шаблона] → сознательная плата grill-сессии: любое изменение шаблона после C5 — осознанная правка золотого снимка.
- [Схлопывание пробелов может стереть намеренную разницу имён вроде «А Б» и «А  Б»] → принято grill-сессией (вопрос 3 третьего раунда); уникальность имён валидатор сравнивает по точной строке, а такая пара имён остаётся теоретической.
- [Кастомная игра с кастомным файлом ISO-месяцев вне числа месяцев молча переносится] → не регресс: ровно та же политика C3a для чисел, она уже в отчёте.

## Migration Plan

Схема БД и данные не меняются. Один коммит: переезд генератора → золотые снимки зелёные → удаление `resources/import_template.xlsx`, `nri_manager.spec`-записи, бандл-теста. Игры на пресете не замечают изменения форматов; кастомные игры получают новые формы и честный шаблон. Откат — revert коммита (файл возвращается из истории).
