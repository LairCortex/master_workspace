# Design: close-custom-calendar-map

## Context

См. `proposal.md` — Why. Контекст решения:

- E2E-инфраструктура уже умеет водить реальное приложение offscreen: `tests/ui/test_e2e_standard_game_acceptance.py` (C3a) и `test_e2e_calendar_wizard_entry.py` (C4) стартуют/гасят `Application` на временной базе, ждут асинхронные состояния через `wait_for`-хелперы (`tests/ui/conftest.py`, `helpers.py`, `timeline_probe.py`) и кликают widgets по `objectName`.
- Все нужные клик-якоря заданы ещё в C3b/C4: клетки `GameCalendarCell`, плашка `GameCalendarIntercalaryChip`, шапка `GameCalendarDayName` в сетке, кнопки/чекбокс мастера, эра-чекбокс попапа. Их widget-приёмка кликами уже есть в `tests/presentation/test_calendar_grid.py` — e2e-приёмка повторяет те же действия поверх полного жизненного цикла.
- Прецедент пин-теста: `tests/test_spec_no_import_template_bundle.py` — проверка-запрет текстом по фиксированному файлу. Для запрета Qt-носителей текст не годится: `QDate` легально живёт в docstring (`calendar_grid.py`, `timeline_date_popup.py`) и в QSS-текстах.
- Требование карты (grill 2026-09-21): прод C6 не трогает; версии не трогаются; существующие helpers на `vm.set_dates` остаются.

## Goals / Non-Goals

**Goals:**
- Запрет-пин, который нельзя «починить» переименованием или переносом в строку-подсказку, и который не падает на упоминаниях в документации.
- Две e2e-приёмки кастомного календаря, где каждый календарный элемент нажат мышью; прогон «проходит» = вся копия тестов зелёная.
- Раздел пользовательской документации о календаре + актуализированные чек-лист, карта и CHANGELOG.

**Non-Goals:**
- Переписка существующих e2e-helpers на клик-путь (остаются `vm.set_dates` ради скорости и стабильности).
- e2e-диалог xlsx-импорта поверх кастомной игры (покрыто сервисными тестами C5).
- Двойной прогон приёмки в обеих темах; любые изменения прода и версий.

## Decisions

### D1. Пин-запрет — AST-скан, а не текстовый grep

`tests/test_no_qt_date_carriers.py` парсит `ast` каждый `.py` под `app/` и `tests/` (без `__pycache__`) и падает на:
1. импорте имени `QDate` или `QCalendarWidget` (`ImportFrom`);
2. обращении к атрибуту `setDate` (`ast.Attribute`/`ast.FunctionDef` с таким именем — прокси-метод не должен вернуться ни как вызов, ни как объявление; `vm.set_dates` — другое имя, не задевается).

`date()`-прокси отдельно не гейтится: его подпись обязана принимать/возвращать `QDate`, поэтому п.1 закрывает и его — альтернатива «запретить атрибут `date`» отвергнута, `.date()` легален у `datetime`. Упоминания в docstring/комментариях не являются AST-узлами — упоминания в тексте проходят (сценарий спеке). Ошибка содержит путь файла и номер строки. Текстовый grep (прецедент spec-datas) отвергнут: ловил бы docstring и QSS-строки.

### D2. Приёмка — один файл `tests/ui/test_e2e_custom_calendar_acceptance.py`, два теста

Обе сцены едут через реальный `Application` по образцу `test_e2e_standard_game_acceptance.py`, фикстуры `tests/ui/conftest.py`:

1. `test_custom_calendar_from_wizard_to_every_caption_and_restart` — новая игра (первый вход мастера — модалка до `show()`), клик-путь мастера: «Кастомный» → «Неделя» (8 имён) → «Месяцы» (строки «имя | длина») → «Вставные дни» (одна плашка) → «Предпросмотр» → «Применить»; затем событие на вставном дне и событие «до н.э.»: поле даты EventDialog → `ThemeDatePopup` → клик по плашке/клетке + эра-чекбокс; затем проверки подписей (шкала, лента, детальная, снимок мира) и перезапуск `Application` на той же базе — координаты и подписи прежние.
2. `test_custom_calendar_midgame_shorten_shows_shift_report` — игра с записями на кастоме; мастер → «Месяцы» уменьшает длину → экран отчёта о переносе показывает имена перенесённых записей → применить → лента/детальная отдают новые даты.

Альтернатива «два файла» отвергнута: общая преамбула (посев кастома мастером) переиспользуется первым тестом как фикстура-фабрика; второй тест стартует с применённым кастомом через прямой `promote_draft` без второго мастер-прогона — дешевле повторного полного мастер-прогона ради второй игры.

### D3. Клик-механика — только существующие якоря и хелперы

Клетки находятся `findChildren(GameCalendarGrid)` → `GameCalendarCell`/`GameCalendarIntercalaryChip` (по номеру месяца/правила), клики `qtbot.mouseClick`, ожидание попапов через `wait_for`; кнопки мастера — по `objectName` из `views/calendar_wizard.py`. Прод под приёмку не допиливается: если клик-путь где-то блокирован отсутствием якоря — это дефект C6-приёмки и правится в тестах (ожидания/тайминги), не в проде. Исключение-предупреждение: права нет менять виджеты ради удобства тестов.

### D4. Тема одна, кастом фиксированный

E2E стартует в тёмной теме (тема существующих e2e); фиксированная спека: неделя 8 дней (имена «Перови» — «Осьми»), месяцы 3 × {30, 29, 28}, одно правило вставного дня после месяца 2 — не похожа ни на пресет, ни на фикстуры юнит-тестов, любое протекание видно сразу. Тесты кожи сетки/мастера остаются в `test_calendar_grid.py`/`test_calendar_wizard_dialog.py`.

### D5. Документация — из уже написанных текстов, без нового прод-кода

Раздел `docs/README.md` «Календарь игры»: что настраивается (неделя → месяцы → вставные дни), вставной день явным противопоставлением «празднику» (формулировка из рамки карты и экрана мастера), где мастер («Настройки → Календарь…», первый запуск новой игры), старые игры = «Стандартный». Строки `docs/functional-checklist.md`: пункт «Названия месяцев…» → «Календарь…» с мастером; строка кастомных месяцев переписана под приёмочные сценарии. Карта: ячейка C6 переписана под фактическое содержание и закрыта; статусная строка сверху помечает карту закрытой (C0–C6). CHANGELOG — запись по прежнему формату с «версии не трогаем».

## Risks / Trade-offs

- [Клик-тайминги попапов над реальным `Application` — источник нестабильности] → переиспользование отработанного `wait_for` и двухтаповой механики из island/standard-acceptance тестов; при мигании — стабилизация ожиданиями, не откатом на `vm.set_dates`.
- [Пин-запрет гейтит только AST-имена, текст `QDate` в QSS/строках не ловит] → сознательный компромисс: виджет/носитель возвращается только через импорт или класс, строковый токен сам по себе безвреден.
- [Обе приёмки медленные (полные циклы + перезапуск)] → ровно два теста; xlsx и темы из e2e исключены; суммарно +2 цикла приложения против уже живущих e2e-файлов.
- [Карта/чек-лист и спека разъедутся формулировками] → правки документов и дельта `ui-testing` в одном изменении, валидация `openspec validate --strict` в задачах.

## Migration Plan

Применение — обычное слияние в `main`: только файлы тестов и документации, без схем и прод-кода; откат — revert коммита, ничего не чинить. Порядок задач: пин → приёмка-1 → приёмка-2 → документы → полный прогон.
