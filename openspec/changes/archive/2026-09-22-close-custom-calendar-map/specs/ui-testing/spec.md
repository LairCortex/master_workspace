# Delta: ui-testing (close-custom-calendar-map)

## MODIFIED Requirements

### Requirement: E2E-сценарии основных пользовательских потоков

Система SHALL иметь автоматизированные системные тесты, запускающие реальное приложение (полный жизненный цикл, а не отдельные компоненты) на временной тестовой базе данных и проверяющие пользовательские потоки: создание новой игры в лаунчере, открытие существующей игры, создание/редактирование/удаление сущностей каждого из четырёх типов (персонажи, организации, локации, предметы), создание события и его редактирование в детальной панели, поиск, настройку подключения LLM (включая проверку соединения) и AI-генерацию значения поля, импорт данных из .xlsx, экспорт игры в архив .nri и переключение между играми.

#### Scenario: Новая игра

- **WHEN** пользователь создаёт новую игру в лаунчере
- **THEN** открывается главное окно, его заголовок содержит имя игры, таймлайн пуст

#### Scenario: Открытие существующей игры

- **WHEN** пользователь открывает существующую игру, содержащую данные
- **THEN** открывается главное окно и таймлайн показывает события этой игры

#### Scenario: CRUD сущностей

- **WHEN** пользователь создаёт сущность любого из четырёх типов из контекстного меню таймлайна, редактирует её в карточке сущности и удаляет
- **THEN** после сохранения сущность отображается в списке и детальной панели, после удаления исчезает из них

#### Scenario: Событие и детальная панель

- **WHEN** пользователь создаёт событие на таймлайне и редактирует его в детальной панели
- **THEN** событие отображается на таймлайне с обновлёнными значениями

#### Scenario: Поиск

- **WHEN** пользователь вводит поисковый запрос с учётом игнорирования регистра
- **THEN** результаты содержат сущности, совпадающие по имени

#### Scenario: Настройка LLM и генерация

- **WHEN** пользователь сохраняет подключение LLM, проверка соединения успешна, и затем запускает AI-генерацию значения поля
- **THEN** статус ассистента «ready», поле заполняется сгенерированным текстом

#### Scenario: Импорт из .xlsx

- **WHEN** пользователь импортирует .xlsx-файл, содержащий события и сущности
- **THEN** импортированные записи отображаются на таймлайне и в соответствующих списках

#### Scenario: Кастомные месяцы

- **WHEN** в игре применён кастомный календарь и открывается таймлайн с событиями
- **THEN** таймлайн отображает даты с именами месяцев и вставными днями этого календаря (сквозной клик-путь настройки и проверки — в requirement «E2E-приёмка кастомного календаря»)

#### Scenario: Экспорт игры

- **WHEN** пользователь экспортирует текущую игру
- **THEN** создаётся архив .nri, содержащий базу данных игры

#### Scenario: Переключение игры

- **WHEN** пользователь переключается на другую игру из меню
- **THEN** открывается главное окно новой игры, предыдущее окно закрыто

## ADDED Requirements

### Requirement: E2E-приёмка кастомного календаря

Система SHALL иметь автоматизированные сквозные тесты кастомного календаря, проходящие полный пользовательский путь на реальном жизненном цикле приложения, где каждый календарный элемент интерфейса — сетка дней, плашка вставного дня, переключатель эры и экраны мастера — управляется реальными мышиными кликами и нажатиями клавиш, а не программами через внутреннее API ViewModel. Приёмочные тесты SHALL выполняться в одной теме оформления.

#### Scenario: Мастер до конца и жизнь кастомной игры

- **WHEN** в новой игре пользователь кликами проходит мастер календаря до конца (неделя из восьми дней, месяцы своих длин, вставной день), применяет календарь, затем кликами по сетке выбора даты создаёт событие на вставном дне и событие с эрой «до н.э.»
- **THEN** шкала, лента, детальная панель и снимок мира подписывают эти даты именами активного календаря (вставной день — своим именем без номера), а после перезапуска игры календарь и обе записи остаются без изменений

#### Scenario: Правка календаря в середине игры с отчётом о переносе

- **WHEN** в игре с записями пользователь через мастер укорачивает месяц так, что часть дат становится невалидной, и применяет календарь
- **THEN** мастер показывает экран отчёта о переносе с именами перенесённых записей, а лента и детальная панель показывают перенесённые записи на новых датах

### Requirement: Запрет Qt-носителей даты в коде и тестах

Тестовый набор приложения SHALL содержать автоматическую проверку, что ни в продуктовом коде, ни в тестах нет ссылок на Qt-класс даты, Qt-виджет календаря и удалённые прокси-методы `date()`/`setDate()` попапов даты — ни импортов, ни вызовов. Упоминания этих имён в текстах документации (docstring/комментарии) проверкой допускается. Григорианский тип даты стандартной библиотеки остаётся легальным входом координатного API и под запрет не попадает.

#### Scenario: Возвращение Qt-носителя ломает проверку

- **WHEN** в продуктовый или тестовый исходный код добавляется импорт или использование Qt-класса даты либо Qt-виджета календаря
- **THEN** автоматическая проверка завершается падением с указанием файла и строки

#### Scenario: Упоминание в тексте документации не мешает

- **WHEN** имя Qt-класса даты встречается только в docstring или комментарии
- **THEN** автоматическая проверка проходит
