## Context

Фаза 1 (`add-dnd-module-foundation`) оставила модуль без витрины: `app/dd/` умеет качать/проверять/хранить датасеты и подключать их игрой (ключ `game_settings` `dnd_datasets`), но записи датасета нигде не разбираются (domain описывает только файл-носитель), типы реестра статичны (`EntityType` + литерал `_descriptors`), поиск — пять SQL-репозиториев, упоминания принимают только числовой id, предпросмотр грузит строго из каталога `_get_entity_service`, строка лестницы знает только `event_id`. Карточка LSS-персонажа — документ `character` v2 с `data`-строкой (изучен: `info`/`stats`/`bonuses`/текстовые блоки форматированного редактора); в бандле схем dd `character.json` отсутствует; Foundry-импорт обещан роадмапом, но в коде не сделан. В датасетах LSS ровно шесть секций — монстров нет. Мотивация и состав — `proposal.md`; решения grill-сессии — сводка в `docs/dnd-module-roadmap.md`.

## Goals / Non-Goals

**Goals:**

- Один обобщённый шов «внешний источник сущностей» вместо четырёх точечных заплаток ядра; в ядре — ни одного предметного слова.
- Полный профиль ядра (без `app/dd`) байт-в-байт сохраняет поведение: пустые регистрации, тот же гейт.
- Данные модуля — только таблицы/ключи модуля; схема ядра не меняется.
- Импортёры LSS-документов работают с существующим `ValidationReport` posture (error блокирует, warning пропускает).

**Non-Goals:**

- Мультикласс, CR-калькулятор, HP-синхронизация (`dnd:health`/`lss:command`), iframe-встраивание (4a), свой формат файла монстра, конвертер наших текстов в LSS — вне (хвост роадмапа).
- Редактирование записей датасетов/заклинаний из приложения.
- Удаление D&D-сущностей (в продукте нет пути удаления сущностей).

## Decisions

### Д1. Протокол внешнего источника — в ядре, регистрация — в composition root

`app/presentation/modules/protocol.py` расширяется протоколом `ExternalEntitySource`: описатели типов (`key`, `label`, `plural_label`, `icon_key`, флаги `searchable`/`mentionable`/`pinnable`/`reference`) + методы провайдера: `search(query) -> tuple[ExternalHit]`, `card_source(key, source_id) -> ExternalCardSource | None`, `mention_candidates(query)`, `resolve_mention(key, source_id)`, `card_tabs(target: CardTabTarget) -> tuple[CardTabSpec]`, `event_marks(event_ids) -> Mapping[int, str]`, `visible` (условие видимости в выдаче — рубильник справочника). Регистрация одна: `Application._compose_game_system_module` передаёт список источников в `ApplicationWiring`/`SearchService`/`MentionFieldHost`/`EntityPreviewViewModel` (там, где сейчас каталог сервисов ядра). Ядро оперирует `str`-ключами; `EntityType` остаётся замкнутым перечислением ядра.
Альтернатива — точечные флаги в ядре под dd (отклонено: четыре рассыхающихся шва, предметные слова); альтернатива — источник «мимикрирует» под `EntityType` (отклонено: enum ядра нельзя расширять из модуля).

### Д2. Реестр: единый словарь поверх enum + внешних описателей

`entity_registry` дополняется реестром добавочных описателей (`register_external(descriptors)`, идемпотентный, только до первого окна): `resolve(key)` видит ядерные и внешние типы, `SEARCH_TYPES`/`RELATED_CONFIG` читают объединение. Ядерные литералы не трогаются; охранка параллельных словарей дополняется проверкой, что единственный путь внешнего типа в реестр — `register_external`. Профиль без dd: реестр неизменен (пин).
Альтернатива — обход реестра провайдером на каждой поверхности (отклонено: ломает требование «единого реестра» и подписи групп поиска).

### Д3. Карточка предпросмотра внешней сущности — через `EntityCardViewModel` с duck-источником

Провайдер собирает `ExternalCardSource` (имя, «источник», текстовые блоки, связи-переходы `(key, source_id, name)`, картинка при наличии); `EntityCardViewModel` принимает его как существующий duck-объект, связи берутся из карточки источника, а не из `related_refs_for_key` (KeyError закрыт описателем). Заголовок «Карточка: <тип>» общий. Отдельного QML-делегата нет — read-only колонка уже умеет рендерить поля/тексты/связи/картинку.
Альтернатива — второй делегат-«читалка» (отклонено: дублирование пиксельного контракта колонки).

### Д4. Грамматика упоминаний: строковый id по типу

`domain/mentions.py`: разбор `@[d](t:id)` с id `\d+|[A-Za-z0-9][A-Za-z0-9._/+-]*`; допустимость формы проверяется по описателю типа (ядерные — только цифры, внешние — строковый/составной `источник/запись`; обратное направление запрещено, чтобы старые тексты не переинтерпретировались). `MentionFieldHost.insertMention`/`activateMention` переходят на `str`-id (числовые конвертируются на границе ядро↔host). Кандидаты `@`: слияние ядерного `search_names` и `mention_candidates` источников; переключатель справочника скрывает `reference`-типы. Клик: ядерный путь не меняется; внешний — `resolve_mention` → read-only карточка в живой зоне; недоступно — существующий канал одного `QMessageBox` («Упоминание не найдено» с формулировкой недоступности).
Альтернатива — числовые суррогаты id (отклонено: id записи — внешний ключ навсегда, суррогат гниёт при правке датасета).

### Д5. Индекс датасетов в dd: кэш id→запись с инвалидацией по содержимому

`dd/application/dataset_index_service.py` — разбор JSON подключённых наборов в память (dict `(dataset_id, entry_id) → запись`, индекс по типам, слаги гримуаров), инвалидация по `sha256` файла (файлы маленькие, полных переразборов не боятся). Поиск/пики/валидатор/упоминания читают индекс, а не диск. Пустой список подключений — пустой индекс.

### Д6. Таблицы модуля — на общем Base, создаются включением модуля

`dd/infrastructure/db/dd_models.py` объявляет таблицы на ядровом `Base` (импорт ядро→вниз легален; в профильном выключении пакет не импортируется — метаданные чисты, ядро не обрастает). Включение модуля (`ModuleSettingsService.enable` и bootstrap при старте D&D-игры) вызывает `create_all(tables=dd_subset)`; выключение таблицы сохраняет (как решено роадмапом). Состав:
- `dd_character_ext` — `character_id` PK/FK→characters, ссылки вида/подвида/класса/подкласса/предыстории (тройка `source_key`+`ref_id`+`snapshot_name`), `level`, `lss_sheet_id`, `raw_document` TEXT (сырой LSS-файл), `text_blocks` JSON (именованные блоки «имя→текст», включая рендер структуры);
- `dd_character_spell_link` — `character_id`, `source_key`, `slug`, `snapshot_name`;
- `dd_monster` — `id`, `name`, `image_id`→images (переиспользование хранилища картинок ядра), `rating`, `blocks` JSON (текстовые разделы монстра);
- `dd_encounter` — `event_id` PK/FK→events `ON DELETE CASCADE`, `composition` JSON (`{monster_id, count, name_snapshot}`), `note`.
Ключи `game_settings`: `dnd_search_show_reference` (bool, по умолчанию «показывать» — справочник обнаруживается с первого включения), `dnd_grimoires` (список id). Механизм миграций — штатный `init_db()`; для уже открытых D&D-игр таблицы досоздаются включением/bootstrap (аддитивно).
Альтернатива — таблицы через `_MIGRATIONS` (отклонено: DDL уезжает из модуля в ядро).

### Д7. Импорт персонажа: схема `character.json` в бандл + доменные проверки dd

Схема `character.json` (draft-07) бандлится рядом с восемью схемами датасетов (гейт версии по образцу `FORMAT_VERSION`), проверка — существующий `validate_shape`. Доменные проверки `dd/domain/character_checks.py` (коды `CHAR_*`): живой экспорт принимается легально (`bonusesSkills`/`bonusesStats`, `createdAt`, `wizardStep`/`choices` — warning-коды), `blockquote` и неизвестные узлы текстовых блоков — warning с вырезанием узла при конвертации (мы их не порождаем никогда). Отчёт — общий `ValidationReport`; конвертер `editor_doc_to_text()` — whitelist узлов: paragraph/text/списки→текст, `formula`/`roller`→строка формулы как есть, `resource`→«<имя ресурса>», `divider`→пустая строка, `spoiler*`→развернутый текст, `taskList`→строки с чекбоксами «[x]/[ ]»; нераспознанный узел — текст детей + warning. Структурный рендер (`stats`/`skills`/`weaponsList`/`resources`/`coins`/`spells`) — детерминированные именованные блоки в `text_blocks`. Снимки ссылок `info.charClass.id` и т.п. резолвятся по индексу подключённых датасетов; не подключен — тройка с пустым source_key + снимок из файла.

### Д8. Гримуары: толерантный парсер, не JSON Schema

У LSS нет публичной схемы Foundry-файла заклинаний — проверка доменная (`dd/domain/grimoire.py`, коды `GRIMOIRE_*`): структура «список заклинаний с именем/слагом/описанием» (HTML описаний → plain-text конвертером), слаги нормализуются; ошибки — пуст/неразбираемый файл; дубликаты слогов заклинаний — предупреждение; пересечение с SRD-слагами — предупреждение «слаг из SRD» (легально, но избыточно). Хранилище — `~/.nri_manager/grimoires/<id>.json` по образцу датасетного (`DatasetStorage`-сibling). Golden-тесты на реальных Foundry-экспортах (файлы добавляются в тесты при apply).

### Д9. Лестница: аддитивный `marks` в контракте строки

`build_rows` получает необязательный аргумент `marks_by_event: Mapping[int, tuple[str, ...]]` и поле `Row.marks` (пустой кортеж по умолчанию — все существующие тесты зелены); делегат рисует маркер токенами темы (`color.accent`/`chart`) без геометрии и новых координатных пределов. Источник пометок — `event_marks` зарегистрированных источников через `TimelineViewModel`. В профильном выключении — пусто.
Альтернатива — отдельная строка-«обёртка» встречи (отклонено: встреча не имеет отдельного времени).

### Д10. Табы карточек: общий TabBar в QML-островах карточек

Карточка события и карточка сущности (острова `EventDialog`/сущностного редактора) получают горизонтальный `ThemeTabButton`-бар группировки; группы задаются декларацией полей по типам в одном месте presentation; поведение (активный таб, сохранение со скрытых табов, прыжок к ошибке — `field_invalidated` уже несёт поле) — общее. Модульные табы: `CardTabSpec(key, title, factory(wiring, target_id))` — содержимое рисует модуль (свой QML-остров/фрейм с собственным VM), ядро даёт полосу табов и жизненный цикл (release подписок при закрытии — норма «остров не отвечает после релиза»). Дизайн-задача `ui-ux-designer` (первый таск) фиксирует состав групп, внешний вид полос, вид пометки встречи (Д9) и посадку модульных табов; до её результата кодинг табов не начинается.

### Д11. Имена SRD-заклинаний из слага

Человеческое имя — механическая гуманизация слага (дефисы→пробелы, заглавная первая) без выдумывания текста; в карточке строка «Полный текст доступен в Long Story Short». Слаг+источник — ключ; один слаг в двух SRD-редакциях — две сущности (`srd51/…`, `srd52/…`).

## Risks / Trade-offs

- [Единое изменение большое — долгий apply] → задачи нарезаны вертикальными срезами с зеленым гейтом после каждого; порядок срезов фиксирует tasks.
- [Грамматика упоминаний — общий разбор, риск регресса старых маркеров] → golden-тесты парсера на существующих текстах + двусторонние фаззы строковых id.
- [EntityCardViewModel терпит чужие ключи только с описателем — KeyError в неожиданных местах] → реестр отвечает на любой зарегистрированный ключ; тесты-зонды по всем поверхностям (поиск/пины/предпросмотр/упоминания).
- [Правка датасета ретроактивна: чипы и пины остаются снимками] → осознанный компромисс grill (снимок имени + «источник не подключён»); живой пересинк — не обещаем.
- [Foundry-формат без авторитетной схемы] → толерантный парсер + golden-файлы; при смене формата чинится по Changelog LSS (норма роадмапа).
- [Индекс датасетов в памяти] → файлы < единиц МБ; инвалидация по sha256; при пустых подключениях — ноль затрат.
- [Два профиля гейта] → каждый срез бегает `run_tests_isolated.py` в обоих профилях; профильные пины на пустые регистрации и байт-поведение ядра.

## Migration Plan

Аддитивно: новые таблицы (create_all по включении), новые ключи `game_settings`, новые файлы в глобальных хранилищах (`~/.nri_manager/grimoires/`). Ни одна существующая строка не трогается. Откат = выключение модуля (флаг гаснет, таблицы остаются) или откат кода на обычный профиль (`NRI_DISABLE_DD_MODULE=1`) — обычное приложение читает такую игру как раньше.

## Open Questions

- Точный вид пометки встречи и состав групп табов — домен дизайн-задачи (первый таск tasks), не влияет на спеки.
- Имена golden-файлов Foundry-экспортов подбираются при apply из реальных выгрузок (формат зафиксирован парсером, не вопрос спецификации).
