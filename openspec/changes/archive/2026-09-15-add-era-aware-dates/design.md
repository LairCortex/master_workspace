# Design: add-era-aware-dates

## Context

См. `proposal.md` — Why. Текущее состояние, влияющее на решение:

- Каждая дата — `datetime.date`, в SQLite текст `YYYY-MM-DD`; границ 100/9999 в домене и БД нет, они живут только в `theme_date_popup.py` (`MIN_DATE`/`MAX_DATE`, спин 100…9999, границы `QCalendarWidget`).
- `datetime.date` не представляет год < 1 и не парсит «до н.э.»; `QCalendarWidget` не показывает годы до 1 г. н.э. — ноль и зеркальный календарь неизбежны как продуктовое решение (принято на гриллинге: дата + флаг эры, зеркало по нашей эре).
- Точек, где важен порядок дат, ровно пять: валидация `end < start` (`domain/entities/base.py`, `domain/entities/rating.py`), `order_by`/оконный запрос `event_repository.py`, фильтр окна и сортировка `timeline_rows.py`, логика окна `timeline_viewmodel.py`.
- Даты есть у шести таблиц: `events`, `organizations`, `characters`, `items`, `locations`, `ratings` (`infrastructure/db/models.py`). `Rating` дублирует пару дат, не наследуя `BaseEntity`.
- Переезд схем — идемпотентные шаги в `init_db()` (`infrastructure/migrations.py`): `_MIGRATIONS` (ADD COLUMN по факту отсутствия столбца) и шаговые пересборки по образцу `_migrate_nullable_end_dates`; alembic не используется.

## Goals / Non-Goals

**Goals:**
- Эра как часть каждой даты без нового класса даты: пара (`datetime.date`, `is_bc`) плюс один общий арифметический помощник.
- Единый целочисленный хронологический ключ для сравнений, SQL-сортировки и оконного фильтра.
- Идемпотентный переезд старых БД с копией `.bak`; работоспособность старой версии приложения поверх migrated-файла.

**Non-Goals:**
- Вынос каталога `games/` изнутри сборки — отдельная задача (решение гриллинга).
- Экспорт дат в xlsx (экспорт дат в приложении нет; канон текстового вида при появлении — «N г. до н.э.»).
- Настройка «своя эра» для игры, нулевой год на экране, юлианский календарь.

## Decisions

### D1. Представление: пара (date, flag), а не новый тип даты
Поле `is_bc: bool` рядом с каждой из `start_date`/`end_date` в домене и ORM. Альтернатива — класс `GameDate` (отвергнута: точки сравнения централизованы, цена переписывания всех слоёв выше, а UX «календарь + чекбокс» — требование).

### D2. Ключ эпохи: `key = ordinal` (н.э.) / `key = ordinal − 732·year` (до н.э.)
`era_key(d, is_bc) = d.toordinal() if not is_bc else d.toordinal() - 732 * d.year`. Наивное `±ordinal` отвергнуто: `−ordinal` обращает порядок внутри BC-года (15 марта 44 г. до н.э. получает ключ раньше 5 марта), тогда как спека требует естественного хода дней внутри эры. Свойства (проверены исчерпывающим перебором всех BC-дат и сверкой с SQL из D4): ключ строго растёт вдоль реальной BC-хронологии (древнее = меньше): год убывает и доминирует (шаг 732 = 2·366 больше максимального обратного прыжка ординала на границе года: два 366-дневных года подряд в пролептическом григорианском календаре невозможны, поэтому прыжок ≤ 365+366−1 = 730, — итоговый шаг на границе года +2…+3: два соседних обычных года дают +3, високосный с обычным — +2), внутри года дни идут естественно (+1); разделение эр: BC-ключи ∈ [−3 667 573, −367] < 0 < 1 ≤ CE-ключи ∈ [1, 3 652 059] (границы подтверждены перебором); инъективность — из строгой монотонности на полном порядке BC-дат (разность 732·year ≥ 732 > разброса ординала внутри года); зеркальные месяцы/високосность «до н.э.» = у нашего года с тем же числом (Q11 без изменений: используется тот же пролептический григорианский объект года Y, 29 февраля до н.э. существует тогда же, когда после н.э.). Альтернатива — астрономический год `1−Y` (отвергнута: рассогласует календарь-зеркало с ключом; выгоды нет — порядок от неё не меняется).
Общий помощник живёт в `app/domain/date_era.py`: `era_key`, `cmp_era_dates`, `assert_range` (1…9999 обеих эр). Валидация «end не раньше start» в `base.py`/`rating.py` и все сравнения переходят на помощник; прямое сравнение `date` вне него запрещено (проверяется тестами на смешанные эры).

### D3. Хранение: четыре аддитивных столбца в шести таблицах
`start_bc INTEGER NOT NULL DEFAULT 0`, `end_bc INTEGER NOT NULL DEFAULT 0`, `start_key INTEGER NULL`, `end_key INTEGER NULL`. Ключи nullable — иначе вставки старой версии приложения падают (требование совместимости). Текстовые даты остаются источником значения; ключ — производный индекс порядка. Альтернатива — одна колонка-int вместо даты (отвергнута: ломаются все чтения старой версии, нет аддитивности).

### D4. Бэкфилл и поддержка инварианта «ключ либо проставлен, либо NULL»
Шаг `init_db()` (после ADD COLUMN): идемпотентный
```sql
UPDATE <t> SET start_key = CASE
  WHEN start_bc THEN (CAST(julianday(start_date) AS INTEGER) - 1721424) - 732 * CAST(strftime('%Y', start_date) AS INTEGER)
  ELSE CAST(julianday(start_date) AS INTEGER) - 1721424
END WHERE start_key IS NULL
```
Вывод из D2: для любой даты `julianday('YYYY-MM-DD') = toordinal + 1721424.5`, хвост `.5` усекается `CAST` одинаково у всех дат (усечение на порядке не сказывается), поэтому обе ветви дают значение, побитово равное `era_key` из D2, — константа `1721424` вычитана именно для того, чтобы ключи из БД напрямую сравнивались с ключами, посчитанными приложением (общий сдвиг эр сохранял бы порядок только внутри БД). Выражение сверено с Python-формулой исчерпывающе: все календарные даты 0001…9999 обеих эр (7 304 118 ключей, включая високосные/невисокосные годы и границы 0001/9999) — расхождений нет. То же выражение для `end_key` при `end_date IS NOT NULL`. Это же закрывает строки, дописанные старой версией после миграции. Сортировка/окно в `event_repository.py` переходят на `start_key`/`end_key`; `timeline_rows.py` и `timeline_viewmodel.py` оперируют ключами, полученными через D2.

### D5. Перенос старых БД: копия `.bak` перед первым переездом
Если у таблицы нет `start_bc` (признак немигрированной игры) и файл базы существует: `shutil.copy2(game.db, game.db.bak)` при отсутствии `.bak` (повторно не перезаписывается). semantics: эра всех перенесённых дат — «н.э.» (значение даты не меняется, ключ дописывается D4).

### D6. UI: один чекбокс на календарь, границы 1…9999 на эру
`_CustomCalendar`: `MIN/MAX = date(1,1,1)/date(9999,12,31)`, спин 1…9999, чекбокс «до н.э.»; переключение эры не меняет чисел выбранной даты; clamp — по текущей дате независимо от эры. `_DateWindowPopup` — два независимых чекбокса (решение Q9). Мосты попапов отдают парами (дата, `is_bc`); диалоги события, карточки сущности, снимка мира хранят пару в себе, QML получает готовые строки `display` (уже питоновские) и новые булевы `*Bc` для фацетов — форматный слой (`format_game_date`) печатает «N г. до н.э.». Значение по умолчанию — сегодня, эра «н.э.».

### D7. Импорт xlsx: два новых текста-формата
`parse_cell_date` добавляет распознавание «`N г. до н.э.`» и `−YYYY-MM-DD` → `(date, True)`; нативные ячейки Excel и голый ISO — эра «н.э.» (как раньше). Неразбираемое — проблема строки, как сейчас. Колонка связей/призраки (`ghosts`) считают границы призраков ключами.

## Risks / Trade-offs

- [Код сравнит `date` напрямую и ошибётся через эру] → только 5 существующих точек + тесты на смешанные эры (сортировка шкалы, окно, валидация карточки); помощник D2 — единственный разрешённый путь.
- [`format_game_date` вызывается где-то с чистой датой без эры] → инвентаризация всех вызовов в задачах; сигнатура принимает пару.
- [Старая версия пишет даты, ключ=NULL, окно в новой версии их не видит] → бэкфилл D4 запускается в `init_db()` при каждом открытии, идемпотентен.
- [Порядок `era_key` (D2: `ordinal − 732·year` для до н.э.) не совпадает с «астрономическим» високосным правилом до н.э.] → принято зеркало (решение Q11): для игрового мира 29 февраля до н.э. существует тогда же, когда и после н.э.
- [Раздвоение полей дат в `Rating` и `BaseEntity`] → правки применяются в обоих местах, проверятся общими тестами репозиториев.

## Migration Plan

1. Домен + помощник + валидации; ORM-столбцы; формат даты; репозиторий/строки шкалы на ключах.
2. `init_db()`: ADD COLUMN (существующий паттерн `_MIGRATIONS`) → копия `.bak` при первом переезде → SQL-бэкфилл ключей.
3. UI (попапы, диалоги, QML-мосты), импорт xlsx, документация (`docs/README.md`), спецификации, тесты.
Откат: удаление новых колонок не требуется (аддитивно), старая версия читает прежние даты; `game.db.bak` — страховка на случай бага пересборки.

## Open Questions

Нет — все продуктовые развилки закрыты на гриллинге (эр-ключ, зеркало, границы, чекбоксы, форматы, миграция, совместимость, вынос `games/` — отдельной задачей).
