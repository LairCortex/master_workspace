# Design: wire-game-calendar-key-binding

## Context

C0 `add-game-calendar-core` дал `app/domain/game_calendar.py`: протокол `GameCalendar`, реализации `StandardCalendar`/`CustomCalendar`, спеку/валидацию/предпросмотр. Приложение его не импортирует. Ключ порядка — `era_key` (`app/domain/date_era.py`): `toordinal()` / `toordinal() − 732·year` (до н.э.); `StandardCalendar.to_key` в C0 сам зовёт `era_key`. Точки порядка дат: ORM-хук `_sync_era_keys`, сортировка/окно (`event_repository`, `timeline_rows`, островные viewmodel'ы), проверка `end ≥ start`, призраки xlsx-импорта — все идут через `era_key`. Дерево решений зафиксировано grill-сессией 2026-09-19 (Q1–Q19), карта — `docs/custom-calendar-roadmap.md`, инвентарь — `docs/spike-custom-calendar.md`.

Ограничения: ключ — 64-битный `INTEGER`; UI настройки (C2/C4) нет → в реальном запуске активен только «Стандартный»; колонки дат типизированы как `date`, координата вне `datetime.date` (месяц больше 12, месяц длиннее 31 дня, вставной день) в них не помещается.

## Goals / Non-Goals

**Goals:**
- Порядок дат приложения считается через активный объект-календаря (шов под будущее).
- Пресет «Стандартный» даёт побитово прежний ключ; хук, `julianday`-бэкфилл и репозитории не переписываются под кастом.
- Чистая (без БД) политика сдвига невалидных координат и форма отчёта.

**Non-Goals:**
- Хранение и кодирование координат (C2); обход шести таблиц и запись сдвинутых координат (C2).
- Persist отпечатка календаря и сверка на открытии (C4); сетка/мастер/импорт игрового текста (C3/C4/C5).
- Запись в `game_settings`; подключение accessor к `main.py`.

## Decisions

### D1. `era_key` остаётся единственным публичным порядком и становится тонким диспетчером
`(d, is_bc)` сохраняет сигнатуру; тело: ленивый импорт `current_calendar()` и вызов `to_key(MonthDay(d.year, d.month, d.day), is_bc)`. Ни один из 13 вызовов не меняется по тексту.

### D2. Рекурсия рвётся приватной формулой `_gregorian_key`
Перенести действующую формулу (`toordinal`/шаг 732) в приватную `_gregorian_key(d, is_bc)` в `date_era`; `StandardCalendar.to_key`/`from_key` зовут её, а не `era_key`. Цепочка: `era_key → активный календарь → (Стандартный) → _gregorian_key`; Стандартный никогда не вызывает `era_key`. Модульный цикл `date_era ↔ game_calendar` рвётся ленивым импортом в теле `era_key`. Альтернатива (перенос диспетчера `era_key` в `game_calendar`) откинута: правит 13 импортов.

### D3. Accessor активного календаря — модульный глобал в `game_calendar`
`_current_calendar: GameCalendar = StandardCalendar()`, `current_calendar()`, `set_current_calendar(cal)`, `reset_current_calendar()`. Без блокировок: единый цикл событий qasync, переключение игр сериализовано (`shutdown()` + `start()`). Это адрес риск №1 из спайка (`_current_months`) — явный set/reset вместо молчаливой мутации; подключение к переключению игры — C2.

### D4. Чистый предикат и сдвиг поверх протокола (ровно три причины)
`classify(coord, cal): None | reason` и `shift_invalid(coord, cal): (coord, reason) | None` в `game_calendar`. Правила: день больше `month_length(year, month)` → (тот же месяц, последний день); номер месяца больше числа месяцев → (последний месяц, его последний день) того же года/эры; номер вставного дня вне списка → clamp к последнему правилу (перенумерацию правил мастера — не сюда). Валидная на входе координата → без изменения (пустой результат), сдвиг идемпотентен. Год вне 1…9999 причиной сдвига НЕ является — остаётся `InvalidGameDateError` из ядра. `assert_range`/`cmp_era_dates` не меняются.

### D5. Форма отчёта о переносе
Frozen-датакласс записи: `table`, `row_id`, `field ∈ {start, end}`, `old = (ord/coord, is_bc)`, `new = (…)`, `reason = день_overflow | месяц_вне_числа | индекс_вставного`. Домен БД не читает: список записей собирает вызывающий обход (C2). Локализация/имена — вне домена (C4 рисует экран).

### D6. Реальный запуск = Стандартный, ветка кастома — тесты подмены
Дефолт accessor даёт пресет «Стандартный»; хук `_sync_era_keys` (уже зовёт `era_key`) и SQL `julianday` продолжают давать прежние числа. Кастом достижим только подменой accessor в тесте; физическая запись кастом-координат в колонки-дату невозможна → модели/миграции не трогаем (решение Q16/Q8).

## Risks / Trade-offs

- **Две копии григорианской формулы (питон `_gregorian_key` + SQL `julianday`).** Не плодим новые: SQL не меняется, питон = ровно прежняя формула; тест-сверка `julianday == era_key` в `test_migrations.py` обязана остаться зелёной.
- **Ленивый импорт скрывает зависимость `date_era → game_calendar`.** Документируется комментарием; обратного импорта в теле модулей нет, цикл один и он рвётся.
- **Модульный глобал accessor повторяет урок глобала месяцев.** Осознанно: единственный читатель `era_key`, явный set/reset; переключение игр приобщит сброс в C2.
- **Сдвиг не трогает реальные записи в этом куске.** Ожидаемо: хранитель координат ещё `date`; готовы чистая политика и форма отчёта, обход по таблицам — C2.

## Migration Plan

Миграции данных нет: меняются только доменные функции, `era_key` сохраняет сигнатуру при новом теле. Дефолт-Стандартный → числа ключа прежние → реальные игры не затрагиваются. Откат — откат commit. Обход шести таблиц и запись сдвигов подключатся в C2, сверка отпечатка и экран отчёта — в C4.

## Open Questions

Нет. Границы будущих кусков зафиксированы: хранилище координат и обход+запись сдвигов — C2; подключение accessor к жизненному циклу — C2; экран отчёта и сверка отпечатка — C4.
