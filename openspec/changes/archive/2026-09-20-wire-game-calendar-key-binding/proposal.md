# Proposal: wire-game-calendar-key-binding

## Why

C0 закрыт: арифметическое ядро `app/domain/game_calendar.py` есть, приложение его не импортирует. Ключ порядка дат живёт в `app/domain/date_era.py` (`era_key`, BC-зеркало с шагом 732). Кусок C1 из `docs/custom-calendar-roadmap.md` («переезд ключа») соединяет ключ с ядром так, чтобы порядок считался от активного объекта-календаря, сохранив для встроенного пресета «Стандартный» побитово те же числа ключей — старые игры не сдвигаются, `julianday`-бэкфилл и репозитории не переписываются. Кусок закладывает шов под настройку (C2) и чистую политику переноса записей с невалидными координатами. UI настройки куска C1 не имеет, поэтому ветка игрового календаря проверяется только тестами подмены активного календаря.

## What Changes

- `era_key(d, is_bc)` остаётся единственной публичной точкой порядка дат и сохраняет сигнатуру; тело становится тонким диспетчером на `current_calendar().to_key(MonthDay, is_bc)`. 13 точек вызова в 5 файлах правок по тексту не получают.
- `app/domain/date_era.py` получает приватную `_gregorian_key(d, is_bc)` (текущая формула `toordinal`/732). `StandardCalendar` переключается с `era_key` на `_gregorian_key` — взаимная рекурсия диспетчера и его дефолтного календаря исключена.
- `app/domain/game_calendar.py` получает accessor активного календаря: дефолт `StandardCalendar()`, явные `set_current_calendar`/`reset_current_calendar`, один активный календарь на процесс, без блокировок (единый цикл событий qasync). Осознанная замена прежнего молчаливого глобала имён месяцев.
- В домене появляется чистая (без БД) политика сдвига невалидных координат: предикат «невалидна + код причины» и преобразование координаты в ближайшую валидную (переполнение дня → последний день того же месяца; месяц вне числа месяцев → последний день последнего существующего месяца; номер вставного дня → clamp к крайнему правилу). Идемпотентно; столкновение записей на одной дате допускается. Плюс форма отчёта о переносе для будущего экрана мастера.
- Не меняется в этом куске: колонки БД и формат кодирования координат (C2), `julianday`-бэкфилл (остаётся единственным заполнителем ключей стандартного пресета), обход шести таблиц и физическая запись сдвинутых координат (C2), запись в `game_settings`, подключение accessor к запуску/переключению игры (C2), сверка отпечатка календаря и экран отчёта (C4), сетка виджета/мастер/импорт игрового текста (C3/C4/C5), правки `main.py`. Ядро BC-зеркала не переписываем (732 остаётся для стандартного, кастомное зеркало уже в C0).

## Capabilities

### New Capabilities
- Нет: все новые требования расширяют существующую доменную способность `game-calendar-core`.

### Modified Capabilities
- `game-calendar-core`: добавлены требования — accessor активного игрового календаря с дефолтом «Стандартный»; вычисление хронологического ключа приложения через активный календарь при побитовом сохранении стандартного ключа; чистая политика сдвига невалидных координат и форма отчёта о переносе (без обхода БД).
- Примечание: `date-eras` поведенчески не меняется («Единый хронологический порядок» тот же; теперь он реализуется через активный календарь — отражено в design, отдельной дельты не требует).

## Impact

- **domain**: `app/domain/date_era.py` (`_gregorian_key` + `era_key` → диспетчер с ленивым импортом), `app/domain/game_calendar.py` (accessor активного календаря; предикат/сдвиг; форма отчёта).
- **без правок**: вызывающие `era_key` (`timeline_rows.py`, `xlsx_import_service.py`, `wiring.py`, островные viewmodel'ы, хук `_sync_era_keys` в `models.py`) тексты вызовов сохраняют; модели/миграции/репозитории; `main.py`.
- **тесты**: новые в `tests/domain/` (совпадение стандартного ключа после диспетчеризации; предикат/сдвиг/идемпотентность; форма отчёта); золото `test_game_calendar.py`, `test_date_era.py`, `test_migrations.py` — без ослабления.
- **порог PR**: правки в 2 доменных файлах + тесты — ниже порога «20 файлов».
