# Design: wire-game-calendar-coordinates

## Context

C0/C1/C2 закрыты: `app/domain/game_calendar.py` даёт протокол `GameCalendar`, пресеты, чистую политику сдвига (`classify`/`shift_invalid`), форму отчёта (`ShiftReport`) и кодек календарь-настроек; `era_key` — диспетчер на активный календарь, активный календарь грузится из `game_calendar`-ключа `game_settings` (C2). Но «валюта дат» — григорианская `datetime.date`: доменные сущности (`entities/base.py`), 6 датированных таблиц (`Date`-колонки), вьюмодели, подписи (`format_game_date`) и прокси диалогов. Координата вне `datetime.date` (месяц > 12, день > длины месяца, вставной день) в неё не помещается физически. Карта потоков дат: вне двух widgets-попапов дата идёт парой `date | (date, is_bc)` через `split_date_era/era_flag/format_game_date`, порядок везде через `start_key/end_key`; QML получает только готовые строки (`startDisplay`, `startIso` — непроверяемая, QML-кодом не парсится и не пишется обратно, `setDateIso` вызывается только тестами). Дерево решений зафиксировано grill-сессией 2026-09-20 (вопросы Q1–Q24); рамки — `docs/custom-calendar-roadmap.md`, инвентарь — `docs/spike-custom-calendar.md`.

## Goals / Non-Goals

**Goals:**
- Дата записи — координата игрового календаря end-to-end: клик/импорт → домен → хранение → чтение → подпись, включая вставной день.
- Стандартная игра не замечает изменений: побитово прежние date-колонки, ключи, подписи, поведение попапов.
- Рассогласование «запись ↔ календарь» (ручная правка настроек) невозможно как состояние после старта: сдвиг с логом до пересчёта ключей.
- Контракты C3b (сетка эмитирует координату) и C4 (мастер применяет календарь, двигает хранилища, рисует отчёт) зафиксированы работающими механизмами.

**Non-Goals:**
- Замена `QCalendarWidget` на собственную сетку, `week_names`, QSS-селекторы, предпросмотр мастера — C3b/C4.
- Вход «Календарь…» и экран отчёта — C4; парсинг игровых названий месяцев в XLSX — C5.
- Перенос «лишних» координат при возврате к пресету через ручную правку — механизм применения (D8) запускается только с активным кастомом; штатный возврат рисует C4.

## Decisions

### D1. Хранилище — дополнительные nullable-колонки в тех же 6 таблицах
`start_coord`/`end_coord TEXT NULL` через `_MIGRATIONS` (`ALTER TABLE ADD COLUMN`, SQLite-дешевизна, перестроения нет). Чтение: coord-колонка заполнена ⇒ истина в ней, иначе date-колонки. Запись при активном кастоме идёт в coord-колонки; date-колонки не обновляются никогда (мёртвое наследие эпохи до переключения, а не зеркало — расхождение невозможно, потому что их никто не читает при кастоме). Альтернативы отклонены grill-сессией: кодек в существующих `Date`-колонках (перестроение всех 6 таблиц + риск для старых игр) и отдельная таблица-спутник (JOIN на каждое чтение, идентичность записи через (таблица, id, поле), перенос строк между хранилищами при переключении).

### D2. Кодек координаты — в домене, формат с дискриминатором рода
`encode_coord(coord) -> str` / `decode_coord(raw) -> CoordDecoded | CoordCorrupted(reasons)` в `game_calendar.py` рядом с `encode_calendar` (тот же принцип «домен владеет своим хранимым видом»; тот же контракт «битый текст отвечает причинами, не исключением»). Формат: обычный день `"M:год:месяц:день"`, вставной `"I:год:индекс_правила"` — числа без ведущих нулей (каноничность фиксирует round-trip-тест). JSON отклонён: тяжелее и не даёт различимости рода дешевле дискриминатора. Формат — непрозрачное внутреннее представление: читается только кодеком.

### D3. Один резолвер пары (ORM-строка ⟷ координата) — единственная ветка хранилищ
В инфраструктуре (рядом с `_sync_era_keys`): `resolve_coord(row, field) -> GameCoord | None` (coord-колонка непуста → декод; битый текст → `None` + очистка колонки + лог — по specs «Повреждённая координатная колонка»; иначе `date`-колонка → `MonthDay`) и `assign_coord(row, field, coord)` (маршрут: coord-колонка строки уже заполнена →(coord); иначе активный календарь кастомный → coord, стандартный → date-колонки). Хук `_sync_era_keys` вычисляет ключ от `resolve_coord` — текст хука остаётся однострочным на каждый слот. Ни один слой выше (сервисы, вьюмодели, presentation) о двух хранилищах не знает: репозитории кладут в доменные сущности уже `GameCoord`. Альтернатива «маршрут только по типу активного календаря» отклонена: при ручном возврате настроек запись уходила бы в нечитаемые date-колонки (истина же в coord).

### D4. Типы домена: имена прежние, тип — `GameCoord | None`, `date` приводится
`BaseEntity.start_date/end_date: GameCoord | None` (+`*_bc` как были); имена полей и payload-ключей (`wiring`-dict, kwargs сервисов) НЕ меняются — словарь проекта определяет «дата = координата», переименование — косметика ценой десятков правок (grill Q9). В конструкторе/валидаторе сущности и в `era_key` обычная `datetime.date` приводится к `MonthDay` — григорианская дата остаётся частным случаем координаты, ~50 тестовых файлов и xlsx-путь с ISO не переписываются литерал за литералом (grill Q20). `era_key` принимает координату; запись несуществующей координаты отклоняет `InvalidGameDateError` (D6 из C0, без тихой нормализации) — попап её не произведёт, xlsx сдвигает сам (D7). `cmp_era_dates`/`assert_range` — сигнатурные типы под координату, поведение то же.

### D5. Подписывалка одна на оба рода координат
`format_game_date(coord | date | None, fallback, is_bc)` в `date_utils`: обычный день — прежний «дд Месяц год[ г. до н.э.]», вставной — «Имя год[ г. до н.э.]» без номера (grill Q11/рамка карты). Все носители подписи (таймлайн-строки, детальная, поиск, снимок мира, чип окна) уже идут через неё — меняются только их входные типы. `split_date_era` обобщается до координат (`split_coord_era` тем же телом), QML-строки `startIso/endIso`: ISO, когда координата представима датой (месяц ≤ 12, день ≤ реального григорианского месяца, месяц/день в 1-значной и 2-значной границах), иначе — кодек-строка `encode_coord` (QML их не парсит — контракт наблюдателя, grill Q21); эра остаётся отдельным булевым свойством.

### D6. Диалоговые прокси и фиктивный ISO-слот переезжают сейчас
`_DateProxy` обоих диалогов: `date() -> GameCoord | None`, `setDate(coord | None)`; зовущие — только тесты (~6 файлов: `test_dialogs`, `test_widget_gaps`, `test_entity_card_island`, `test_event_dialog_island`, `tests/ui/helpers.py`, `test_e2e_dialog_save_failures`) — мигрируют в этом же изменении, «потом в C6» не копим (grill Q10, Q17). `WorldSnapshotViewModel.setDateIso` удаляется вместе с двумя его тестами: QML его не вызывает, ISO-контракт в обратную сторону фиктивен. Попапы (`ThemeDatePopup`, `_DateWindowPopup._CustomCalendar`) не трогаются: `QCalendarWidget` продолжает эмитировать `(date, era)` — `set_dates`/`set_date` приводят дату к координате (D4), поэтому C3a и C3b независимы.

### D7. XLSX: разбор прежний, невалидное сдвигается с видимой строкой отчёта
`xlsx_schema` возвращает пары `(дата, era)` как сейчас; на входе в сервис дата приводится к координате, `classify`/`shift_invalid` против активного календаря; сдвиг не молчит — в итоговый отчёт импорта попадает строка «перенесено: лист, строка, поле, старая → новая» (grill Q12: массовый отказ строк сделал бы ISO-импорт в кастомные игры непригодным, рамка карты «импорт без переключения принимает ISO всегда»). Призрачные границы импорта (`era_key` по min/max) — от координат. Автосозданные цели связей получают уже сдвинутые даты (общий маршрут до записи).

### D8. Порядок старта: ремонт координат → сдвиг → сверка ключей
`CalendarSettingsService.load_and_apply` остаётся точкой загрузки календаря (C2); после него, до репозиториев/VM/`load_events` — новый обход шести таблиц: 1) нечитаемые тексты coord-колонок обнуляются с логом (D3); 2) координаты (из резолвера, с эрами) прогоняются через `build_shift_report`, невалидные сдвигаются и записываются тем же маршрутизированным `assign_coord` (D3), переносы — в лог; 3) `reconcile_era_keys` пересчитывает ключи от разрешённых координат (текст сверки C2 сохраняется, тип входа — координата). Всё идемпотентно: на стандартной игре обход — no-op (date-колонки — валидные григорианские месячные координаты, coord-колонки пусты). Мастер C4 — то же применение, только с экраном отчёта вместо лога и боевым вызовом при смене настройки; `apply_to_records` дополняется переносом хранилищ: применение кастома заполняет coord-колонки (date не трогает), применение пресета переносит в date (со сдвигом при необходимости) и очищает coord (grill Q24).

### D9. Вьюмодели-переносчики — только типы
Пары `(date, is_bc)` становятся `(GameCoord, is_bc)` механически: поля и слоты `set_dates`/`set_date`, валидация `valid`=event `end ≥ start` через `cmp_era_dates` (unchanged), `timeline_rows._bound_key`/окно/сортировка — `era_key` от координат, снимок мира (`wiring.on_snapshot_requested`) — ключ от координаты, `timeline_date_popup`: сравнение обратного тапа — уже `cmp_era_dates` от координатных пар, предзаполнение невалидной координатой — clamp `shift_invalid` только для показа, запись не трогается (grill Q19). `QDate`-конверсии остаются внутри виджетов-попапов до C3b.

## Risks / Trade-offs

- [Двуххранилищность записи — класс рассинхрона] → единственный писатель/читатель — резолвер D3; ветвление по признаку заполненности, а не по «текущему календарю», поэтому ручная правка настроек не может направить запись в нечитаемое хранилище; date-колонки при кастоме не обновляются никогда — врать нечему.
- [Приведение `date` → `MonthDay` переживает баги валидации] → несуществующий день (31.04 и т.п.) отсекает `classify`/`InvalidGameDateError` ровно как сейчас отсекает SQLite для `date`; приведение — синтаксис, не нормализация.
- [Сдвиг на старте молча правит записи] → видим через лог (перенос = строка в логе) и через то же применение с отчётом в C4; идемпотентность проверяется тестом «два старта — второй не двигает».
- [`Iso`-строки QML перестают быть ISO для вставных дней] → QML поле непроверяемое и нигде не парсится (спайк + карта потоков); наблюдатель различает род по `startDisplay`, дублирующее булево эры не меняется.
- [~30 затронутых файлов с тестами — близко к порогу «крупный PR >20 файлов»] → коммиты делятся по границе «домен + хранение + сервисы» / «presentation + прокси + xlsx-отчёт» (прецедент R3, как в C2).
- [Даунгрейд приложения до C3a на игре с кастомом] → потеря отображения кастома (старые date-колонки — снимок эпохи до переключения) — ожидание согласовано: кастомных боевым игр ещё нет, стандартные игры при даунгрейде не теряют ничего, новые колонки SQLite игнорируются прежней схемой прочтения.

## Migration Plan

Схема: `ALTER TABLE … ADD COLUMN start_coord/end_coord TEXT` для шести таблиц в `_MIGRATIONS` (`init_db()`) — идемпотентно по `PRAGMA table_info`. Данные: переноса нет — пустые coord-колонки означают «живём в date-колонках»; старт-обход D8 при активном пресете — no-op. Запись в CHANGELOG «миграция через init_db()» по конвенции репозитория. Откат изменения — revert коммитов: старые версии приложения корректно читают базы с лишними колонками.

## Open Questions

- Имена/расположение резолвера (`coord_codec`-модуль инфраструктуры vs соседство с моделями) — вкус реализации, на контракты не влияет.
- Итоговые русские фразы строк отчёта xlsx-переноса и логов — правятся на taste при реализации.
