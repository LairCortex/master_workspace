# Design: fix-silent-dialog-save-debt

## Context

Долг W5 (дорожная карта, строки про Q2.5): диалог-путь сохранения молчит при сбое. Состав долга (проверено по коду):

- `EventService.create_event_with_relations` (`event_service.py:174-197`) и `update_event_with_relations` (:218-246): `except Exception: rollback; return None`.
- `EntityService.update_entity_with_relations` (`entity_service.py:124-167`): то же.
- `wiring.on_saved` (:265-284), `wiring.on_event_updated` (:349-374), `wiring.on_entity_saved` (:559-573): вызов сервисиного метода, результат не проверяется, exceptions не перехватываются — ошибка уплывает в нишу из-за того, что `asyncio`-таск никто не ждёт.
- Одиночное создание сущности из «+»-меню: `on_entity_saved` внутри `on_add_entity` (:311-323) — `except Exception: rollback`, молча.
- Уже честные пути-образцы: `on_event_dates_moved` (:390-426) — rollback, перезагрузка ленты, ровно один `QMessageBox.critical`; `on_event_create_at` (:432-465) — зеркало того же; вложенное создание во всплывающем окне `_open_related_create_dialog` (:632-638) — свой QMessageBox.
- Вызывающие у трёх `*_with_relations` один — `wiring`; менять сигнатуры ради одного потребителя незачем.

## Goals / Non-Goals

**Goals:**
- Ни один путь сохранения из UI не молчит при сбое.
- Поведение успеха bit-for-bit прежнее (тесты успеха не переписывать под уведомление).
- Семантика сбоя единая: rollback → перезагрузка отображений → ровно одно модальное сообщение.

**Non-Goals:**
- «Не закрывать диалог при провале save» (диалоги трогать запрещено: их переезд в QML заблокирован решением Q2.5, правим только отчётность). Диалог и при новом поведении закрывается сразу — данные этой правки пользователь теряет; фиксируется как осознанный минимум, ровно как в drag-пути.
- `delete_event_type` → `False` и прочие булевы возвраты сервисов — вне долга (UI-вызывающие их уже обрабатывают).
- Удаление сущностей, xlsx-импорт, character-sheet-пути — вне долга.

## Decisions

### D1. Сервисы пробрасывают, wiring показывает

Три метода `*_with_relations`: `rollback` остаётся в сервисе (он владелец сессии-паттерна), далее `raise` вместо `return None`. Возвращаемый тип по успеху не меняется (объект события/сущности). Причина: `None` нельзя отличить от «событие не найдено» без второго канала, а try-обёртка над raise в одном вызывающем месте — это вся нужная диспетчеризация. Альтернатива «сервис бросает без rollback» отклонена: rollback рядом с точкой сбоя уже есть везде, разносить его по handler'ам — регресс риска (забыть).
В `update_event_with_relations` событие может отсутствует (`get_event` → None → `refresh(None)` → исключение): после D1 это станет наблюдаемым `AttributeError`. Минимальная честность: перед refresh проверить `updated_event is None` и бросить осмысленное исключение (`KeyError` с id запрещён стилем для бизнес-ошибок; свой `EventNotFoundError` в `app/domain/errors`? — нет: единый generic не нужен, поднимаем `ValueError(f"событие {event_id} не найдено")`). Формулировку текста сообщения смотрит wiring-месседж.

### D2. Единая форма notification в трёх handler'ах

Каждый из четырёх handler'ов (`on_saved`, `on_event_updated`, `on_entity_saved`-оба) оборачивает запись в `try/except Exception` (с `# noqa: BLE001`, как в drag-пути): `rollback` в сервисе уже выполнен; handler перезагружает то, что показывал бы успех (лента через `_reload_timeline()`; в edit-пути ещё detail-панель после перезагрузки — но без показa «нового» объекта), затем `QMessageBox.critical(window, "Ошибка", f"Не удалось сохранить…: {exc}")`. Текст префикса по пути: «события» / «события с связями» — точнее:
- create/edit события: «Не удалось сохранить событие: {exc}»
- entity update: «Не удалось сохранить сущность: {exc}»
- entity solo-create: «Не удалось создать сущность: {exc}»
Порядок «перезагрузка → затем messagebox» — как в drag-пути (модалка блокирует loop, под неё остаётся уже консистентная лента).

### D3. Одиночное создание сущности: тот же handler-паттерн

`on_entity_saved` внутри `on_add_entity` (:311-323): голый except заменяется на rollback (уже есть) + `QMessageBox.critical` + никакого частичного refresh не требуется (объект не создавался, лента сущностей не показывается на шкале). Внешний `except` конструктора/поповера (:327-328) — оставить с rollback, но добавить лог: это не путь сохранения данных, а путь «диалог не открылся» — модалкой не дёргаем, чтобы не плодить двойные сообщения при каскаде. Комментарий фиксирует разницу.

### D4. Тесты первыми (TDD)

- Сервисные юниты: `create_event_with_relations` / `update_event_with_relations` / `update_entity_with_relations` — при падающем `commit` (AsyncMock) исключение летит наружу, `rollback` вызван ровно один. Тест «событие не найдено» для update — `ValueError`.
- Wiring-тесты (qtbot + monkeypatch `QMessageBox.critical` spy, фейковый сервис с `side_effect=RuntimeError`): четыре пути — модалка ровно один раз, текст с причиной, таск не тонет; success-пути существующих тестов (`test_e2e_events`, `test_e2e_crud`, `test_dialogs`) не меняются.
- Тест «сессия рабоча после сбоя»: после провалившегося сохранения второе — успешное (in-memory fixture conftest).

## Risks / Trade-offs

- [Пользователь по-прежнему теряет правки: диалог закрылся до результата] — осознанный минимум Q8.(а); полный фикс требует(async save в диалоге) и отложен до решения по переезду диалогов.
- [`raise` меняет контракт `*_with_relations`] — вызывающих ровно три, все в wiring и все правятся этим же change; сторонних потребителей нет (проверено grep'ом).
- [QMessageBox внутри _spawn-таска блокирует сессионный лок до закрытия модалки] — принято: drag-путь живёт с этим, окно модальное, параллельных сохранений пользователь сделать не может.
