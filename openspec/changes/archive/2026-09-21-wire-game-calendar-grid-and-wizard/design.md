# Design: wire-game-calendar-grid-and-wizard

## Context

Дерево решений зафиксировано grill-сессией 2026-09-20 (куски C3b + C4 одним изменением — решение пользователя). Мотивация — в proposal.md; требования — в дельтах specs. Текущее состояние: дата приложения — координата игрового календаря (`GameCoord`, кодек, coord-колонки — C3a); попапы рисуют григорианский `QCalendarWidget` с подменой картинки через `popup_prefill_date`; сервис `CalendarSettingsService` умеет загрузку, обход-сдвиг, сверку ключей и `apply_to_records(preview/apply)`; вторая половина дизайна (сохранение) намеренно оставлена мастеру.

Ключевые ограничения: QML-островки не трогаем (попапы — узаконенное widgets-исключение, spec qml-shell); схема БД не меняется (только ключи `game_settings`); лаунчер синхронный и базу не открывает; комментарии в коде — только на английском (detekt-подобное правило repo не вводит, но принятый стиль домена — англоязычные докстринги); гейт 100%-покрытия строк.

## Goals / Non-Goals

**Goals:**
- Один переиспользуемый widgets-виджет сетки, из которого растут: оба попапа даты, живой предпросмотр мастера.
- Контракт «координата внутрь / координата наружу» вместо `QDate`, с удалением прищура предзаполнения.
- Мастер: экраны-ступени с черновиком и применением через отчёт; точки входа (меню + первый вход новой игры).
- Заодно — удаление legacy-прокси `date()/setDate(QDate)` диалогов события/карточки (забор части инвентаря C6).

**Non-Goals:**
- e2e-приёмка кастомного календаря и полный перенос оставшихся QDate-прокси — C6.
- Праздники, астрономия, время суток, фильтры по дням недели — вне карты.
- Перевод мастера на QML, редактирование имён недель пресета.

## Decisions

### D1. `GameCalendarGrid`: композиция QWidget + QGridLayout именованных кнопок

Виджет в `app/presentation/views/calendar_grid.py`: панель навигации (наследует нынешнюю панель `_CustomCalendar`: ◀, комбо месяцев, спин года 1…9999, ▶) + шапка имён недели (`GameCalendarDayName`) + сетка кнопок-ячеек (`GameCalendarCell`, свойство `selected`) + строки-плашки (`GameCalendarIntercalaryChip`) после месяца-хозяина. API: `refresh()` (перечитать активный календарь), `set_selection(coord | None, is_bc | None)`, `selection() -> GameCoord | None`, `is_bc()/set_era()`, сигналы `day_selected(GameCoord)`, `page_changed(int, int)`; режимы `show_era: bool`, `interactive: bool` для предпросмотра мастера.
**Почему не `QTableView`+делегат**: кликабельность плашек, точечное тематизирование именованием классов и кликабельные widget-тесты дешевле на composited-виджетах; делегат потребовал бы ручной hit-geometry для плашек. **Почему не наследовать `QCalendarWidget`**: виджет принципиально не умеет ни длину недели, ни число месяцев (подтверждено спайком).

### D2. Имена недель пресета — presentation-константа

`STANDARD_WEEK_NAMES` (7 русских имён, Пн…Вс) живёт в `date_utils`/грид-модуле, НЕ в домене (домен не локализует — принцип C0). У кастомного календаря имена берутся из `spec.week_names`. Первый столбец — индекс 0 (`weekday()==0` = понедельник у пресета, `week_names[0]` — у кастомного); это фиксирует Monday-first вместо прежнего локали-зависимого поведения QCalendarWidget (принято grill'ом, приложение русскоязычное).

### D3. Координатный контракт попапов

`ThemeDatePopup.date_selected` отдаёт `(GameCoord, is_bc)`, `_DateWindowPopup.range_applied` — пары координат; вход предзаполнения принимает `GameCoord | date | (coord, era)` через `as_game_coord`/`split_date_era`. `popup_prefill_date` и `_display_day_of_intercalary` удаляются: grid рисует любую валидную координату сам, а невалидные сохранённые уже сдвинуты стартовым обходом. Механика двух тапок и низкоэкранный откат остаются слово-в-слово, меняется только тип носителя (`QDate` → `GameCoord`).

### D4. Тема: именованные селекторы вместо `QCalendarWidget`

Из `compile_popup_qss` удаляются правила `QCalendarWidget { ... } / QToolButton / QAbstractItemView`; добавляются правила `GameCalendarGrid`, `GameCalendarCell` (+ `[selected="true"]`, `:hover`), `GameCalendarIntercalaryChip`, `GameCalendarDayName`. Тест темы проверяет наличие четырёх имён и отсутствие строки `QCalendarWidget`; style-facing-статус имён комментируется по образцу `_DateWindowPopup`.

### D5. Мастер — widgets-диалог со стеком страниц + viewmodel

`CalendarWizardDialog` (`views/calendar_wizard.py`): `QStackedWidget` экранов выбор/неделя/месяцы/вставные/предпросмотр (+ отчёт поверх), справа — панель предпросмотра `GameCalendarGrid(interactive=False, show_era=False)`. `CalendarWizardViewModel` (`viewmodels/calendar_wizard_viewmodel.py`): frozen-State (`step`, частичная форма, `can_advance`, `problems: tuple[SpecProblem, ...]`, отчёт), методы-интенты (`choose_kind`, `edit_week_length`, `edit_month`, `move_rule`, `try_advance`, `apply`). Валидация каждой ступени — `validate()` ядра на частичной спеке (непройденные ступени = дефолты), русские фразы — словарь `_CODE_PHRASES` из `calendar_warnings` (дополняется сценарно, общий текст уже есть). Диалог не содержит бизнес-логики (правило review-культуры repo).

### D6. Черновик: значение-спека + индекс ступени

Новый ключ `game_calendar_draft`: JSON `{"v":1, "spec": <то же тело, что у custom-значения game_calendar>, "stage": "months"}` — переиспользует `encode_calendar`/`decode_calendar` для тела спеки; кодирование инвентарит. Пройденная ступень = записать собранную спеку целиком (непройденные ступени в ней — дефолты: 7 имён недели → григорианские имена и т.д.), `stage` = следующая незакрытая. Продолжение: старт с `stage`, предполнение из `spec`. Нечитаемый/невалидный черновик = «черновика нет» (лог, без окна). Флаг `calendar_wizard_seen`: `"0"/"1"`; проставляется ТОЛЬКО веткой первого входа (крест/выбор без брошенного черновика → `"1"`; закрытие с живым черновиком → остаётся `"0"`). Из меню флаг не трогается.

### D7. Посев новой игры — в `init_db` по факту свежего создания схемы

`init_db` уже различает «базу создаём» (таблиц не было) и «базу мигрируем»; в первой ветке сеются `game_calendar` (standard v1) и `calendar_wizard_seen="0"` по образцу `_seed_default_event_types`. **Почему не в синхронном `create_game`**: он создаёт пустой файл без открытия БД (ограничение лаунчера из spike'а); альтернатива «свой sqlite-коннект в GameDataManager» добавила бы вторую реализацию записи в обход async-слоя. Игра, созданная между C2 и этим изменением, считается старой (без мастера) — принято.

### D8. Первый вход — модалка внутри `start()` до `show()`

В `Application.start()` после обхода записей и сборки VM, до `MainWindow.show()`: если `calendar_wizard_seen == "0"` — вложенный `QDialog.exec()` мастера (прецедент — лаунчер в qasync-петле). Ветка «крест» = apply-путь пресета (для новой пустой игры отчёт пуст, транзакция тривиальна); если черновик заведён — флаг не ставится, игрок выходит в окно на пресете. Ошибки применения — окно с причиной, мастер остаётся.

### D9. `promote_draft` в сервисе — одна транзакция поверх применения

`CalendarSettingsService.promote_draft(session, calendar, report)`: применяет `apply_to_calendar`-ветку (dry_run=False — та же атомарная транзакция C2: сдвиги+ключи+переезд хранилищ), затем в ЭТОЙ же транзакции пишет `game_calendar` (overwrite — лечит и повреждённую строку), удаляет `game_calendar_draft`, ставит `calendar_wizard_seen="1"` если применение закрывает первый вход; после commit — `set_current_calendar(calendar)` и `session.expire_all()`. Вьюмодель мастера вызывает `apply_to_records(dry_run=True)` для отчёта, экран отчёта подтверждает, затем одна транзакция promote. **Почему в сервисе, а не viewmodel'е**: атомарность записи настройки с переносом записей — требование storage-контракта (spec game-calendar-settings), и вьюмодель остаётся Qt-транспортной прослойкой.

### D10. Имена в отчёте — из уже обходящихся строк

`ShiftReport` остаётся доменным (таблица, id, поле, координаты, причина) — не пачкаем домен подписями отображения. Вьюмодель мастера строит подписи, сопоставляя `(table, row_id)` с ORM-строками того же обхода `apply_to_records(dry_run=True)` (расширить возврат сервисной проверки списком `(row, resolved)`, который `_collect_checks` уже возвращает, или отдельным запросом имён перед показом). Подпись: название события/сущности, иначе `<русское имя таблицы> №<id>`. Поле — «начало/конец», даты — `format_game_date(old/new, is_bc)`.

### D11. Распространение применения — существующая цепочка перезагрузки показа

После успешного применения сигнал viewmodel → `Application`: `timeline_vm.load_events()` (перерисовка ленты+чипа),пересборка открытых таблиц датированных сущностей (table host), детальной панели — если открыта. Попапы, подписи карточек/диалогов читают календарь при следующем открытии (`refresh()` grid'а при `open_at`, как нынешний `refresh_month_names`). Мастер модальный — открытых окон дат нет, partial-обновления не нужны.

### D12. Удаление legacy-прокси диалогов

`date()/setDate(QDate(...))`-прокси окон события и карточки удаляются; тесты (включая `clicked.emit(QDate)` островов, helpers ui-тестов) переходят на координатные пары — QML-мосты и VM уже понимают координаты с C3a. Оставшийся в C6 инвентарь QDate-прокси после этого тает до транзитных литералов.

## Risks / Trade-offs

- [Объём >20 файлов в одном изменении] → решение пользователя; задачи сгруппированы по под-кускам (сначала grid+попапы+тема+тесты, затем мастер, затем входы+посев), каждая группа зелёная до следующей.
- [Массовый перенос тестов с `QDate` может сломать скрытые допущения островов] → helpers (`tests/ui/helpers.py`) и `test_timeline_island`/`test_theme_date_popup` правятся первыми в группе сетки; прогон всего `python -m pytest` после каждой группы.
- [Monday-first у пресета — видимое отличие от локали-зависимого QCalendarWidget] → сознательная фиксация grill'ом (Q4 сессии); фиксируется тестом сетки.
- [Вложенный `exec()` в `start()` может конфликтовать с qasync-расписанием] → прецедент лаунчера в той же петле; тест первого входа прогоняется через `qtbot` (паттерн тестов лаунчера).
- [Применение при огромном числе записей — длинная транзакция] → принимается: тот же профиль уже у C2-обхода; откат по ошибке целиком.
- [Крест первого входа = пресет мог не быть задуман пользователем] → поведение описано в spec/подсказке мастера; черновик не даёт потерять недоделанную сборку.

## Migration Plan

Схемных миграций нет: новые ключи `game_settings` идемпотентны, старые версии приложения их молча игнорируют (читают только известные ключи) — откат приложения безопасен. Игры, открытые впервые этой версией, получают посев; остальное поведение включается только при действиях пользователя в мастере. Применение откатывается единой транзакцией без следов.
