## Context

C0/C1 закрыты: в `app/domain/game_calendar.py` живут `GameCalendar` (протокол), `StandardCalendar`, `CustomCalendar`, `validate`, accessor `current_calendar()/set_current_calendar()/reset_current_calendar()`, чистая политика сдвига и форма `ShiftReport`. `era_key` — диспетчер на активный календарь, который никем не устанавливается (всегда дефолтный пресет). Настройки месяцев — отдельный ключ `custom_months` и процесс-глобал `_current_months` в `presentation/utils/date_utils.py`; читаются «в момент рисования», ставятся в `Application.start()` (загрузка `main.py:792`) и в цепочке сохранения диалога (`main.py:811-837`). Ключи `start_key/end_key` синхронизирует ORM-хук `_sync_era_keys`, идемпотентный SQL-бэкфилл на `julianday/strftime` — вторая копия григорианской формулы. Дерево решений зафиксировано grill-сессией 2026-09-20 (вопросы Q1–Q18); требования — specs этого изменения.

## Goals / Non-Goals

**Goals:**
- Один источник календарной правды: ключ `game_calendar` → активный календарь → имена и ключи; процесс-глобалов имён не остаётся.
- Календарь переживает перезапуск и переключение игры; сломанное значение не роняет игру и не молчит.
- Хранилище ключей согласовано с активным календарём без второй формулы.
- Готовый механизм применения календаря к записям — боевой вызов появится в C4.

**Non-Goals:**
- UI настройки календаря (мастер C4; в C2 настройки только читаются/мигрируют).
- Собственная сетка календаря, подпись вставного дня, неделя пресета «Стандартный», XLSX-парсинг (C3/C5).
- Отпечаток применённой спеки / детектор «календарь сменился из-под базы».

## Decisions

### D1. Схема хранения и кодек в домене
Ключ `game_calendar`, JSON: `{"v": 1, "kind": "standard", "month_names": {"3": "Медвежарь"}}` либо `{"v": 1, "kind": "custom", "months": [{"name","length"}], "week_names": [...], "intercalary": [{"name","after_month"}]}` — имена полей один-в-один с `CalendarSpec` (альтернатива — вложенность `"custom": {...}` — отклонена: лишний уровень без выигрыша). Кодек `encode_calendar(calendar) -> str` / `decode_calendar(raw) -> CalendarDecoded | CalendarCorrupted(reasons)` — в `game_calendar.py` как чистые функции (доменный тип ⟷ его хранимое представление; альтернатива «кодек в инфраструктуре» отклонена: он оперирует доменными типами, storage о них не должен знать). `StandardCalendar` хранит `month_names` (по умолчанию — текущие `DEFAULT_MONTHS`, переезжают в домен из `date_utils`); у `CustomCalendar` имена — из спеки. Неделя пресета не заводим: `render_calendar_year` для пресета остаётся `TypeError` до C3.

### D2. `CalendarSettingsService` вместо роста `main.py`
`app/application/services/calendar_settings_service.py`: `load_and_apply(session) -> LoadOutcome` (чтение+миграция+установка+предупреждение-флаг), `save(calendar)` (для C4), `apply_to_records(session, calendar, dry_run)` — обход шести `_ERA_TABLES`. `main.py` в `start()` вызывает `load_and_apply` на месте `_load_month_settings` (после `init_db`, до VM и `load_events`), в `shutdown()` — `reset_current_calendar()`. Алтернатива (три async-метода в `Application`, паттерн LLM-настроек) отклонена: мастер C4 повторяет загрузку/сохранение, ему нужен тот же вызываемый модуль, и тесты сервиса пишутся без Qt.

### D3. Миграция `custom_months` — внутри загрузки
Порядок в `load_and_apply`: прочитать оба ключа → нет `game_calendar`+есть читаемый `custom_months` → равен григорианским именам? нет записи, удалить старый : записать `month_names`-ключ → удалить старый; битый `custom_months` → удалить, логовать. Оба ключа → новый побеждает, старый удалить. Однократность обеспечивает сам факт удаления старого ключа (альтернатива «флаг миграции» отклонена: лишний ключ в таблице настроек).

### D4. Битое значение: пресет + предупреждение, запись цела
`decode` возвращает причину: `corrupt_json`, `unknown_version`, список `SpecProblem`; невалидный спек строится через исключение `CustomCalendar` (конструктор — валидационные ворота C0). `main.py` показывает одно `QMessageBox.warning` за открытие; маппинг кодов → русские фразы живёт в presentation (словарь `calendar warning`), неизвестный код/версия → общая фраза (домен не локализует — принцип C0). Битая запись не трогается (починка — мастер C4; переписывание стёрло бы данные ручной правки БД). Предупреждение отделено от загрузки: сервис возвращает результат, окно показывает Application — сервис остаётся тестируемым без Qt (альтернатива «сервис сам показывает модалку» отклонена).

### D5. Пересчёт ключей: python, идемпотентно, диффом
На старте, после установки календаря: `reconcile_era_keys(session)` — по шести таблицам выбираются `(id, start_date, start_bc, start_key, end_date, end_bc, end_key, ...)`, новый ключ считается `era_key(...)`, запись мутируется только при расхождении; один `commit()`. Побочный выигрыш: полностью заменяет SQL-бэкфилл — `_backfill_era_keys` удаляется из `migrations.py` вместе с формулой на `julianday/strftime` (единственная формула — активный календарь; C1-риск «две копии формулы» закрывается). ORM-хук `_sync_era_keys` не меняется: новые записи получают корректный ключ при записи. Стоимость: select+арифметика по всем строкам каждого запуска (закрытая формула, тысячи строк ≈ миллисекунды; отпечаток спеки отклонён как лишний синхронизируемый факт — grill Q13).

### D6. `apply_calendar_migration` — режим через флаг
Метод `CalendarSettingsService.apply_to_records(session, calendar, dry_run=True) -> ShiftReport`: координаты записей собираются в `ShiftCheck`-ы (таблица, id, поле, `MonthDay`/`IntercalaryDay`, эра) и отдаются доменному `build_shift_report`; в режиме применения координаты заменяются на `new` и ключи пересчитываются, commit один — откат на любой ошибке. Координата вставного дня в хранилище пока невыразима (колонки дат — григорианский `Date`), но в C2 ни один календарь из приложения вставных дней не содержит, поэтому обход оперирует только `MonthDay`; таблица координат вставных дней — C3+. Боевых вызовов в C2 нет; контракт фиксируется тестами сервиса (grill Q8/Q14).

### D7. Имена: протокол + делегат вместо глобала
В протоколе `GameCalendar` — свойство `month_names: Mapping[int, str]` (у `CustomCalendar` — `{i+1: spec months[i].name}`, у `StandardCalendar` — с переопределением в конструкторе). `date_utils` теряет `_current_months`, `set/get_custom_months`, `months_to_json/months_from_json`, `SETTINGS_KEY`; `month_name(month)` и `format_game_date` остаются и читают `current_calendar().month_names` (подпись `dd MonthName yyyy[ г. до н.э.]` не меняется). `theme_date_popup` (комбо месяцев) — те же вызовы `month_name`/`get`-замена на делегат/`current_calendar().month_names`. Подпись ремоделинга таймлайна (`timeline_viewmodel.py:268`) — сам объект `current_calendar()` (неизменяемые календари, сравнение по идентичности; альтернатива «отпечаток spec» отклонена: дороже и дублирует идентичность).

### D8. Удаление UI месяца-диалога
Целиком удалляются: `views/month_settings_dialog.py`, `viewmodels/month_settings_view_model.py`, `qml/MonthSettingsRoot.qml`, пункт и QAction «Названия месяцев…», сигнал `month_settings_requested`, методы `_load/_save/_on_month_settings`. В меню «Настройки» остаётся тема; до C4 вход в настройки календаря отсутствует — осознанный зазор (grill Q11).

## Risks / Trade-offs

- [Пересчёт на каждом старте — О(n)] → только select+арифметика, запись при расхождении; порог «заметно дорого» не достигнут на объёмах сценарных игр; точечный пересчёт при редактировании уже делает ORM-хук.
- [Механизм `apply_to_records` в C2 без боевых вызовов — неиспользуемый код до C4] → контракт зафиксирован тестами; требование «мастер C4 вызывает этот механизм» уже стоит в specs (`game-calendar-settings`, «Применение календаря к записям игры»), так что C4 не сможет его потерять.
- [Удаление SQL-бэкфилла: старые базы с пустыми ключами] → `reconcile_era_keys` перекрывает его полностью (тот же эффект через `era_key`), включая заполнение NULL-ключей до-era-эпохи.
- [Двойной смысл стандартного ключа: `{3:"Январь"} ≠ «нет записи» только побайтово] → сравнение с `DEFAULT_MONTHS` по значению словаря — детерминировано, покрыто тестом D3-сценария «эквивалент дефолту».
- [~25 затронутых файлов с тестами — близко к порогу «крупный PR >20 файлов»] → один change остаётся, но коммиты делятся по границе «домен+сервис+миграции» / «presentation+удаление UI» — по прецеденту R3.
- [Глобал удалён, тесты в 13 файлах его дёргают] → все обращения мигрируют в этом же изменении (`set_current_calendar(StandardCalendar(month_names=...))` для кейсов имен); зелёный pytest — гейт.

## Migration Plan

Однократная прикладная миграция значения `custom_months → game_calendar` происходит в `start()` (D3) — отдельного скрипта нет; даунгрейд приложения на версию до C2: потеряется переопределение имён (старый ключ удалён) — данные записей не повреждаются (координаты и ключи стандартны). Резервная копия `game.db.bak` перед первым открытием уже гарантирована механикой date-eras. Откат изменения в коде — обычный revert: схема БД не менялась.

## Open Questions

- Итоговый список русских фраз для предупреждений (по кодам `SpecProblem`) — правится на taste при реализации, наcontract не влияет.
- Формат `month_names` при пустом словаре (`{}` vs отсутствие поля) — нормализуется кодек-реализацией в «нет поля», round-trip-тест фиксирует.
