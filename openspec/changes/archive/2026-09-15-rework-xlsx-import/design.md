## Context

См. `proposal.md — Why` и `specs/xlsx-import/spec.md` (контракт поведения). Текущее состояние, важное для решения:

- Импорт: `XlsxImportService` читает только `wb.active`, маппит строки на `EventService.create_event` / `EntityService.create_entity`; ни сервис, ни wiring (`_do_import`) не вызывают `session.commit()` — записи держатся в единном пожизненном `AsyncSession` и «приживаются» чужими коммитами.
- Связи в БД: 13 M2M-ассоциаций (`event_character` и т.п., составной PK, CASCADE). `EventService.update_event_with_relations` умеет только полную замену набора (отвязывает отсутствующих) — семантике импорта («только добавлять») не соответствует.
- Имена сущностей не уникальны в схеме — неоднозначность выясняется только запросом к базе.
- Диалог: QML-остров `XlsxImportDialog` + `XlsxImportViewModel` (синхронный VM), запуск через `ApplicationWiring._run_import` под общим `asyncio.Lock`.
- Бандлинг: `nri_manager.spec` уже includ'ит `docs/` в бандл (по образцу показывается README/CHANGELOG) — тот же механизм подходит для ресурса-шаблона.

## Goals / Non-Goals

**Goals:**

- Один сервис-парсер с декларативным реестром листов/колонок; единый цикл analyze → plan → apply.
- Детерминированная семантика слияния (upsert/merge/автосоздание) без изменения схемы БД и без alembic.
- Атомарность: один commit успеха / rollback сбоя, без влияния на остальные потоки (импорт под `_session_lock`).
- Диалог с состояниями: выбор → пред-анализ (пул проблем) → подтверждение → прогресс → отчёт, в существующем QML-острове.

**Non-Goals:**

- Экспорт в xlsx, импорт `ratings`-сущностей, связей событие↔событие, поддержка `.xls`.
- Изменение схемы БД, переписывание mention-маркеров при импорте (остаётся «create не переписывает»).
- Отвязывание связей импортом, удаление сущностей импортом.

## Decisions

### D1. Декларативный реестр листов и колонок

Модуль `xlsx_schema.py` (рядом с сервисом): для каждого из пяти типов — имя листа, RU-колонки с EN-алиасами, допустимые колонки связей. Парсер, подсказка диалога и генератор описания колонок читают один реестр — исключается расхождение «подсказка ≠ парсер» (историческая болячка FORMAT_TEXTS). Альтернатива (жёсткие словари в теле парсера, как сейчас) отклонена: три потребителя одной схемы.

### D2. План-модель вместо немедленного применения

`analyze_file(path) -> ImportPlan`: one-shot чтение workbook (`read_only, data_only`), построение «запланированных операций» на строку. Один и тот же план используется для показа пула проблем и для применения — повторный `import_file` не перечитывает файл (нет окошка «файл изменился между анализом и импортом» при переиспользовании объекта плана; если пользователь сменил файл — план пересобирается). Фатальные ошибки плана блокируют применение. Построчные проблемы план хранит как `skipped_rows`.

### D3. Индекс разрешения имён (проход имён перед проходом связей)

До прохода 1 строится `name_index: {(type, lower(name)) -> model | NEW | AMBIGUOUS}` (исходный регистр сохраняется у создаваемых сущностей; совпадение — через `lower()`, согласованно с текущим поиском):

- внутри файла слияние по (тип, имя) уже выполнено парсером (merge строк);
- на каждый тип — однократный SQL-запрос вида `GROUP BY lower(name) HAVING COUNT(*)>1` для множества неоднозначных имён базы (не на строку); строка из файла с уникальным совпадением → upsert, с неоднозначным → создание новой сущности.

Разрешение цели связи: сначала name_index (строки файла приоритетнее — детерминизм), затем база (уникальное совпадение), иначе — автосоздание цели по D5. Альтернатива «разрешать только внутри файла» отклонена: требование ссылаться на уже ведущиеся в мире сущности.

### D4. Применение связей — только добавление, вопреки «replace»-семантике сервисов

Обход плановых связей выполняет `xlsx_import_service` напрямую через ORM-отношения моделей (`event.characters.append(...)` и т.п. для всех 13 M2M, кроме `*_rating`), с дедупликацией. `EventService/EntityService.update_*_with_relations` НЕ переиспользуются — их семантика «полная замена» противоречит контракту «импорт ничего не отвязывает» (см. spec, сценарий «Связи не отвязываются»). Поле `event_type` относится к проходу 1 (события), а не к связям.

### D5. Автосоздание целей: буфер «ghost-сущностей»

Ссылка на несуществующую цель заводит в плане запись ghost с датами ссылающейся строки; при повторных ссылках даты расширяются (min start / max end). В проходе 1 ghost'ы материализуются как обычные сущности (минимально валидные: имя + даты). Тип события из `Тип` аналогично: неизвестный тип материализуется в `event_types` со свободным `color_index` (наименьший незанятый 1..8, при занятых всех — циклический). Каждый ghost и новый тип попадает в `decisions` отчёта.

### D6. Транзакционность и коммит

Сервис получает доступ к сессии (di: репозитории уже держат общую `AsyncSession`; добавляется явная зависимость `session_provider` или `commit/rollback`-колбэк от wiring). `apply_plan(plan)` оборачивается в явную транзакцию: успех — один `commit()`, любое исключение проходов — `rollback()` + проброс ошибки в UI. Импорт идёт под существующим `_session_lock`, конкурентных транзакций на сессии нет. Это устраняет и текущий дефект «нет коммита»: spec-сценарий «данные сохраняются сразу» проверяется перезапуском приложения в E2E.

### D7. Upsert без переименований

Upsert-кандидат находится запросом по точному имени (тип + `lower(name)` как в поиске). Так как совпадение по имени и есть ключ upsert, поле `name` обновляемой сущности фактически неизменно → правило mentions «rewrite только при смене name» не затрагивается, переписывание маркеров импортом не нужно. Пустая ячейка = «не трогать» реализуется фильтром полей на уровне плана (в операцию попадает только непустое значение). Скалярный `Рейтинг` вне 1..5 — проблема строки (не молчаливый clamp).

### D8. Диалог: состояния в одном QML-острове

`XlsxImportViewModel` становится стейт-машиной `idle → analyzing → problems(fatal|rows) → importing → done(report)`: свойства `analysisIssues[]`, `hasFatal`, `canImport`, `report{}`; тексты колонок-подсказок генерируются из реестра D1. `import_requested` разделается на `analyze_requested(path)` и `confirm_import()`. Wiring: `MainWindow` — одно QAction «Импорт из .xlsx…»; `_run_import` один, без параметра типа. Отчёт — панель диалога (не `QMessageBox`, per spec про показ в диалоге).

### D9. Шаблон — статический ресурс + сохранение копией

`resources/import_template.xlsx` коммитится в репозиторий и includ'ится в `nri_manager.spec` (data-files рядом с `docs/`); путь — тем же резолвером «dev vs bundle», что используется для показа README. Кнопка «Скачать шаблон»: `QFileDialog.getSaveFileName` → побайтовое копирование ресурса. Альтернатива (генерация openpyxl на лету) отклонена по решению пользователя: готовый файл проще контролировать и он 1-в-то что тестируется.

## Risks / Trade-offs

- [Изменение семантики: импорт начинает обновлять сущности вместо всегда-создания; старые привычные файлы «вдруг» будут апдейтить] → отчёт явно разделяет создано/обновлено; сценарий upsert покрыт E2E.
- [Фантомные связи при битых `;`-списках (лишние пробелы, пустые сегменты)] → нормализация сегментов (strip, пропуск пустых) в парсере + покрытие тестами.
- [Большой файл: индексация имён по всем типам — 5 групповых запросов, план хранит всё в памяти] → измеримые миры (сотни строк) с запасом; read_only-чтение не держит workbook открытым дольше парсинга.
- [Долгий импорт под `_session_lock` блокирует другие потоки UI] → эквивалентно текущему поведению импорта; прогресс-колбэк сохраняется.
- [Коммит в конце: крах после commit частично не откатываем — но commit ровно один в конце, поэтому «всё или ничего» выполняется структурно] → поддержать нельзя только прерывание пользователем; cancel из интерфейса сознательно не делаем (не-goal).
- [Регистр имён листов/имён сущностей: «иван» ≠ «Иван» при upsert] → upsert и разрешение связей по `lower()` (консистентно с текущим поиском), исходный регистр сохраняется у созданной сущности.

## Migration Plan

1. Реализация сервиса + схемы + тестов (старый диалог живёт до переключения wiring).
2. Переключение wiring/меню на единый импорт, удаление пяти QAction и старых FORMAT_TEXTS.
3. Ресурс шаблона + кнопка скачивания.
4. Обновление E2E-фикстур (`import_sample.xlsx` → формат пяти листов).
Схема БД не меняется, миграций в `init_db()` нет. Откат = revert коммитов изменения (обратно совместимых правок нет).
