## Context

См. `proposal.md` — Why. Текущее состояние, важное для подхода: composition-root `app/main.py` — единственное место сборки конкретных классов; лаунчер синхронный и живёт до qasync-цикла; пер-игровые настройки — ключ/value-таблица `game_settings` через `GameSettingsRepository`; весь сетевой ход — один общий `httpx.AsyncClient` (`app/infrastructure/http/`); листы окон — контракт `modal-sheets` через `ApplicationWiring.open_sheet`; гейка — покрытие 100 % по `app/`, сеть в тестах запрещена (`httpx.MockTransport`). Документация форматов LSS (датасеты, гранты, персонажи) публична; схемные артефакты — статические файлы longstoryshort.app.

## Goals / Non-Goals

**Goals.** Модуль, о котором ядро знает ровно одну вещь — что такой механизм есть. Датасеты и их проверка работают офлайн после загрузки. Импорт файла атомарен: либо набор оказался в хранилище целиком, либо хранилище не менялось.

**Non-Goals.** Не проектируем: таблицы D&D-сущностей (фаза 2), генерацию (фаза 3), QWebEngine/мосты (фаза 4), обновление содержимого датасетов редактором, каталог публикации наборов (его нет у LSS).

## Decisions

1. **Признак модуля — ключ `dnd_module` в `game_settings`** со значением `{"enabled": true, "version": <int>}`. Ключи объявляются в `GameSettingsRepository` (общий реестр ключей ядра остаётся единым источником). Почему не `PRAGMA user_version` и не отдельная таблица: ядро должно читать признак до любой сборки состава одним запросом через штатный репозиторий, а запись признака — обычная операция записи настроек с единой точкой транзакции. Версия — целое число модуля, не версия приложения: живёт медленнее релизов.

2. **Модуль за протоколом ядра.** В ядре (`presentation/modules/protocol.py`) — `Protocol` `GameSystemModule` (`attach(main_window, wiring)`, `detach()`, `enabled`), дефолт — no-op. `main.py` единственный импортирует `app.dd`: читает признак и собирает `DndModule(...)` или no-op-заглушку. «Включить D&D-модуль…» — штатный пункт ядра: сервис ядра пишет признак, после чего composition-root в той же сессии дополняет состав модулем и вызывает `attach` — без перезапуска. Охранка `tests/test_dd_module_isolation.py`: импорт `app.dd` вне `app/dd/` и `app/main.py` запрещён; внутренние слои модуля сторожат существующие тесты слоёв (дерево `app/dd/` подчиняется тем же правилам).

3. **`app/dd/` повторяет слоями ядро**: `domain/` (модель датасета, отчёт проверки), `application/` (`DatasetLibraryService`, `DatasetValidatorService`, `ModuleSettingsService`), `infrastructure/` (хранилище файлов, `LssDatasetsClient` поверх общего клиента), `presentation/` (лист «Датасеты D&D…», модели представлений). Ядро модуля ничего не знает о UI ядра, крепится только через `attach`.

4. **Хранилище**: `~/.nri_manager/datasets/` (новая константа в `infrastructure/paths.py` — единственный источник пути). Один датасет — файл `<dataset_id>.json` + сайдка `<dataset_id>.meta.json` (источник `srd`/`homebrew`, дата импорта, sha256, итог последней проверки). Имя файла выводится из `id` файла после валидации формата имени; коллизии идентификаторов разрешаются только подтверждённой заменой (SRD-файлы защищены). Альтернатива «один индексный файл» отвергнута: атомарность замены и параллельные игры.

5. **Схемы LSS — ресурсы пакета** (`app/dd/resources/schemas/`, фиксированный набор `wizard-dataset.json`, `grant.json`, по-сущностных; отдельный `FORMAT_VERSION`). Почему не загрузка схем сетью: детерминизм офлайн и совпадение с тестами; обновление — явная правка ресурсов релизом после просмотра LSS-changelog. Списки слагов SRD-заклинаний — сетевые артефакты: качаются вместе с SRD, проверка слагов без них пропускается (как и предписано документацией).

6. **Скачивание**: `LssDatasetsClient` (адреса SRD 5.1/5.2 и слагов — константы клиента), ошибки маппятся в русские формулировки по образцу `LlmError`, автоповторов нет — повтор кнопкой листа. Идемпотентность: SRD уже в хранилище — загрузка не запускается автоматически.

7. **Валидатор**: `jsonschema` (draft-07) для формы + собственный обход межполевых проверок из документации LSS; вывод — замораживаемый датакласс отчёта (`issues: tuple[CheckIssue]`, у пункта `code`, `severity`, `path`, RU-текст). Резолвинг ссылок — по всем подключённым к игре наборам (список подключённых к игре наборов от сервиса библиотеки), при проверке вне игры — только по самому файлу. Формулы (`[STR]`, `ceil(...)`, d-нотация) разбираются минимальным вычислителем формул LSS — общим для всех проверок.

8. **Лаунчер (синхронный)**: выбор системы — `QInputDialog.getItem` («Обычная»/«D&D», дефолт «Обычная») перед диалогом имени; при «D&D» создание дописывает `dnd_module`. `list_games()` читает признак синхронно (короткий `sqlite3`-запрос к `game_settings`) и кладёт флаг в `GameInfo`; QML-строка рисует метку «D&D». Метка главного окна — виджет в строке меню, добавляемый модулем при `attach`.

9. **Меню модуля** (для D&D-игры): группа «D&D» — «Датасеты D&D…» (лист через `open_sheet`, контракт `modal-sheets`) и «Выключить D&D-модуль…» (подтверждение → сервис снял признак → UI-секция модуля снимается, метки исчезают). Пункт «Включить D&D-модуль…» — у ядра, в группе «Игра».

11. **Профиль «без модуля»** — переменная окружения `NRI_DISABLE_DD_MODULE=1` (единственная точка чтения — composition-root): при ней `main.py` не импортирует `app/dd` вообще, лаунчер не предлагает «D&D», меню без группы модуля, D&D-игра открывается как обычная с предупреждением (тот же путь, что недоступная версия). Для пользователя выключателя нет — профиль приёмочный/аварийный; покрытие в этом прогоне меряется по составу профиля (профильный конфиг запуска, не правки `exclude_lines`), полный профиль — 100 % по всему `app/` включая `app/dd/`.

12. **Тесты**: валидатор — табличные тесты на каждой проверке (golden-сниппеты против SRD-эталонных фрагментов), хранилище — `tmp_path`, сеть — `httpx.MockTransport`, лист — offscreen по образцу `test_sheet_frame`, round-trip `.nri` с признаком, охранки изоляции. Пакет `jsonschema` — внешняя зависимость, под гейку покрытия не попадает (гейка считает `app/`).

## Risks / Trade-offs

- [LSS меняет схемы/адреса] → версии схем зафиксированы ресурсами; релизный чек-лист сверяется с интеграционным changelog LSS; несовместимая версия формата даёт явную ошибку проверки, а не тихий пропуск.
- [Признак читает ядро, запись ведёт модуль] → ключ объявлен в реестре ключей ядра; модуль пишет его своим сервисом через тот же репозиторий, единая точка транзакции соблюдена.
- [Синхронное чтение признака на каждый список игр] → один запрос per файл, каталоги игр штатно единичные десятки; при росте — кэш по mtime (открытый вопрос ниже).
- [Формулы LSS сложнее мини-вычислителя] → разбор «не вычисляется» = error/warning по категории проверки, молчаливого принятия нет; расширение вычислителя — отдельная правка с тестами.
- [QWebEngine-искушение раньше фазы 4] → в зависимостях и коде QWebEngine отсутствует; спецификация фазы 4 вне этого изменения.

## Migration Plan

Обычный релиз: новых таблиц нет, миграция `migrations.py` не затрагивается; у существующих игр признак отсутствует — они обычные. Откат релиза безопасен: признака/файлов ядро прежней версии не читает, данные игр не менялись. Пользовательский откат — выключение модуля (данные хранилища остаются).
