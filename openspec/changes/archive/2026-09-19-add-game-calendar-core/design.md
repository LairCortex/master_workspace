# Design: add-game-calendar-core

## Context

Сейчас календарь — это `datetime.date` + тонкая надстройка эпох: `app/domain/date_era.py` (`era_key(d, is_bc) = d.toordinal()`, для BC `d.toordinal() − 732·d.year`, годы 1…9999 обеих эр). Порядок запросов идёт только через `start_key/end_key`. Мотивация и рамка куска — `docs/custom-calendar-roadmap.md` (C0) и `proposal — Why`; дерево решений зафиксировано grill-сессией 2026-09-18 (итог — в этой карте и ниже в решениях).

Ограничения, определяющие подход:
- ключ живёт в SQLite INTEGER → 64 бита, это единственный физический предел календаря;
- «Стандартный» пресет математически не выражается фиксированными длинами месяцев (високосные годы);
- ядро до C1 не импортируется приложением → нулевой риск регрессий, но API должно быть готово к вызову из ORM-хуков (по одной координате за раз, без состояния).

## Goals / Non-Goals

**Goals:**
- Один файл-модуль `app/domain/game_calendar.py`: протокол + две реализации + спека + валидация + текстовый предпросмотр.
- Формулы O(1)/O(log #месяцев) на вызов, без обращения к `datetime` в кастомной реализации.
- Полное покрытие требований delta-спека тестами `tests/domain/test_game_calendar.py`.

**Non-Goals:**
- Хранение (TEXT-кодирование координат в колонках), миграция ключей, сдвиг невалидных записей — C1.
- Загрузка настроек из `game_settings`, формат ключа — C2.
- Виджет-сетка, мастер, XLSX-парсер — C3/C4/C5.
- Любые изменения в коде приложения.

## Decisions

### D1. Одна реализация «Стандартного» делегирует действующей функции, а не копирует формулу
`StandardCalendar.to_key/from_key` внутри зовёт `era_key` / `date.fromordinal` из существующих модулей; `weekday` — `datetime.date.weekday()` для григорианской даты-зеркала BC. Альтернатива — независимая копия формулы — откинута: второй экземпляр формулы (а их и так два, см. спайк про SQL-бэкфилл) открывает риск разъезда; делегирование делает совпадение с `era_key` тавтологией, а золото-тест — лишь проверкой обвязки.

### D2. Протокол `GameCalendar`, а не класс-иерархия
`typing.Protocol` с методами `to_key(coord, is_bc) / from_key(key, is_bc) / weekday(coord) -> int | None / month_length(year, month) / is_valid(coord) / spec` (у стандартного — встроенный минимальный spec-вью). Причина: C1/C3 зависят только от протокола; ветвление std/custom — факт реализации, не тип.

### D3. Координата — два замороженных dataclass'а, эра параметром функции
`MonthDay(year, month, day)` | `IntercalaryDay(year, index)` (union `GameCoord`), `is_bc: bool` — аргумент `to_key/from_key`, как сейчас у `era_key(d, is_bc)`. Альтернатива «флаг эры внутри координаты» отклонена: кодирование в колонках — C1, а раздельность уже доказала удобство в ORM-хуках. `index` — позиция в упорядоченном списке правил; стабильность позиции при правках спеки — ответственность C1/C4 (перенос имён правил), не ядра.

### D4. Кастомная арифметика — чистая линейная формула
Спека: `CalendarSpec(months: tuple[MonthSpec(name, length)], week_names: tuple[str, ...], intercalary: tuple[IntercalarySpec(name, after_month), ...])`, все кортежи, frozen. Инварианты построены: `L = Σ месяцев + Σ вставных` — длина года одинакова все годы; префиксные суммы `prefix[m]` считаются один раз при построении календаря и хранятся.
- офсет внутри года обычного дня: `prefix[month−1] + (day−1)`;
- офсет i-го вставного дня: `prefix[after_month] + i_после_этого_месяца + Σ вставных более ранних хозяев` — фактически единая таблица «стартовый офсет каждого вставного дня», тоже префиксная; месячные офсеты резервируют под вставные дни свои промежутки, поэтому формула `from_key` — бинарный поиск по массиву «начало каждого месяца + все вставные дни»;
- ключ н.э.: `1 + (year−1)·L + offset` (эпоха `to_key(1,1,1)=1`);
- ключ до н.э. (зеркало): `to_key(координата как н.э.) − 2L·year`. Строгость: длина года постоянна → скачок между последним днём года и первым днём предыдущего = L < 2L ⇒ монотонность и «всё BC < 0 < всё AD» выполняются (нынешние 732 = 2×366 — частный случай).
Альтернатива «список дней + обход» откинута по асимптотике; «формула с високосным правилом» — по решению Q2 (в карте).

### D5. День недели считается по «месячным» дням
`counter = (year−1)·(L − n_intercalary) + offset_без_вставных` — счётчик обычных дней; `weekday = counter mod W`, якорь: `MonthDay(1,1,1) → 0`; словарь имён — `week_names[counter mod W]`. Вставной день → `None`. Раз вставные дни не попадают в счётчик, дни недели вокруг них не сдвигаются, а годовой сдвиг цикла (`L месячных дней mod W`) возникает сам — «сброс недели» эмулируется длиной месяца, кратной неделе (рамка карты). Якорь в ключ не входит.

### D6. Границы и валидация — минимальная санитация + int64 guard
`validate(spec) -> list[SpecProblem]` (пусто = ок) со всем списком причин: пустое/повторное имя в пределах своего измерения (месяцы, дни недели, вставные дни — отдельно); `length < 1`; `W < 2` или `W ≠ len(week_names)`; месяцы отсутствуют; `after_month ∉ 1…len(months)`; и guard переполнения: `9999·L·2 < 2⁶³`, т.е. `L ≤ (2⁶³−1)//19999` (≈ 4.6·10¹⁴). Год вне `1…9999` — не про валидацию спеки, это ошибка координаты. `to_key/from_key` на невалидном — `InvalidGameDateError(ValueError)`. Молчаливой нормализации нет (Q7). Продуктовых потолков ядро не содержит; спиннеры мастера (C4) ограничат комфорт ввода, а не модель.

### D7. Модуль не хранит глобальное состояние
Календарь — объект, создаваемый из спеки (`CustomCalendar(spec)`, `StandardCalendar()`); никаких процесс-глобалов (урок `_current_months` из спайка; наследник-глобал C2 будет отдельным решением). Конструктор `CustomCalendar` валидирует спеку и бросает `ValueError` с полным списком причин — полувалидный календарь недоступен.

### D8. Предпросмотр — функция модуля, не тестовый хелпер
`render_calendar_year(calendar, year) -> str`: заголовок имён недели, по месяцу — сетка недель (строки длиной W, пустые ячейки до первого дня), после месяца-хозяина — плашка `«— имя —»`; используется тестами (сверка колонок с `weekday`) и будет точкой сверки с сеткой C3. Хранить в модуле, чтобы сравниваемый код был один.

### D9. Тесты: золото + свойства + отбраковка
- золото: `StandardCalendar` vs действующий `era_key` (граничные + случайные, seed фиксирован);
- круговой обход: исчерпывающий по малым спекам и выборочный по спекам-гигантам (месяц 99999 дней — только края);
- свойства (случайные валидные спеки, seed зафиксирован): round-trip, монотонность, непрерывность недели, инвариантность соседей вставного дня, совпадение `render` с `weekday/month_length`;
- табличная отбраковка: по сценарию на каждую причину валидации.
Тесты не трогают Qt и БД — чистый домен, `tests/domain/`.

## Risks / Trade-offs

- Ветвление std/custom в C1/C3 (две реализации) → принято сознательно (обещание «старые игры молча живут»); точка ветвления одна — фабрика по пресету в C1.
- `index` вставного дня нестабилен при правках порядка списка → компенсировано: спека immutable, перестройка только целиком; политика переноса записей — обязанность C1/C4, зафиксировано в D3.
- BC-зеркало при несовпадении длин игрового года с григорианским не «совместимо» с ключами старых игр по величине — но смешивание эр разных календарей внутри одной игры невозможно (одна игра = один календарь), конфликт не достижим.
- Соглашение о нумерации дня недели (Mon=0 в Python, Sun/Sat-first в Qt-виджете) — может разойтись с ожиданиями C3 → фиксируем: протокол возвращает индекс в `week_names`/григорианский `date.weekday()` (Mon=0), а визуальный порядок колонок — забота C3.
- `from_key` по массиву офсетов бинарным поиском: O(log месяцы) — при 500 месяцах это 9 сравнений, риск производительности снимает D4.

## Migration Plan

Изменение аддитивное: два новых файла, приложение не меняется, мигрировать нечего. Откат — удаление файлов. C1 применит ядро к `era_key`/хукам/бэкфиллу отдельным изменением.

## Open Questions

- Имена дней недели и порядок колонок предпросмотра по умолчанию для пресета «Стандартный» (пн-вс vs вс-пн) — влияет только на отрисовку C3; индексы протокола от этого не зависят.
- Точное TEXT-кодирование координат (`IntercalaryDay`) в колонках БД — выбирается в C1, ядру не зависит.
