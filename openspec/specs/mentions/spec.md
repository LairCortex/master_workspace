# mentions Specification

## Purpose

Маркеры упоминаний в текстовых полях разбираются одной Python-грамматикой, display-имя следует за rename цели, а клик открывает живую цель или сообщает о мёртвой — без смены формата хранения и без QML.

## Requirements

### Requirement: Единая грамматика маркеров

Система SHALL разбирать и собирать маркеры хранения вида `@[display](тип:id)` одной qt-нулевой грамматикой. Разбор MUST извлекать display, тип и числовой id. Сборка маркера MUST снимать символы `[` и `]` только из display (колонка `name` цели SHALL NOT очищаться). Если после снятия скобок display пуст, система MUST подставить `"?"`. Views SHALL импортировать грамматику, а не дублировать её.

#### Scenario: Разбор валидного маркера

- **WHEN** в тексте есть маркер `@[Алиса](character:42)`
- **THEN** разбор даёт display «Алиса», тип `character`, id `42`

#### Scenario: Скобки снимаются только в маркере

- **WHEN** система собирает маркер из имени цели, содержащего `[` или `]`
- **THEN** в маркере этих символов в display нет, а сохранённое имя цели в колонке `name` не изменилось

#### Scenario: Пустой display после strip

- **WHEN** display после снятия `[` и `]` оказывается пустым
- **THEN** в маркере display равен `?`

#### Scenario: Вставка из попавера без скобок

- **WHEN** пользователь выбирает сущность в попавере завершения `@`, и у выбранного имени есть квадратные скобки
- **THEN** вставленный маркер хранения не содержит `[` и `]` в display

### Requirement: Rename переписывает display по типу и id

При сохранении существующей сущности или события, если поле `name` изменилось, система MUST в той же транзакции и том же commit переписать display всех маркеров этой пары тип+id. Отбор кандидатов MUST идти SQL `LIKE '%(тип:id)%'` по шести колонкам: `descriptions.characteristics`, `descriptions.backstory`, `characters.personality`, `characters.tasks`, `organizations.tasks`, `locations.tasks`; затем Python-rewrite, для которого авторитетны тип и id, а прежний display любой. Если `name` не изменилось, система SHALL NOT сканировать колонки. Create, delete, вставка из xlsx, чар-листы и поле `music_url` SHALL NOT запускать rewrite.

#### Scenario: Смена имени переписывает чужие тексты

- **WHEN** пользователь сохраняет сущность или событие с новым именем, и в одной из шести колонок есть маркер этой пары тип+id со старым display
- **THEN** после успешного commit маркер содержит новое display, тип и id те же

#### Scenario: Имя не менялось — скана нет

- **WHEN** пользователь сохраняет карточку или событие без смены `name`
- **THEN** тексты в шести колонках не переписываются ради упоминаний

#### Scenario: Rollback оставляет маркеры

- **WHEN** сохранение со сменой имени не дошло до commit и транзакция откатилась
- **THEN** маркеры в базе остались прежними

#### Scenario: Create и xlsx не переписывают

- **WHEN** создаётся новая сущность или событие (в том числе вставкой из xlsx)
- **THEN** существующие маркеры в шести колонках не переписываются

### Requirement: Клик по живому упоминанию открывает цель

Клик по маркеру существующей сущности MUST открывать её карточку. Клик по маркеру существующего события MUST открывать диалог события тем же путём, что двойной клик по событию на шкале (`parent` главного окна, стек диалогов как у карточек).

#### Scenario: Клик по живой сущности

- **WHEN** пользователь кликает mention сущности, которая есть в базе
- **THEN** открывается карточка этой сущности

#### Scenario: Клик по живому событию

- **WHEN** пользователь кликает mention события, которое есть в базе
- **THEN** открывается диалог правки этого события тем же путём, что dblclick на шкале

### Requirement: Клик по мёртвому упоминанию сообщает один раз

Если на клике по mention нет сервиса для типа или в базе нет строки с этим id, система MUST показать ровно один `QMessageBox` с одним и тем же текстом; ящик SHALL NOT быть `critical` и SHALL NOT дублироваться в statusBar. Двойной клик по событию на шкале, когда `get_event` пуст, SHALL оставаться без сообщения.

#### Scenario: Мёртвый id в mention

- **WHEN** пользователь кликает mention, тип которого известен, но строки с этим id нет
- **THEN** показан ровно один не-critical `QMessageBox`, карточка и диалог события не открываются, statusBar не меняется из-за этого клика

#### Scenario: Неизвестный тип на mention-клике

- **WHEN** пользователь кликает mention типа, для которого нет сервиса
- **THEN** показан тот же один не-critical `QMessageBox`, что и для отсутствующей строки

#### Scenario: Шкала молчит при отсутствии события

- **WHEN** пользователь дважды кликает событие на шкале, а загрузки события нет
- **THEN** модального сообщения нет
