# ui-testing Specification

## Purpose

Система UI-тестирования проекта: E2E-сценарии полного запуска приложения по основным пользовательским потокам, widget-тесты интерактивных views, детерминированная изоляция данных и сети, и гейт 100%-покрытия строк в CI.

## Requirements

### Requirement: E2E-сценарии основных пользовательских потоков

Система SHALL иметь автоматизированные системные тесты, запускающие реальное приложение (полный жизненный цикл, а не отдельные компоненты) на временной тестовой базе данных и проверяющие пользовательские потоки: создание новой игры в лаунчере, открытие существующей игры, создание/редактирование/удаление сущностей каждого из четырёх типов (персонажи, организации, локации, предметы), создание события и его редактирование в детальной панели, поиск, настройку подключения LLM (включая проверку соединения) и AI-генерацию значения поля, импорт данных из .xlsx, экспорт игры в архив .nri и переключение между играми.

#### Scenario: Новая игра

- **WHEN** пользователь создаёт новую игру в лаунчере
- **THEN** открывается главное окно, его заголовок содержит имя игры, таймлайн пуст

#### Scenario: Открытие существующей игры

- **WHEN** пользователь открывает существующую игру, содержащую данные
- **THEN** открывается главное окно и таймлайн показывает события этой игры

#### Scenario: CRUD сущностей

- **WHEN** пользователь создаёт сущность любого из четырёх типов из контекстного меню таймлайна, редактирует её в карточке сущности и удаляет
- **THEN** после сохранения сущность отображается в списке и детальной панели, после удаления исчезает из них

#### Scenario: Событие и детальная панель

- **WHEN** пользователь создаёт событие на таймлайне и редактирует его в детальной панели
- **THEN** событие отображается на таймлайне с обновлёнными значениями

#### Scenario: Поиск

- **WHEN** пользователь вводит поисковый запрос с учётом игнорирования регистра
- **THEN** результаты содержат сущности, совпадающие по имени

#### Scenario: Настройка LLM и генерация

- **WHEN** пользователь сохраняет подключение LLM, проверка соединения успешна, и затем запускает AI-генерацию значения поля
- **THEN** статус ассистента «ready», поле заполняется сгенерированным текстом

#### Scenario: Импорт из .xlsx

- **WHEN** пользователь импортирует .xlsx-файл, содержащий события и сущности
- **THEN** импортированные записи отображаются на таймлайне и в соответствующих списках

#### Scenario: Кастомные месяцы

- **WHEN** в игре имена месяцев получены переносом устаревшей настройки (мастер календаря ещё не существует, диалог настройки удалён)
- **THEN** таймлайн отображает даты с этими названиями

#### Scenario: Экспорт игры

- **WHEN** пользователь экспортирует текущую игру
- **THEN** создаётся архив .nri, содержащий базу данных игры

#### Scenario: Переключение игры

- **WHEN** пользователь переключается на другую игру из меню
- **THEN** открывается главное окно новой игры, предыдущее окно закрыто

### Requirement: Widget-тесты интерактивных views

Система SHALL иметь изолированные UI-тесты, управляющие мышью и клавиатурой интерактивными views приложения через их актуальную поверхность: реальный QML-остров для перенесённых экранов и widget для оставшихся нативных экранов/мостов. Тесты SHALL покрывать таймлайн (отрисовка событий, выбор элемента, контекстное меню), диалог события (сохранение, связанные сущности), детальную панель (отображение и редактирование), карточку сущности (режим редактирования, дополнительные поля по типам, изображение, связи, AI, сохранение без valid-гейта), редакторы дат (специальные даты), mentions (вставка и клик — widgets-редактор и библиотечное поле упоминаний через `QQuickWidget` с тестовым хостом, без продуктового диалога-стенда), обзор мира (режим «Показать всё»), AI-ассистента (статусы) и состояние приложения. Интерактивные QML-контролы SHALL адресоваться по `objectName`; карточка SHALL иметь semantic-приёмку по типам и один live-retheme-тест без потери введённых данных, выбора или скролла. Уже принятая поэлементная pixel-приёмка библиотечных компонентов SHALL не дублироваться в наборе карточки.

#### Scenario: Карточка сохраняет без valid-гейта

- **WHEN** в изолированном тесте пользователь нажимает Save в карточке сущности с пустыми полями
- **THEN** QML-остров эмитит запрос сохранения с текущими данными, не закрываясь до результата владельца

#### Scenario: Ошибка сохранения карточки

- **WHEN** владелец завершает сохранение карточки ошибкой
- **THEN** реальный остров остаётся открыт, сохраняет введённые данные и разрешает повторный Save

#### Scenario: Поля карточки различаются по типу

- **WHEN** тесты открывают карточку последовательно для каждого поддерживаемого типа сущности
- **THEN** через `objectName` доступны ровно базовые, дополнительные, image- и related-контролы, заданные конфигурацией каждого типа

#### Scenario: Валидация блокирует сохранение

- **WHEN** пользователь пытается сохранить событие с незаполненными обязательными полями
- **THEN** диалог события не принимает данные и указывает на ошибку; карточка сущности этим valid-гейтом не ограничена

#### Scenario: Взаимодействие с таймлайном

- **WHEN** пользователь кликает по отображаемому событию
- **THEN** в детальной панели загружаются данные этого события

#### Scenario: Клик по mention-ссылке

- **WHEN** пользователь кликает по mention-ссылке сущности в тексте
- **THEN** открывается соответствующая детальная карточка

#### Scenario: Статусы кнопки AI-ассистента

- **WHEN** LLM не настроен, а затем настроен
- **THEN** AI-действие сначала неактивно, затем активно с соответствующими текстами

#### Scenario: Live-retheme карточки сохраняет состояние

- **WHEN** тема переключается при открытой карточке с введённым текстом, выбранной связью и прокрученной формой
- **THEN** QML-остров использует новую палитру без потери текста, выбора, позиции скролла и без пересоздания общего движка

#### Scenario: QML-поле упоминаний через хост

- **WHEN** тесты библиотечного поля упоминаний поднимают `QQuickWidget` с хостом
- **THEN** контролы адресуются по `objectName` (корень, plain-слой, каретка, `mentionChip_<type>_<id>`); round-trip storage, попавер ≥2 символов / Esc / Space / backspace за `@` / Enter|клик вставки проходят без инстанцирования диалога события или карточки

### Requirement: Детерминированная изоляция данных и сети

UI-тесты SHALL NOT создавать данные за пределами временного каталога конкретного теста: база данных игры — реальный файл, но во временной каталог игр; конфиг подключения LLM — во временный файл. Тесты SHALL NOT выполнять реальные сетевые запросы: ответы сервера LLM предоставляются эмулируемым HTTP-транспортом с предустановленными данными. Файловые диалоги (открытие и экспорт) в сценариях SHALL заменяться stub-ами с предопределёнными путями.

#### Scenario: Нет артефактов вне tmp

- **WHEN** запущен полный прогон всех тестов
- **THEN** в каталоге игр проекта, домашнем каталоге пользователя и в сети нет новых файлов и запросов

#### Scenario: Сеть в LLM-потоках

- **WHEN** выполняется E2E-сценарий LLM (проверка соединения, генерация)
- **THEN** все HTTP-запросы обработаны эмулируемым транспортом с предустановленными ответами

### Requirement: Гейт 100%-покрытия строк

CI SHALL проверять, что строковое покрытие пакета приложения составляет 100%, и завершать сборку ошибкой при любом снижении. Веточное покрытие SHALL измеряться и отображаться в отчёте, но не использоваться как гейт. Исключения из покрытия: `if __name__ == "__main__":` (через exclude_lines) и `# pragma: no cover` — не более двух на весь пакет, каждое с обязательным обоснованием в примыкающем inline-комментарии.

#### Scenario: Непокрытая строка ломает CI

- **WHEN** в код попадает строка, не покрытая тестами
- **THEN** job тестов CI завершается ошибкой по гейту строкового покрытия

#### Scenario: Ветки не гейтят

- **WHEN** покрытие всех строк составляет 100%, а некоторые ветки покрыты частично
- **THEN** CI проходит, веточная метрика отображается только в отчёте

#### Scenario: Обоснованное исключение

- **WHEN** строка недостижима в тестах и не является `__main__`-гардом
- **THEN** она помечается `# pragma: no cover` с inline-обоснованием, общее число таких пометок не превышает двух

### Requirement: Внедрение HTTP-клиента приложения

Приложение SHALL принимать опциональный общий HTTP-клиент при конструировании; при отсутствии переданного клиента оно SHALL создавать собственный клиент с параметрами по умолчанию. Это SHALL позволять тестам запускать реальное приложение с эмулируемым клиентом сети.

#### Scenario: Старт с инжектируемым клиентом

- **WHEN** приложение стартует с переданным тестовым HTTP-клиентом
- **THEN** все запросы LLM (проверка соединения, генерация) выполняются через переданный клиент

#### Scenario: Старт без клиента

- **WHEN** приложение стартует без явной передачи клиента
- **THEN** оно использует стандартный клиент приложения с дефолтными таймаутами

### Requirement: Детерминированный жизненный цикл QML-островов в тестах

Изоляция тестов SHALL исключать саму частую причину недетерминированности QML-поверхностей: разрушение общего QML-движка, пока хотя бы один переживший тест `QQuickWidget`-остров держит на него ссылку. Сброс изоляции SHALL сначала довершить отложенные уничтожения и отсроченные релизы островов, затем отвязать и уничтожить все оставшиеся живые острова и только затем разрушать движок; порядок «острова → движок → тема-runtime» SHALL сохраняться. В production-коде приложение по-прежнему не разрушает движок, и контракт «движок один на приложение» не меняется.

#### Scenario: Живой остров переживает сброс

- **WHEN** тест оставил живым незакрытый QML-остров и завершился, после чего автофикстура-сброс разрушает движок, а позже сборщик мусора добирается до пережившего виджета
- **THEN** ни на одном из этих шагов не происходит падения (включая SIGSEGV внутри загрузки источника острова), и Python-ссылка на уничтоженный остров остаётся безопасной (обращения к ней сигнализируют об уничтоженном объекте, а не рушат процесс)

#### Scenario: Отложенные релизы исполняются до смерти движка

- **WHEN** к моменту сброса у переживших оболочек диалогов стоят в очереди отложенные уничтожения виджетов и отсроченные освобождения островов
- **THEN** они исполняются, пока движок ещё жив, и ни один отложенный колбэк не обращения к уже разрушенному движку (нет ошибок teardown вида search-wiring)

#### Scenario: Пиксельная приёмка при зафиксированном коэффициенте пикселей

- **WHEN** тестовый процесс запускается на хосте с Retina-экраном (устройство сообщает удвоенный коэффициент пикселей)
- **THEN**grab-пиксели островов измеримы в логических пикселях (коэффициент = 1) одинаково на локальной машине и в CI, а отдельный guard-тест падает первым, если фиксация коэффициента когда-либо сломается

#### Scenario: Повторный setup после сброса

- **WHEN** после сброса изоляции следующий тест снова запрашивает QML-остров
- **THEN** создаётся ровно один движок (прежняя проверка «ровно один движок» проходит), и остров на нём работает как обычно
