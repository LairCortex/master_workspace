# llm-remote-provider Specification

## Purpose

Генерация контента AI-ассистентом через внешнюю LLM по OpenAI-совместимому API: подключение, генерация полей, обработка ошибок и проверка соединения.

## Requirements

### Requirement: Генерация через OpenAI-совместимый endpoint

Система SHALL выполнять генерацию текста, обращаясь к OpenAI-совместимому API (`POST {base_url}/chat/completions`) с заданными пользователем `base_url` и именем модели, и SHALL поддерживать как облачные провайдеры (OpenAI, OpenRouter, Groq и др.), так и локальные OpenAI-совместимые серверы (Ollama, vLLM, LM Studio, llama.cpp server). Запросы генерации разных полей (в том числе запуск «всех полей сразу» на уровне одной сущности) SHALL выполняться параллельно: каждый запрос выполняется независимо от остальных, без общей последовательной очереди; результат записывается в своё поле по завершении этого запроса.

#### Scenario: Успешная генерация поля

- **WHEN** пользователь нажимает AI-кнопку при настроенном и корректном подключении
- **THEN** поле заполняется сгенерированным текстом, блокировка поля снимается, прогресс индикатор исчезает

#### Scenario: Локальный сервер без ключа

- **WHEN** в подключении задан локальный endpoint (например, Ollama на этой машине) и ключ не задан
- **THEN** генерация выполняется успешно (пустой ключ допустим)

#### Scenario: Последовательная генерация нескольких полей

- **WHEN** пользователь запускает генерацию нескольких полей подряд (независимые нажатия AI-кнопок или бандл «сгенерировать сущность», предыдущие генерации ещё не завершены)
- **THEN** каждый запрос стартует без ожидания завершения предыдущих (общей последовательной очереди нет) и выполняется параллельно с остальными, а результат попадает в своё поле по завершении этого запроса

### Requirement: Политика запросов — таймауты и повторы

Система SHALL ограничивать каждый запрос таймаутами (установление соединения — 10 секунд, ожидание ответа — 120 секунд) и SHALL автоматически повторять запрос (не более 2 повторений с увеличивающейся задержкой) только при сетевых сбоях, таймаутах и ответах 429/5xx; на прочие ошибки клиента (прочие 4xx) повторять запрос система не должна.

#### Scenario: Успех после повторной попытки

- **WHEN** первая попытка запроса завершилась ошибкой 503 или таймаутом, а повторная попытка успешна
- **THEN** пользователь получает результат генерации без повторного нажатия кнопки

#### Scenario: Неисправимая ошибка клиента без повтора

- **WHEN** сервер ответил ошибкой 401, 403 или 404
- **THEN** система не повторяет запрос и сразу показывает пользователю соответствующую ошибку

### Requirement: Обработка ошибок генерации

Система SHALL сообщать об ошибках генерации понятным пользователю текстом на русском языке: ошибки авторизации/доступа (401/403) — «неверный ключ или недостаточно прав», 404 — «модель или endpoint не найдены», 429 — «превышен лимит запросов», таймаут — «время ожидания ответа истекло», недоступность сети — «сервер LLM недоступен». При ошибке содержимое поля SHALL оставаться неизменным, а кнопка AI — возвратиться в активное состояние. Ошибка одиночной генерации SHALL показываться пользователю диалогом с названием поля и причиной; если завершается волна, в которой несколько запросов завершились ошибкой, система SHALL показать один диалог со списком всех неудавшихся полей и причинами (при одинаковой причине — один раз).

#### Scenario: Неверный ключ

- **WHEN** генерация завершилась ошибкой 401/403
- **THEN** пользователю показывается диалог с названием поля и сообщением о неверном ключе, текст поля не меняется

#### Scenario: Сбой генерации не блокирует работу

- **WHEN** генерация завершилась любой ошибкой
- **THEN** поле остаётся с прежним содержимым, редактируемым, и пользователь может повторить генерацию

#### Scenario: Ошибка бандла

- **WHEN** по завершении волны генерации сущности часть полей завершилась ошибкой, а часть — успешно
- **THEN** показывается один диалог со списком неудавшихся полей и причинами, успешные поля остаются заполненными

### Requirement: Проверка соединения

Система SHALL предоставлять пользователю проверку подключения LLM: минимальный тестовый запрос (генерация одного токена) к заданному endpoint с заданной моделью, по результатам которого система сообщает об успешном соединении или причине ошибки. Непрошедшая проверка не SHALL блокировать сохранение настроек.

#### Scenario: Успешная проверка

- **WHEN** пользователь нажимает «Проверить соединение» при корректных настройках
- **THEN** система показывает, что соединение установлено

#### Scenario: Неудачная проверка

- **WHEN** тестовый запрос завершился ошибкой (неверный ключ, неверная модель, сервер недоступен)
- **THEN** система показывает причину ошибки и позволяет сохранить или отредактировать настройки
