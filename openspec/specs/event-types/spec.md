# event-types Specification

## Purpose

Пользовательские типы событий внутри одной игры: закрытая палитра цветов-индексов, НРИ-набор по умолчанию, редактирование типов и назначение типа событию — чтобы шкала событий могла различать события цветом, не ломая единую дизайн-палитру.

## Requirements

### Requirement: Типы событий хранятся в игре

Каждая игра SHALL хранить собственный упорядоченный набор типов событий: тип имеет название и цвет-индекс из поставляемой палитры. Событие SHALL иметь не более одного типа; отсутствие типа — валидное состояние. Набор типов не SHALL переезжать между играми и не SHALL читаться из файлов темы. При первом открытии старой игры (миграция) в пустой набор SHALL быть посажен набор по умолчанию: **Сюжет, Побочное, Слух, Встреча, Ров будней, Находка** — в этом порядке, с цветами палитры по порядку индексов.

#### Scenario: Старая игра получает набор по умолчанию

- **WHEN** игра без таблицы типов открывается новой версией приложения
- **THEN** набор типов содержит шесть значений по умолчанию в указанном порядке, ни одно событие не имеет типа

#### Scenario: Типы не общие между играми

- **WHEN** в одной игре переименован или добавлен тип
- **THEN** в другой игре набор типов не изменился

#### Scenario: Событие без типа

- **WHEN** событие создано или отредактировано с пустым выбором типа
- **THEN** событие сохранено без типа и отображается как событие без типа

### Requirement: Тип назначается событию из списка

Диалог создания и редактирования события SHALL предоставлять выбор типа из текущего набора игры: активные типы с их цветами, option «без типа» и текущее значение по умолчанию. На острове события строка типа SHALL быть выпадающим списком с образцом цвета палитры типа; выпадающий список SHALL не обрезаться краем острова — если обрезка обнаруживается на приёмке, допускается widgets-combo как единственный fallback, без смены набора типов и без colorpicker. Назначение типа SHALL сохраняться вместе с событием и быть видимым в шкале (цветная метка строки). Тип события не SHALL влиять на фильтры, поиск или панель деталей этого куска.

#### Scenario: Выбор и сохранение типа

- **WHEN** в диалоге события выбран тип «Слух» и диалог подтверждён
- **THEN** событие сохранено с этим типом, его строка на шкале отмечена цветом типа

#### Scenario: Снятый тип

- **WHEN** у события с типом выбрать «без типа» и подтвердить
- **THEN** событие сохранено без типа, метка цвета в его строке исчезла

#### Scenario: Образец цвета в селекторе

- **WHEN** в наборе игры есть тип с индексом палитры
- **THEN** в селекторе типа диалога события рядом с именем виден образец этого индекса, без произвольного colorpicker

### Requirement: Набор типов редактируется диалогом из панели событий

Панель событий SHALL предоставлять пункт «Типы событий…» в своём «+»-меню, открывающий QML-остров управления набором в прежнем нативном диалоговом контейнере: переименование типа, изменение порядка, добавление типа, удаление типа и выбор цвета типа из поставляемой палитры `color.chart.1…8` (готовые образцы, не произвольный colorpicker). Каждое изменение SHALL применяться к игре сразу через синхронный запрос тонкой view model и отражаться на всех существующих событиях этого типа без их пересохранения. Диалог SHALL оставаться write-through: кнопки Save и подтверждения изменений при закрытии SHALL отсутствовать; закрытие не SHALL откатывать уже применённые изменения. QML SHALL только отображать состояние и эмитить запросы, а публичный Python API фасада SHALL сохраняться 1:1.

#### Scenario: Переименование видно в назначении

- **WHEN** в диалоге типов переименовать тип, назначенный событиям, и закрыть диалог
- **THEN** изменение применено немедленно, в диалоге события тот же тип отображается новым именем, его цвет не изменился

#### Scenario: Палитра, а не colorpicker

- **WHEN** открыть выбор цвета типа
- **THEN** доступны ровно восемь готовых образцов `color.chart.1…8` и никакой возможности задать произвольный цвет нет

#### Scenario: Изменение порядка применяется сразу

- **WHEN** пользователь перемещает тип в списке
- **THEN** новый порядок записывается сразу и виден всем потребителям без кнопки Save

#### Scenario: Закрытие без подтверждения

- **WHEN** пользователь изменил название, порядок или цвет и закрывает диалог
- **THEN** подтверждение и Save не показываются, а уже применённые изменения сохраняются

#### Scenario: Запросы проходят через фасад

- **WHEN** пользователь добавляет, переименовывает, перемещает, перекрашивает или удаляет тип
- **THEN** QML эмитит синхронный запрос view model, операция проходит через прежний публичный API Python-фасада, а сервисы не передаются в QML

### Requirement: Удаление типа отвязывает события

Удаление типа, назначенного событиям, SHALL быть возможном и SHALL отвязать этот тип от всех событий (события остаются валидными событиями без типа); удаления или иного изменения самих событий при этом быть не SHALL.

#### Scenario: Удаление занятого типа

- **WHEN** удалён тип, который имели три события
- **THEN** события целы, ни у одного из них типа нет; остальные типы и их назначения не затронуты
